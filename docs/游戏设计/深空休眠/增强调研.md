# 深空休眠 玩法/视觉增强调研（v2：复刻原型的空间与镜头）

> 2026-10-12。**第二轮调研**，起因是用户反馈：
> 「现在的视觉上和猛鬼宿舍差别比较大，他是有个主角可以操作移动的，自己跑到房间里面
> 躺下，并且可以滑动屏幕查看地图上其他位置的情况，你再搜索调研一下，视觉和玩法尽量复现」
>
> 第一轮调研见 [调研.md](调研.md)（新游戏选型，30 条来源）。**本文档只覆盖第一轮
> 漏掉或误判的部分**：原型的**空间结构、相机、角色操作、开局流程、视觉语言**。
> 第一轮把注意力放在「经济 / 塔防 / 数值」上，空间与镜头这一层几乎没看，
> 于是做出了一个「单间舱室 + 环形通道条」的抽象界面——机制在，**体感不在**。
>
> **「采纳 / 不采纳」清单在 §6，含推翻第一轮决策的说明——那份清单标了
> 「不要重新评估」，本次是用户明确要求推翻，逐条写清了为什么。**

## 0. 差距诊断：我们做成了什么，原型是什么

| | 本作现状（v1.11.0） | 原型《猛鬼宿舍》 |
|---|---|---|
| **视图** | 单间舱室的格子网格（一屏一间） | **整层楼的俯视平面图**，比屏幕大，相机跟随角色 |
| **地图** | 6 间舱室围一条**环形通道**（抽象示意） | 12 间**不规则凹形**房间 + **网格状走廊**网络 |
| **角色** | 没有角色。玩家 = 一个座位 | **可操控的小人**，左下角虚拟摇杆，在走廊里跑 |
| **开局** | 点选舱室（20 秒，冲突随机判） | **跑到一间空房 → 关门 → 上床**（20-30 秒） |
| **镜头** | 固定，无滑动 | **拖动滑动看全楼**；相机跟随角色 |
| **门** | 屏幕下方一条「门带」 | **画在房间靠走廊那面墙上**，带血条 + 升级箭头 |
| **建筑** | 格子里的图标 + 底部 Sheet | **压在格子上的实体**，头顶浮 `+N` 产出数字 |
| **鬼** | 环形通道条上一个圆点 | 走廊里走动的**实体**，头顶红色血条 + LV |
| **HUD** | 顶部资源 + 计时器 | 左上资源、**上中一排玩家头像胶囊**、右侧 FF/加速 |

**结论**：玩法骨架（双资源 / 三条升级线 / 威胁撞门进化 / 点空地建造）第一轮抄对了，
**但「你是一个在楼里跑的人」这件事完全没做出来**——而那正是原型体感的核心：
*「我在被追，我要赶紧找一间房躲进去」*。没有角色、没有空间，就没有这个体感。

## 1. 空间结构（第一轮完全没覆盖）

### 1.1 地图是整层楼的俯视平面图

12 间宿舍，**左到右为 A/B/C 列、上到下为 1/2/3/4 行**，共 3 列 × 4 行。
（[18183 微信小游戏](https://www.18183.com/down/8795508.html)、
[18183 正版](https://www.18183.com/zhxz/8885015.html)、
[游戏狗](https://www.gamedog.cn/android/4014997.html)）

**房间是不规则凹形**，不是矩形——攻略里反复提「凹形布局最合适」「U 形」「L 形」
「对开门房间」。截图（§5）里能直接看到 L 形 / U 形 / T 形三种轮廓。
这是**刻意的**：凹形决定了「炮台往哪儿摆能形成交叉火力」，
[18183 安卓版](https://www.18183.com/zhxz/8979746.html)明确说
「每个房间都提供独特的战术空间，需要根据房间结构合理放置炮塔，**形成交叉火力网**」。

**走廊是网格状网络**，不是一条环：纵向主走廊 + 多条横向支廊，
房间挂在走廊两侧，门开向走廊。截图 m1（§5）里能看到两条纵向走廊夹着房间列。

### 1.2 相机：跟随 + 可拖动

- 「进入游戏后，使用**左下角的轮盘**，赶紧找到一间无人的房间」
  （[九游](https://www.9game.cn/wenda/423765.html)、
  [豌豆荚](https://m.wandoujia.com/download/22064/)：「点击下面的滚轮按钮可以移动」）
- 「**你也可以滑动屏幕查看猎梦者的位置**」
  （[18183 新手教学](https://www.18183.com/zhxz/9013823.html)）
- 「倒计时结束前**快速滑动视角浏览 12 间宿舍**，重点锁定 B1、A2、B3、A4 四间」
  （[17 手游网](https://m.17xy.cn/soft/2864.html)）

即：**双指/单指拖动 = 平移相机；摇杆 = 移动角色**，两者独立。
相机默认跟随角色，拖走后停在原地（再看摇杆才回去）。

> 移动端同类实现的通行做法（外部参考）：相机跟随时**不要硬锁**，
> 玩家拖走后进入「自由视角」，角色移动或点「回到我的位置」再恢复跟随——
> 硬锁会让「我想看看队友那边」这个操作根本做不出来。
> （[Unity Cinemachine 跟随相机文档](https://docs.unity3d.com/Packages/com.unity.cinemachine@2.9/manual/CinemachineBodyFramingTransposer.html)）

### 1.3 玩家之间的空间关系有意义

- 猎梦者**从地图一角出生**，所以「往远离出生点的角落跑」能多争取约 2 分钟发育时间
  （[幻想游戏网](http://m.hxgame.net/azgame/999276.html)）
- 「选宿舍注意 2 点，一个是门要在上方位置，二尽量选择较远的位置……
  **偏远位置可以让猛鬼不会第一时间走到玩家这里进行攻击，优先攻击其他队友的房间**」
  （[87G 国际服](https://m.87g.com/youxi/102372.html)）

**位置因此是一个真实资源**：离鬼越远越安全，但离队友越远越难被救。
这一层博弈在第一轮的「同时点选舱室」里被完全抹掉了。

## 2. 开局：跑动抢房（第一轮明确否决过，本次推翻）

### 2.1 原型的流程

1. 匹配后所有人**站在走廊里**，有几句对话气泡（截图 s1）
2. **20-30 秒倒计时**，用左下角摇杆跑到一间空房
3. 进房 → **关门** → **上床** → 开始产金币
4. 倒计时结束，**猛鬼从气闸/走廊尽头入场**开始砸门

### 2.2 走廊里的危险

> 「如果出现**红色倒计时**，请马上离开走廊，否则我们无法保证你的安全。」
> 「请不要尾随其他同学进入宿舍。如果你进入宿舍后发现**床上有人**，请尽快远离房间。」
> ——[豌豆荚（游戏内规则文本原文）](https://m.wandoujia.com/download/22064/)

即走廊是**致命区**，且**一间房只能一个人**（床上有人就得走）。

### 2.3 本作怎么处理（**这条要改，见 §6 不采纳 #1**）

「4 人房里有人在开局 20 秒被淘汰」的体验问题，第一轮的理由今天依然成立。
本作保留**跑动抢房**（用户明确要求），但把「被抓」从**淘汰**改成
**撞倒 + 掉落生物能 + 击退**——张力保留（你会被撞飞、会损失资源、
会离想去的房间更远），但不会有人 20 秒就出局。

**这是本次唯一一处「不照抄」**，理由写在 §6。

| 机制 | 内容 | 来源 |
|---|---|---|

| **可以进队友房间替他花钱** | 剧情模式「帮你花钱」：站在队友房里可以**花队友的钱**给他造炮台 | [游戏截图 m4 §5] |
| **双人宿舍模式** | 两名玩家**共享一间房与资源**，分工布防 | [幻想游戏网](http://m.hxgame.net/azgame/999276.html) |
| **鬼的逃跑线** | 血量掉到阈值 → 撤退回血；「打掉血鬼会跑，然后回复正常」 | [九游](https://www.9game.cn/wenda/423765.html) |
| **靠挠门升级** | 鬼**每次攻击都在升级**，所以打掉它血 = 拖慢它成长 | [87G 国际服](https://m.87g.com/youxi/102372.html) |
| **狂暴 / 震撼** | 狂暴：门血见底触发，短时攻速攻击力暴涨；震撼：范围眩晕炮台 3 秒 | [好游快爆](https://m.3839.com/wenda/n/700/3759700.htm) |
| **门朝上是优势** | 门朝上的房间，鬼砸门时血条不会被鬼的身体挡住 | [87G 国际服](https://m.87g.com/youxi/102372.html) |
| **玩法出处** | 底层借鉴《魔兽争霸 3》RPG 地图《**巨魔与精灵**》 | [竞核 / 今日头条](http://m.toutiao.com/group/7657442429695558182/) |

> **「门朝上是优势」是设计缺陷，不复刻**（第一轮已判，理由不变）：
> 血条被遮挡是**信息呈现问题**，正解是把血条画在不会被遮挡的层（屏幕空间 UI），
> 而不是让玩家靠选房间朝向规避。本作门一律画在房间靠走廊那面墙上，
> **血条抬到门体上方一个固定高度的浮层**，任何朝向都读得到。

## 4. 视觉语言拆解（截图逐项，见 §5 的图）

原型是**暗色低饱和的像素/低分辨率卡通**（[18183 2026 版](https://www.18183.com/down/8877093.html)：
「采用**像素卡通风格**画面」；[18183 官方版](https://www.18183.com/zhxz/8885008.html)：
「**昏暗的像素画风**」）。

拆到「可实现的构图规则」这一层：

| 元素 | 做法 |
|---|---|
| **地板** | 房间内是**灰色瓷砖网格**，每格可见；空地格中央一个 `+` |
| **墙体** | 房间轮廓外一圈**厚深色墙**；房间形状是凹形（L/U/T） |
| **走廊** | **棕色砖纹地砖**，与房间的灰瓷砖在色相和纹理上都分开 |
| **门** | 嵌在房间靠走廊那面墙上，一个深色门框 + **门体上方一条绿色血条** + **绿色圆形升级箭头** |
| **床** | 占一格，床头有橙色金币图标 + 浮动的 `+N`（每秒产出） |
| **建筑** | 占一格，压在瓷砖上，头顶浮 `+N` + 对应资源图标（金币 / 闪电） |
| **鬼** | 走廊里一个 Q 版人形实体，头顶**红色血条 + `LV.n`** |
| **角色** | Q 版小人，头顶一个小名牌；在走廊里跑动 |
| **HUD** | 左上：金币 + 闪电两个资源；上中：**一排玩家头像胶囊**（含各自房间等级）；右侧：`FF`（快进）与「加速」圆钮；右下：**维修**圆钮；左下：**摇杆** |
| **氛围** | 走廊灯光忽明忽暗，且**随鬼的等级推进逐段熄灭** |

> 氛围那条来自玩家长评：「宿舍走廊的昏暗灯光、猛鬼破门时的木屑飞溅、
> 炮台攻击时的特效（比如闪电塔的连锁电流），细节做得很到位，尤其
> **『走廊灯光随猛鬼等级熄灭』**的设定，关灯后突然跳出的影子真的会吓一跳」
> ——[233 乐园玩家长评](https://www.233leyuan.com/game-user-comment/6921eb4b8f7300005e594cb0)
>
> 这是**用环境叙事表达难度曲线**的好例子：灯灭到哪，鬼就强到哪。
> 比一个数字更直观，而且不需要音频（本项目零音频基础设施）。

## 6. 采纳 / 不采纳清单

### ✅ 采纳

| # | 机制 / 做法 | 理由 |
|---|---|---|
| 1 | **整层楼的俯视平面图**（比屏幕大） | 这是「体感」的地基。没有空间就没有「被追」 |
| 2 | **可操控角色 + 左下角虚拟摇杆** | 用户明确要求；也是「跑到房间躺下」这条体验的前提 |
| 3 | **相机跟随 + 拖动平移** | 用户明确要求；且「看队友/看鬼在哪」是协作的信息基础（第一轮 §1.6 的体验公式同样要求威胁可见） |
| 4 | **开局跑动抢房**（倒计时内跑到空房 → 关门 → 上床） | 用户明确要求。**推翻第一轮 #4**，理由见下 |
| 5 | **走廊是网格状网络**（纵向主走廊 + 横向支廊） | 房间挂两侧、门开向走廊；鬼沿走廊巡逻与追击 |
| 6 | **房间是不规则凹形** | 「凹形决定炮台摆位 → 交叉火力」是它的空间策略。每局随机分配形状 |
| 7 | **门画在房间靠走廊那面墙上**（血条 + 升级箭头） | 让「门在哪」和「鬼在撞哪扇门」在同一个视野里 |
| 8 | **建筑/床头顶浮产出数字** | 让「这格在产多少」不用点开就知道——它是布局决策的依据 |
| 9 | **上中一排玩家头像胶囊** | 一眼看到队友的房间等级与存活状态。协作游戏的信息基础 |
| 10 | **鬼从地图一角入场**；位置即资源 | 让「选哪间房」重新变成一个真决策（离鬼远 vs 离队友近） |
| 11 | **走廊灯光随鬼的等级推进逐段熄灭** | 用环境表达难度曲线，零音频成本。配 WCAG 1.4.1 的第二通道（见下） |
| 12 | **可以走进队友的房间**（看到他的布局、替他修补） | 第一轮已有「全站浮层修补队友」；有空间之后直接走过去更自然 |

### ❌ 不采纳（**含推翻第一轮的条目**）

| # | 方向 | 理由 |
|---|---|---|
| 1 | ~~**「走廊里被鬼抓到 → 直接淘汰」**（原型行为）~~ **⚠️ 已于第四轮推翻，见 §9.4** | 本作是 **2-4 人合作**，原型是 6 人各自为战。有人开局 20 秒出局，剩下的人要陪一局 6 分钟的残局。当年改为：撞倒 + 掉落生物能 + 击退。**第四轮用户要求「碰到鬼直接死」**，理由是「躺下后不能起身」落地后对局阶段走廊里本来就不该有人 —— 详见 §9.4 |
| 2 | **像素画风**（真·位图像素） | 项目零位图资源管线，全部美术是手写矢量 SVG（`icons.tsx`）。引入像素要么内联 base64 PNG（不可维护），要么用几千个 `<Rect>` 手搓。**采纳的是「构图与信息布局」，不是「像素」**——用矢量做「暗色扁平 + 可见瓷砖网格 + 砖纹走廊」，远看与原型同构 |
| 3 | **一间房只能一个人**（原型的「床上有人请离开」） | 本作有 6 间房 / 最多 4 人，本来就够分。强制独占会让「抢房」变成纯手速竞争，且失败者无房可去（原型是 12 间房 6 人）。**改为：一间房可容纳多人**（双人宿舍模式的做法），但**床只有一张**，先上床的人产资源、后到的人只能建造——保留「抢」但不制造「无家可归」 |
| 4 | **门朝向影响可读性**（门朝上有优势） | 设计缺陷，见 §3 末。正解是把血条画在固定高度的浮层上 |
| 5 | **`FF` 快进按钮** | 原型是**单机**，快进只影响自己。本作是联机对战，任何人快进都会改变所有人的时间轴——要么全员投票（回到已删掉的 rematch 投票那类复杂度），要么就是作弊。**不做** |

## 8. 第三轮补充（2026-10-12，用户实测反馈驱动）

用户在 v2 上线后报了一批问题，其中三条要联网查原型才知道「该长什么样」。
本节是那一轮的调研记录，**结论已经落进实现**。

### 8.1 床与门的等级耦合 ✅ 采纳

**原型规则**：「前期有钱优先升级床，**只需要在升级小床必须要门的等级对应的时候
才升级门**，其他时候不升级门」（[TapTap 猛鬼宿舍综合攻略](https://www.taptap.cn/app/227077/strategy/entity/32268152?page=2)）。
几份攻略给出的实操节奏都是两种升级交替推进：

> 床升到＋2 → 门升到 2 级铁门 → 床升到＋8 → 门升到 5 级铁门 → 床升到＋16 →
> 炮升到 2 级 → 床升到＋32 → 门升到 3 级钢门 → 床升到＋64 …
> （[刷机之家 — 无限金币攻略](http://www.shuajizhijia.net/game/166494.html)）

**本作落地**：**升休眠舱到 Lv N+1 需要气密门 ≥ Lv N**。5 级对 5 级，
所以节奏是「床一级、门一级」交替。理由（不是照抄）：它把「先经济还是先防御」
从一句口号变成一条硬约束 —— 想更快产资源就必须先把门升上去保住它，
而不是把钱全砸进床、门破人亡。**用户明确要求这条**（「床铺升级应该有个门的
等级的前置条件」），并指出当时弹窗里看不出来 —— 现在门槛文案直接写在弹窗里。

不采纳的部分：原型的门有 10 级（铁门 5 + 钢门 5）、床有 10+ 级，本作两边都封顶
5 级（一盘 6 分钟，10 级升不完）；也不做原型的「门材质分级」（铁/钢）——
那是纯皮肤，本作的门等级已经有材质纹理 + 数字两条通道。

### 8.2 墙壁占一格 ✅ 采纳

**原型**：房间是从一整块**深色砖体**里挖出来的，四周的墙是实打实的砖（有砖缝、
有厚度）；地板是另一套浅色瓷砖，格与格之间有斜面（上/左亮、下/右暗）。
见本目录 §5 的参考图 `tmp/猛鬼宿舍参考/m1.jpg`。

**本作落地**：舱室 = 1 格厚的舱壁圈 + 5×4 不规则内部，包围盒 7×6。
**用户明确要求**（「房间墙壁可以建模成一格宽，就和猛鬼宿舍一样」）。

**与原型不同的一处（有意）**：原型没有「通道」这一层材质 —— 房间之外全是同一片
深砖。本作**必须**区分通道与舱壁，因为通道是可通行的危险区（静默体在那走、
在那撞人），而舱壁不可通行。地板已经压得很暗（`#2A3A50`），再给墙留一档更暗的
根本没空间（纯黑对地板也只有 1.82:1），所以**反过来**：舱壁比地板亮一档，
读作「实心的金属结构件」，明度阶梯变成 通道 < 地板 < 舱壁。实测
vs 地板 2.24 ｜ vs 通道 3.15 ｜ vs 深空 3.63。

### 8.3 相机要能推出地图边界 ✅ 采纳（工程项，不是原型调研）

原型的相机在整层楼平面图上自由拖，没有「贴边就卡住」的设定。本作原来把相机夹死在
`[vw − MAP_W, 0]`，**地图最外圈的格子永远只能露出半格、点不到**（用户实测报的）。
现在四个边各留 2 格余量（`PAN_MARGIN`）。

### 8.4 摇杆手感：两个自己造出来的坑（工程项）

不是原型调研，是**实测轨迹**量出来的。用 60fps 采样「角色在地图坐标系里的位置」，
发现按住摇杆不动时轨迹是「匀速走 0.45 秒 → 原地停住」：

| 坑 | 症状 | 修法 |
|---|---|---|
| `onDir` 被 180ms 节流 | 拖动时角色一跳一跳地拐弯（朝向 5.5 Hz 更新） | 预演朝向**每个 move 事件都更新**；上行频率另在主循环节流（80ms） |
| 700ms 看门狗 | **按住不动 = 收不到 move 事件**，被误判成「手势被抢走」→ 角色走两步停一下 | **删掉看门狗**；横拖被浏览器抢走这件事已由 `touch-action: none` 根治，兜底是 `onPanResponderTerminate` |

修完实测 **3.68 格/秒**（服务端 3.6），轨迹是直线的。教训：**看门狗的判据必须是
「真的出错了」，不能是「一段时间没消息」** —— 后者的正常情况（手指按住不动）
恰恰是最常见的输入形态。

### 9.4 为什么推翻 §6 不采纳 #1（「走廊被抓不淘汰」）

§6 当初的理由是：「本作 2-6 人合作，原型 6 人各自为战，有人开局 20 秒出局要陪一局
残局」。**这个理由在规则 1+2 落地后就不成立了**：

- 规则 2 之后，对局阶段**没有任何玩家需要待在走廊里**。走廊只在跑动阶段有人。
- 而静默体在跑动阶段根本不动（`advance` 按 phase 挡住）。于是「走廊接触」只可能
  发生在**倒计时结束、而这个人还没躺下**的时候。

所以「碰到鬼直接死」不再是「随机开局暴毙」，而变成了**「倒计时结束前必须躺下」这条
规则的执法者**：它惩罚的是没躺下的人，不是运气不好的人。原来的三件套（撞倒 + 掉资源
+ 击退）在新规则下反而会制造一个说不通的中间态 —— 人被撞倒、掉钱、禁足 1.5 秒，
但他**本来就哪儿也不用去**。

**代价（如实记）**：`KNOCK_*` 四个常量、`down_until_ms` / `immune_until_ms` 两个字段、
`player_knocked` 事件随之删除；「走廊危险」这条张力在**对局阶段**消失了（跑动阶段本来
就没有，静默体那时不动）。如果以后要恢复「出舱行动」，这一节是起点。

## 10. 第五轮补充（2026-10-13，四矿拆分 + 前端美术 + 交互手感）

用户这一轮给了三件事：①**培养槽改成建造菜单里四个独立条目**；②**前端美术优化**
（更好的贴图、炮台子弹的贴图与特效、点炮台显示攻击范围），并明确「优先用矢量图，
实在需要再用生图 skill」；③**交互手感优化**。三件事都要求先联网调研再开工。

### 10.1 四座矿是四个独立条目（§9.1 那张表的一处修正）

§9.1 把矿写成「培养槽（铜矿）可升 4 级，升级价 1024/2048/4096」。**这个呈现方式
与原作不符** —— 原作的四种矿在道具列表里是**四个并列的条目**，各自有独立的
「放置需要 X 闪电」[64][65][66]：

| 条目 | 放置价 | 产率 |
|---|---|---|
| 铜矿 | 128 闪电 | 8 金币/秒 |
| 银矿 | 1024 闪电 | 32 金币/秒 |
| 金矿 | 2048 闪电 | 128 金币/秒 |
| 钻石矿 | 4096 闪电 | 512 金币/秒 |

**原作两种口径其实都成立**：攻略正文既写「银矿：铜矿的**升级版**」，也有玩家说
「你**升级**的钱都快够**买**一个钻矿了」[58] —— 说明原作里既能原地升级、也能直接
放置。**本作只保留「直接放置」**，理由：两条路并存时，升级链**恒为劣选**
（128+1024 > 1024），留着就是一份永远不该点的 UI。删除升级链之后，四座矿各自
只有一个等级，`MINE_RATE` 按 kind 取值。

**经济的总量没变**：走完升级链到 512/秒 要 128+1024+2048+4096 = 7296 合金，
直接放钻石矿只要 4096 —— 所以这次拆分让高级矿**更便宜**，不会把游戏改难。

### 10.2 美术：可读性优先，矢量优先（**本轮不调生图 skill**）

俯视 2D 的可读性调研给出三条硬规则 [68][69][70]：

1. **剪影优先**。俯视视角下玩家看到的是「顶面 + 一点点侧面」，细节在 44px 的
   格子里全糊掉，**能区分的只有轮廓**。所以每种建筑要给一个**独一无二的外轮廓**，
   而不是同一个方框里换一个小图标。
2. **明度分组优先于色相**。同一组东西（墙/地板/机器/单位）在灰度下也要分得开。
3. **轮廓靠线，不靠填充**。这条本项目已经踩过一次（俄罗斯方块：把空位填充调亮
   的结果是整块盘面变成一片浅灰、格子之间依旧没有分界，最后是靠 `tetrisGrid`
   格线解决的）。新贴图一律带深墨描边。

**为什么不用生图**（用户给了这个选项，明确否决并记下理由）：
- 项目**全部图标是手写矢量**（`icons.tsx`），且项目规范写着「颜色只有
  `theme.ts` 一个来源」。位图会引入第二种视觉语言，且颜色无法跟随主题。
- 本屏有**相机平移**（`camXY`）与**全站浮层**两套缩放，位图在非整数缩放下会糊。
- 位图要进 `app/assets/` + `require()`，还得为不同密度出 @2x/@3x；矢量一套走天下。
- 调研里那些「好看」的塔防素材包 [71][72][73] 全是**位图/像素画**，与本作
  「深空站 + 矢量」的基调也不同。

**落地**：新建 `app/src/stasisArt.tsx`，每个单位一张 `viewBox="0 0 44 44"` 的整格
矢量贴图，统一「**底座 → 主体剪影 → 左上高光 → 深墨描边 → 右下等级徽标**」五层。
地板/舱壁/通道**加纹理但不加填充**：每格一条格线，每四格一个铆钉点。

### 10.3 弹道与命中反馈

**服务端不引入真实弹丸实体**。引擎现在是「射程内按 DPS 连续扣血」
（`dps_in_range` → `e["hp"] -= total * dt`），改成飞行时间会让 DPS 依赖距离 ——
那是**平衡改动**，不是美术改动，不该混在这一轮里做。

所以服务端只多给一份**「谁在开火、打谁」**（`dynamic_snapshot.shots`），
客户端据此做**纯表现层**弹丸：零平衡改动，且炮台没开火时一个元素都不画。

表现三件套的时长取自 VFX 惯例 [74][75]：

| 元素 | 时长 | 说明 |
|---|---|---|
| 枪口焰 | 90ms | 星形闪光，只在开火那一瞬。惯例是 60-100ms（「长到能看见，短到来不及看清」） |
| 弹丸 | 150ms 飞行 | 能量弹 + 拖尾；拖尾是「运动方向」这条信息通道 |
| 命中冲击环 | 220ms | 到达时在目标处扩散一圈 —— **它同时是「这一发打中了」的确认** |
| 伤害数字 | 每 500ms 一次 | 静默体头上弹累计伤害，上限 6 个（超了刷屏，是反效果） |

**刻意不做屏幕震动**：本屏是「俯视地图 + 点格子建造/升级」，而震屏会**与精确点击
冲突**（手指按下去时画面在抖 → 点歪格子）。塔防的打击感来源是「火力覆盖的观感」，
不是「镜头被打到」。改为**被砸的门本体抖动 + 视口边缘警示脉冲**（局部反馈，
不动整个视口）。这条写在这里，免得下次又有人想加。

### 10.4 攻击范围指示器

惯例很清楚（一份 UE4 塔防 demo 的开发笔记 [76]）：**鼠标移到炮塔上显示攻击范围，
移开后消失；单击炮塔弹出管理菜单**。触屏没有 hover，所以本作合成一步：
**点炮台 = 同时画出范围圈 + 打开升级面板**，关掉面板圈就消失。

- 范围圈画在**地板之上、建筑之下**，半透明填充 + **虚线**描边（线型是第二通道，
  不与实线的门/建筑混）。
- 射程取自服务端同一张表（`turret_range(level)` = 4 格起每级 +0.5，上限 6），
  客户端不另算 —— 与服务端「逐塔按自己的等级判距离」是同一个数。
- **只画自己的炮台**：队友的炮台是信息、不是决策，全画出来会糊成一片。

### 10.5 交互手感

| 项 | 现状 | 改法 | 依据 |
|---|---|---|---|
| **摇杆死区** | 无死区（`onPanResponderMove` 里 `hypot(dx,dy)` 直接归一化，抖动也当输入） | **径向死区 0.12** | [77]：死区要用**径向缩放**，不能按轴裁剪（按轴会让斜向出现方形死区、且过死区时速度突跳） |
| **摇杆响应曲线** | 线性 | 死区外用 `t^1.25` 轻微指数 | 保留小幅精细控制，同时边缘仍给满速 |
| **摇杆按下态** | 底座无变化 | 按下时底座提亮 + 内圈出现 | 触摸没有 hover，**按下必须有确认**（否则「摇杆没反应」的错觉） |
| **相机跟随** | 硬跟随（每帧直接写玩家位置） | **阻尼跟随**（lerp 0.12/帧）+ 沿移动方向轻微前视 | 硬跟随会把服务端 tick 的校正抖动**原样传进画面** |
| **可点格子/按钮** | 只有 `activeOpacity` | 加按下缩放 0.96 | 「有反馈」比「反馈好看」重要 [67] |
| **门被砸** | 只有血条在掉 | 门本体抖动 + 视口边缘脉冲 | 血条是**结果**，抖动是**事件**；结果每帧都在变，事件才抓得住眼睛 |
| **建造面板** | 打开后目标格无标记 | 打开时高亮目标格 | 面板盖住了半个屏幕，玩家会忘了自己点的是哪一格 |

### 10.5.1 落地时踩到的一条：摇杆曲线会把 E2E 的比例控制器拖慢

`e2e_stasis_smoke.py` 里那个 `walk_to` 是**比例控制器**：每轮按屏幕坐标差推一次摇杆，
推的幅度写死 40px。加了死区 0.12 与曲线 `t^1.25` 之后，40px（= 77% 量程）只给到
**69% 速度** —— 于是每一轮都走得比预期慢三成，最终在「走进舱室却走不到床边」这一步
超时（实测就是这么红的）。

**修法是改测试、不是改曲线**：真人要跑起来就是把杆推到底，所以推的幅度改成 52px
（= `STICK_R`，满量程 → 满速）。这条记下来是因为**它还会再发生**：任何按固定像素
推摇杆的脚本都隐含了「推多少 = 多快」这个假设，而这个假设在手感改动之后就不成立了。

### 10.5.2 「躺下」的判据：**试了五版，最后一版把判定权整个交出去**

同一步还暴露出第二个问题（**产品缺陷，不是测试问题**），而它试了五版才对。
五版都记在这里，因为每一版都是「看起来对、其实错」：

| 尝试 | 判据 | 结果 |
|---|---|---|
| 1（原实现） | 服务端 `my.pos` 落在床格或它的四邻 | 位置每 tick 才到、还只在 2.5 Hz 那条慢变量路径上 —— **玩家已经站到床边了，按钮要等最多 0.4 秒** |
| 2 | 只看客户端**预演**位置（主循环 33ms 算一次） | 延迟没了，但预演与服务端稳态差约 **0.14 格**（实测），跨格子边界时「按钮在、点下去被服务端拒」—— **UI 在骗玩家** |
| 3 | **预演 ∩ 服务端**都对 | 不骗人了，但**规则本身太窄**（5 格）：那 0.14 格的差跨一次边界就够把服务端甩出这 5 格，于是「屏幕上明明站在床上、按钮就是不出现」。E2E 实测约 **1/3 概率**红在这一步，而玩家遇到时**没有任何办法自查** |
| 4 | **人在自己舱室里**（42 格对 5 格），两端同一个谓词 | 那 0.14 格**不可能**跨出去，于是「按钮在 ⟺ 服务端一定接受」重新成立。**但这是把边界推远，不是解决问题** —— 客户端仍然持有一份服务端判据的副本 |
| **5（最终，v6 发布）** | 判据收回**休眠舱的九宫格**（用户要求），**判定权整个交给服务端**：`stasis_tick` 每个玩家多带一个 `lie` 布尔值，客户端按钮的显隐直接读它 | 两边**不可能**再各说各话 —— 没有第二份实现就没有漂移。代价是按钮最多晚一个 tick（200ms）出现，而玩家这时正在**站定**准备点它，落在「1 秒」那一档里 |

**两条教训**（第二版才是关键的那条）：

1. **先量抖动，再定阈值。** 客户端预演与服务端位置之间有 0.14 格的稳态差
   （跨格子边界能放大成一整格），而原来那条规则只给了 5 格 —— 余量比抖动大不了
   多少，于是它必然间歇性地判错。阈值贴着抖动定，就是在给自己埋一个 1/3 概率的
   flake。**判据的余量必须大于系统的固有抖动。**
2. **修不掉的时候，先把「谁说了算」定下来。** v4 放宽到 42 格之所以看起来好了，
   只是因为 0.14 格相对 42 格可以忽略 —— 规则本身还是「客户端猜服务端会怎么判」。
   v5 不再猜：判据由服务端算、随 tick 下发。这与项目里象棋 `legal`、UNO
   `playable`、飞行棋 `path`、俄罗斯方块 `shapes` 是同一条约定 ——
   **客户端一格规则都不重写**。这条路走过一次弯路（v4）值得记下来：
   当两边都要算同一个判断时，**先问「能不能只让一边算」**，再谈阈值。

### 10.5.3 脚本走位的判据必须是**按钮**，不能是坐标

这条是上面那个缺陷在测试侧的另一面，也记下来：`walk_to` 是个比例控制器，
它收敛的是**屏幕上那个盒子的中心** —— 而 `stasis-hero-me` 那个盒子只装得下昵称
文字（实测 14×19.5px），盒心离脚底有十几像素。所以「脚本认为到了」和「按钮出现」
是两回事。**走位脚本的终止条件应该是「目标按钮出现了」**，不是坐标落在容差里。

v6 把判据收回九宫格之后这条**又变得要紧了**：`walk_to` 收敛的是屏幕上盒子的
中心，而按钮的显隐由服务端判据决定 —— 两者不是一回事。所以脚本里分成了两个函数：
`walk_to` 只用于「走到门口」这类中间目标，**终点一律用 `walk_until_lie`**
（循环里每轮先查按钮在不在，不在才推一次摇杆）。写成「走到坐标就算到」的版本
在 v3 那次实测里就是 1/3 概率红的那一步。

### 10.5.4 相机拖动偶发「拖 14 步只动 3px」

相机拖动那一步实测偶发失败，位移只有 **3px** —— 那 3px 是**相机阻尼的余量**，
说明 responder 压根没授给地图（手势被别的东西吃了），而不是「拖得少」。
两条修法：

1. **只认 `elementFromPoint` 落在 `stasis-map` 上的起点**。原来也接受 `none`
   （那说明底下是个没有 testID 祖先的元素、手势链落在谁身上说不清）。
2. **拖一次没接上就再拖一次** —— 拖动是幂等的，重试不改语义；**但不放松阈值**，
   因为个位数 px 不是「拖得少」而是「没接上」，放松阈值等于把这条断言废掉。

### 10.6 采纳 / 不采纳

**✅ 采纳（全部已落地）**：四矿独立条目（§10.1）、整格矢量贴图 + 剪影优先（§10.2）、
格线纹理而非填充、表现层弹丸三件套（§10.3）、点炮台显示范围圈（§10.4）、
摇杆径向死区 + 响应曲线 + 按下态、相机阻尼跟随、门被砸抖动、按压缩放、建造目标格高亮。

落地的具体位置：贴图与特效在 **`app/src/stasisArt.tsx`**（一格一张
`viewBox="0 0 44 44"` 的 sprite + 枪口焰/弹丸/冲击环三个特效件），弹丸的驱动在
**`app/src/StasisShots.tsx`**（对象池 + 自定开火节奏），范围圈与手感改动在
`StasisScreen.tsx`。**弹道层单独一个文件**是因为主组件已经两千多行，而特效层是
纯展示、无状态、无回调 —— 抽出来既能瘦身，也让「开火看起来怎么样」有一个能整体
替换的地方。

### 10.7 StasisScreen 的拆分（v6）

主组件一度是 **2709 行** —— 项目里最大的文件，比第二名（`BattleshipScreen` 1421 行）
还多出将近一倍。拆的**判据不是行数，而是「谁需要知道什么」**：

| 文件 | 行数 | 管什么 | 凭什么能拆出去 |
|---|---|---|---|
| `app/src/stasisRules.ts` | 272 | 费用表 / 产率表 / 门槛表 / 射程公式 / 预演碰撞 | 与 React 无关，只是「数值 + 纯函数」 |
| `app/src/StasisBoard.tsx` | 674 | 地图渲染：静态层 + 门 / 建筑 / 休眠舱 / 空格 / 范围圈 / 角色 + 摇杆 | 本来就是 `memo` 过的模块级组件，props 全是显式的 |

三条做法值得记下来：

1. **拆出来的第一件事是删死代码。** 搬 `BedView` 时发现它**从来没被渲染过**
   （`BedLayer` 直接画 `PodSprite`），连带 `spriteCell` 样式一起是死的。大文件里
   这种东西不会被看见 —— 只有把它按职责摊开时才浮出来。
2. **面板不要塞进一个 `StasisPanels(props)`。** 一开始是那么写的，props 会有
   二十几个 —— 一个组件接口宽到这个程度，读的人得先把整份 props 表背下来才知道
   它画什么，拆分就变成了搬家。最后是**七个独立小组件，每个 4~9 个 props**。
3. **同一样式长在三处时必须抽成组件，不能抽成常量。** `primaryBtn` / `ghostBtn`
   同时被底部 sheet、全站浮层、结算弹窗用 —— 抽成样式常量只是把重复挪了个地方，
   抽成 `PrimaryButton` / `GhostButton` 才是收口。顺带把「买不起时不禁用按钮」
   这条规矩写进了组件注释（RNW 下 `disabled` = `pointer-events:none`）。

**❌ 不采纳**（含本轮新否掉的）：

| 不采纳 | 理由 |
|---|---|
| **生图 skill / 位图贴图** | 见 §10.2：视觉语言、缩放、多密度、配色单一来源四条都不划算 |
| **真实弹丸实体（服务端）** | 会把「美术改动」变成「平衡改动」，DPS 将依赖距离。见 §10.3 |
| **屏幕震动** | 与点格子建造的精确操作冲突。见 §10.3 |
| **像素画风** | 调研里素材包最多的是像素画 [71][72][73]，但与本作「深空站」基调不符，且像素画在非整数缩放下会有采样毛刺 |
| **矿的升级链**（保留原作那种） | 与「直接放置」并存时恒为劣选，是死 UI。见 §10.1 |
| **悬浮摇杆 / 全屏任意位置起手** | 会与「拖动地图平移」抢手势（本屏已经为此踩过 `onMoveShouldSetPanResponderCapture` 的坑），固定摇杆的代价小于抢手势的代价 |
| **炮塔的炮管跟着目标转** | 看着更帅，但朝向每 tick 都在变，就得把整层贴图（可能几十座塔）从 `memo` 里踢出去、每 tick 重建。方向改由枪口焰与弹丸表达（它们本来就指向目标），炮塔本身画成**对称的环形发射器** —— 没有炮管就没有「指错方向」这回事 |
| **贴图里写等级数字** | 数字改由屏幕层的小徽标画：能跟主题走、能被视觉审计看见，也不必给 13 个等级各画一张图 |

## 11. 第六轮补充（2026-10-13，用户实测报的数值问题）

用户这一轮报了五件事，都是「玩起来不对劲」：

> 数值感觉不太对劲，你再调研一下，感觉**门的血比猛鬼宿舍多**（或者**鬼的攻击力比
> 猛鬼宿舍少**）、**炮塔的攻击力偏低**（或者**鬼的血量偏高**）；另外价格方面：
> **银矿应该是 512、金矿 1024、钻石矿 2048**，**升级门的价格应该是每次 \*2，
> 但是我实际游戏时发现玩着玩着就不是 2 的倍数了**，而且**到一定等级后门、炮台、
> 床铺升级都要合金资源**，具体你再进一步调研一下

外加一条换皮要求：**界面上不许再出现原版的名称**（见 §11.7）。

### 11.1 门的升级价是纯 ×2 链（**用户报的是对的，我们那张表错了**）

用户说的「玩着玩着就不是 2 的倍数了」指的是这一列：

```
旧：16 / 32 / 65 / 128 / 216 / 432 / 864 / 1728 …
                    ↑×2.03   ↑×1.69 ← 这里断了
```

`216` 那一跳只有 ×1.69。§9.2 当时把它标成「中可信度，两条来源都写钢1门 216」，
本轮找到了**两条直接写 128 → 256 的来源**：

| 来源 | 原话 |
|---|---|
| [80] 新浪财经·猛鬼宿舍通关攻略 | 「先建 **128 金币门**，随后升级六座水枪炮台…最后开启 **256 金币门**」 |
| [81] 游戏观察·新手快速上分技巧 2026 | 「门升 3、4、5（128 金币）」「累计生产 **128 加 256 金币**用于门的升级」 |
| [82] TapTap·验算党长文 | 「全程秒升的情况下能一直够到 **16384 的门**和 512 床的闪电需求」 |

16384 落在 `16 × 2^n` 这条链上（16→…→16384 是第 11 跳），128→216 那条链到不了它。
**结论：`216` 是错的，整列改成 `16 × 2^n`**；`65` 一并归一成 `64` —— 它是 32 的
取整写法（×2.03），而用户要的规则就是「每次 ×2」，留着一个 65 等于把这条规则又
开了一道口子。

> **代价（如实记）**：§9.2 那句「`65` 是原型的真实取整方式，照抄不修正」被推翻了。
> 留在这里是为了下次不要又把它「修回去」。

### 11.2 第 6 级起升级要「金币 + 闪电」（用户报的也对）

四条来源指向同一条规则：

| 来源 | 原话 | 说明 |
|---|---|---|
| [83] 新猛鬼宿舍（电视猫） | 「购买游戏机：**在玩家到一定等级的时候，就需要金币加电力升级**」 | 规则本身 |
| [84] TapTap·雪雪爱游戏 | 「**在升钢门时务必要有四个游戏机，电量不够**」 | **分界线 = 进钢门**（第 6 级） |
| [82] TapTap·验算党长文 | 「一直够到 16384 的门和 **512 床的闪电需求**」 | 床也要闪电 |
| [85] 一加社区·猛鬼宿舍 | 「游戏中共两种资源，金币以及闪电，**后期强力建筑是需要闪电才可以建造**」 | 双资源的定位 |

**比例取 1/32**：[86] 腾讯频道里那两扇门「**13 万金币 4 千闪电**」「**26 万金币
8 千闪电**」—— 131072/4096 与 262144/8192 **比值恒为 32**，而且两个数都是 2 的幂，
明显是同一张表里的两行。

采纳：`ALLOY_FROM_LEVEL = 6`、`ALLOY_RATIO = 32`，**门 / 床 / 炮台三样统一取第 6 级
这条线**（原型的休眠舱与炮台没有「铁门/钢门」这种分段，只有门有明确的分界）。

> **连带的硬要求**：人机必须造精炼机。第 6 级往上的每一次升级都要合金，而人机
> 原来的策略里**一条合金线都没有** —— 它会卡在「升门」这个被 `_spend_upgrade`
> 以「合金不够」拒掉的动作上，而 `_stasis_bot_think` 是**静默吞 `ValueError`** 的，
> 「一次决策一个动作」下这就是死循环（同 `_bed_gate_ok` 那条教训）。
> 现在每一条「够不够钱」的判据都走 `_can_upgrade()`，两个资源一起看。

### 11.3 四座矿的价格：**用户口径与来源冲突，按用户口径改了**

用户说「银矿应该是 512、金矿 1024、钻石矿 2048」。但 §9.1/§10.1 引的四条来源
（[64][65][66] 与逗游/多特/一加社区）**一致**写 128 / 1024 / 2048 / 4096，
本轮又搜了一遍（含 2026 年的时间过滤），仍然是这四个数 —— 没有找到支持
512/1024/2048 的来源。

**采纳用户口径**，理由是**本作的局时**：原型一局十几分钟，本作只有 6 分钟，合金
产量差一个量级。旧值下钻石矿要 4096 合金，实测**根本够不着** —— 等于建造菜单上
挂着一个永远点不了的条目（§9.5 其实已经写过「保留只为对齐，不指望它进对局」，
那就是个信号）。改成 128 / 512 / 1024 / 2048 之后四个矿都进得了对局。

> ⚠️ **不要为了「四个矿凑成一条 ×2 链」把铜矿改成 256。**
> 本轮一度把这个当成一个待定项记在这里（理由是 128 → 512 是 ×4、不够「干净」），
> **已经撤回**：又搜了一遍，所有来源一致写的是**铜矿 128**，**没有一条写 256**。
> 那个 256 是「让四个数成等比数列」推出来的，不是原型事实 —— 而用户那句
> 「每次 ×2」说的是**门**（见 §11.1），不是矿。把矿也按 ×2 去凑，等于把一条
> 用户没提过的规则安到矿上，还顺带把前期唯一够得着的矿翻了一倍。
> **四个矿就是 `128 / 512 / 1024 / 2048`，不是等比数列，也不需要是。**

### 11.4 门的血 vs 鬼的攻击：**比值才是问题，而「两边都 ×2」量下来不可行**

#### 诊断

旧表里三条曲线各走各的：

| | 每级增长 | 13 / 10 级时的绝对值 |
|---|---|---|
| `DOOR_HP`（13 级） | **×2** | 1,536,000 血 |
| `ENTITY_DPS`（10 级） | ×1.29 | 60 DPS |
| `ENTITY_HP`（10 级） | ×1.18 | 27,000 |
| `TURRET_DPS`（13 级） | **×2** | 16,384 DPS |

于是两个症状正好是用户报的那两条：

- **「门的血比原作多」**：13 级门 1,536,000 血对上 10 级鬼的 60 DPS —— 一扇门要砸
  **7 小时**。门血每级翻倍而鬼的伤害每级只涨 1.3 倍，**越到后期门越无敌**。
- **「炮塔的攻击力偏低 / 鬼的血量偏高」**：4 座 1 级炮台（16 DPS）打 1 级鬼
  （6000 血）要 **6 分钟** —— 炮台在手感上等于没有。

#### 原型的锚点

| 锚点 | 来源 | 推出什么 |
|---|---|---|
| 「**门比鬼高两级，可以直接无视鬼；高一级就需要输出凑**」 | [87] TapTap 攻略合集 | 门血与鬼伤害的曲线必须**同步**，这条判据才与等级无关（门高两级 ⇒ 门血是 4 倍） |
| 「**一级鬼 2 个扫把炮台就可**」 | [88] TapTap 玩家实测 | 鬼的血量要小到 2~4 座 1 级炮能把它打退 |
| 「12 级的鬼攻击满级门…**基本上和 3 个维修台的回血持平**」 | [89] TapTap·养 13 级鬼攻略 | 鬼的 DPS ≈ 门血上限的 **6%/秒**（3 × 2%） |

#### 试过、**量下来不可行**的那一版

最贴近原型的是「**门与鬼都每级 ×2**」（这样「门高两级」这条判据在每一级都成立）。
**不可行**，而且不是拍脑袋说的 —— 扫了
`D∈{250,375} × G∈{6,8,10,12,16,18,24} × r∈{1.5,1.8,2.0} × H∈{300,400,500,600,900,1200} × evo∈{45,60,90,120}`
（`test/balance_stasis.py` 的同一套打法，2/4/6 人档）：

> **`r = 2` 的每一组，2/4/6 人档全部全灭。**

根因不在比例，在**进化节奏**：本作的静默体每 **45 秒**进化一次（`EVOLVE_MS`），
6 分钟一局**白送 8 级**，×2 就是 **×256** 的伤害；而玩家的经济是指数爬坡、开局只有
1~2 生物能/秒 —— 追不上。原型里鬼的等级是**跟着玩家进度**走的（砸门才升级），
本作是计时为主。

#### 采纳的值

| 常量 | 旧 | 新 | 判据 |
|---|---|---|---|
| `ENTITY_DPS` 基数 / 增长 | 6 / ×1.29 | **10 / ×1.5** | 同级门与鬼的对峙 62.5 秒 → **37.5 秒** |
| `ENTITY_HP` 基数 / 增长 | 6000 / ×1.18 | **600 / ×1.5** | 4 座 1 级炮打退 1 级鬼：约 6 分钟 → **约 28 秒** |
| `DOOR_HP` | 375 × 2^n | **不动** | 见下 |

`DOOR_HP` **一个字没改**是有理由的：门的威胁度只取决于 `DOOR_HP / ENTITY_DPS`
这个**比值**（修补与修复器都是按上限的百分比回血，与绝对值无关），所以「门别那么
肉」要改的是分母。用户给的两条路（「门的血多**或者**鬼的伤害少」）本来就是同一件事。

**顺带把「反杀」救回来了。** v2 起 `REASON_KILLED` 实际不可达（设计 §1.5.1 的已知
缺陷：撤退窗口太窄）。鬼的血量砍到 1/10 之后这条提前胜利重新可达 —— 见 §11.5 的表。

### 11.5 纳米修复器每间最多 4 台（本轮补的）

来源：「**维修台每局只能建四个**」（[64] 等）。不加这条，「门的血比原作多」修不掉：
修复是按门血**上限的百分比**回的，而一间舱室有 20 格、能摆十几台 —— 十几台
= 每秒回 20%+ 上限，鬼的伤害再怎么调都追不上。上限 4 台 = 最高 **8%/秒**，正好是
[89] 那条「12 级鬼 ≈ 3 个维修台的回血」的比例分母。

### 11.6 平衡表（v7，16 局/档，2026-10-13）

跑法：`cd server && python test/balance_stasis.py --games 16`。

| 打法 | 2 人 | 4 人 | 6 人 |
|---|---|---|---|
| 只会造炮台（不升床不升门） | 全灭 12 / **击杀 4** | 全灭×16 | 全灭×16 |
| 龟缩守门（门床拉满，炮台够用） | 全灭 12 / 击杀 4 | 全灭×16 | 救援 7 / 全灭 9 |
| **均衡发展**（= 人机队友的打法） | **救援 13** / 击杀 2 / 全灭 1 | **救援 13** / 全灭 3 | **救援 16** |
| 经济+输出（床拉满后全力堆炮台） | 救援 2 / **击杀 8** / 全灭 6 | 全灭 15 / 救援 1 | 全灭×16 |
| 矿工（2 塔 + 1 精炼机，合金全砸矿） | 全灭×16 | 全灭×16 | 全灭×16 |

读法与 v4 那张一样：**不做事必输、只会堆炮台也基本输、均衡发展守得住就能活**。

1. **「反杀」回来了**（2 人档两行里的击杀数）。这是 §11.4 砍鬼血量的直接结果，

## 12. 第七轮补充（2026-10-13，用户实测报的三条）

用户原话：

> 1. 鬼残血没有退回到气闸门，而是在走廊上某个位置就回血了，应该退回到地图边缘的气闸门才能回血；
> 2. 帧率太低，移动的手感不好；
> 3. 修改玩法，获胜条件中的救援抵达删掉，唯一获胜条件是击杀鬼

第 1、3 条是规则改动，按项目规矩先搜一轮再动手；第 2 条是工程问题，
在 §12.4 里用实测数据说话（没有可调研的「方案」，只有测量）。

### 12.1 第 3 条：**这是有意偏离原型的一处，必须写清楚**

**原型的胜利条件是「撑到天亮」**，不是「打死鬼」：

> 「猛鬼会随时间不断升级…**若房门被攻破则游戏失败，成功坚持到天亮倒计时结束即为通关**」[90]
> 「金币可用于建造炮台、加固宿舍门等防御设施，以此抵御猛鬼的入侵，**坚持到天亮即为胜利**」[91]

也就是说本作 v1~v7 的「撑到 6:00 救援舰抵达」才是对齐原型的写法，而 v8 这条
**是用户明确要求的偏离**。搜到的一条同行的批评正好解释了用户为什么想删它：

> 《祇：女神之路》「塔防部分每次只有一个固定的时间段…**只要撑到天亮，就可以迎来
> 喘息的机会**」——评测把这条列为不足，称之为「**越能吃苦就越有吃不完的苦**」[92]

「撑满时间」当胜利条件的问题在于：**最优解是苟**。玩家会退化成「什么都不做，
等倒计时走完」，整局没有任何进攻决策。v7 的实测正好印证了这一点 —— 人机队友
（`均衡发展`）在 2/4/6 人档上 **16/16 全部撑到救援**，一次都没输过；「反杀」只是
一个可有可无的彩蛋。一条玩家永远不会去做的胜利条件，等于没有这条条件。

**所以 v8 把 6 分钟从「胜利倒计时」改成「击杀期限」**：到点没打死就是失败。

> ⚠️ **同一天用户又追加了一句：「不要求 6 分钟内打死，时间不限」** —— 于是
> 「击杀期限」也删了，**一局没有时长上限**，打到打死或全灭为止。这一版才是最终形态。
>
> 它反而**更贴原型的单局时长**：原作是 10~15 分钟一局 [90]，而 6 分钟是我们为
> 「桌上对局」压短的（`增强调研.md` §9 的进度轴对照里写着）。
>
> **不用怕打不完**：静默体的等级封顶在 10 级（约 7 分半就不再变强），而玩家的经济
> 与炮台是无限爬坡的 —— 僵持的局面**天然朝玩家倾斜**，最终一定分出胜负。会真正
> 僵住的只有「一炮不造又守着满级门」这种自相矛盾的打法，那由 `STALL_CAP_MS`
> （30 分钟）兜底 —— **它不是玩法规则，是防卡死的保险丝**：这是本项目唯一的服务端
> tick，不能让一局永远跑下去。
>
> 顶部那栏随之从倒计时改成**正计时**（`已坚守 M:SS`）：没有终点可倒，压力改由
> **静默体的等级**提供。

### 12.2 第 1 条：Boss「回老家回血」——**同行踩过的坑就在「回几次」上**

原型与本作原来都是「退回气闸回血」，但**退回哪里**这件事同行有明确的教训。
《王国保卫战》三代的 Boss 玛丽西娅就是「掉 1/3 血就飞回阳台开护盾回血」，
玩家社区的改造方案里第一条批评就是：

> 「**死因：每次掉 1/3 血就非要跑**；后面的复仇者师团出的很晚」[93]

同一条改造方案给出的正解是：**撤退次数有限（前两次回血、第三次一打到底），
而且回血可以被玩家打断**（打掉护盾会缩短它回血的时间）。

本作没有「有限次数」这条（一局 6 分钟里它会来回好几趟），所以**必须给玩家一条
「在路上就能打死它」的路径**，否则就是玛丽西娅那个「非要跑」的复现。v8 的落地：

| 改动 | 为什么 |
|---|---|
| 撤退终点从「离所有有主舱门 ≥6 格的通道格」改成**恒为 `M.AIRLOCK`** | 用户实测报的。而且这样它**每次都要重新穿过整条走廊**，来回两趟都在炮台射程里 —— 玩家的正解从「抢十几秒的爆发窗口」变成「沿来路铺开火力」，可读性好得多 |
| **再生与否按位置判，不按「路走完了」判** | 老代码判的是 `path` 空，而 `path` 还可能被 `_go_idle` 之类的路径清空 —— 那时它人还在走廊中间，于是就地回血。**这正是用户报的现象的另一半** |
| 撤退速度保持 35%（不变） | 那 100 秒的往返正是「磨死它」的窗口，`RETREAT_SPEED_MULT` 的注释里量过：调到 0.5 击杀率掉一半，调到 1.0 掉到 0 |

> ⚠️ **§11.4 里「退到 6 格外即停」那条 v2 的决策在 v8 被推翻**。它当年成立是因为
> 「撑到救援」是主胜利条件、反杀只是彩蛋，把窗口从 7 秒拉到 17 秒就够；击杀成为
> 唯一目标之后，规则得反过来服务它。**推翻的理由记在这里，别再改回去。**

### 12.3 连带改动：`EVOLVE_MS` 45 秒 → 50 秒

击杀成为唯一目标之后，「玩家的输出能不能跟上它的成长曲线」就是整局的核心，
而这条曲线原来太陡：45 秒一级 = 6 分钟白送 8 级，血量与伤害各 ×25.6，而玩家的
经济是指数爬坡、前期只有 1~2 生物能/秒。**实测（48 局 × 3 档 × 4 打法）**：

| `EVOLVE_MS` | 均衡发展（= 人机）2/4/6 人 | 只会造炮台 |
|---|---|---|
| 45s（旧值） | 20% / 12% / 16% | 22% / 12% / 4% |
| **50s（现值）** | **41% / 47% / 41%** | 20% / 12% / 8% |
| 55s | 54% / 77% / 66% | 27% / 14% / 12% |
| 60s | 54% / 77% / 79% | — |

> ⚠️ 上表是**「6 分钟击杀期限」那一版**测的（见 §12.1 的追加说明：期限后来也删了）。
> 改成「时间不限」之后，「胜」的定义从「6 分钟内打死」变成「打死」，分母不再一样 ——
> 那张表只用于回答「45 秒还是 50 秒」，**不要拿它的百分比跟 §12.5 的表比**。

取 50 秒：人机（一个中等水平的玩家）落在 40~47%，而明显更差的打法只有 8~20% ——
**难度梯度是分开的**。55 秒往上 4/6 人档就到 77%，赢太容易。

**这条同时更贴原型**：原型的鬼虽然也「随时间不断升级」[90]，但攻略里反复出现的是
「砸门 / 破门」才让它变强；按秒白送 8 级是这条曲线最激进的一端，放慢是朝原型走。

### 12.3.1 「时间不限」逼出来的一个**人机真 bug**：它永远造不出精炼机

改成「时间不限」之后，模拟里冒出一批**跑满 30 分钟兜底上限都分不出胜负**的对局
（2 人档 24 局里有 3 局）。追下去发现人机的状态是这样的：

```
t=1770s 鬼Lv10 11.4%   uid1 bed=5 door=5 bio=12421 alloy=0
                       塔=[(turret,5) × 19]
```

**19 座炮台全是 5 级、合金恒为 0、生物能攒到一万二却什么都买不了。**

根因：`ALLOY_FROM_LEVEL = 6`（v7 加的）之后，第 6 级往上的任何升级都要合金，
而合金只能靠精炼机 —— 但人机的精炼机判据是「手上 ≥200 生物能才造」，**它自己
那条「铺空格」的规则又把每一分钱按 8 块一张花掉了**，于是永远攒不到 200。

这跟 v2 那条「不留储备就永远凑不齐 25 的床升级」**是同一个坑**，只是当年只给
`next_bed` 留了储备、没给精炼机留。修法也一样：**还没精炼机时，铺塔那一步要把
它的 200 一起留在账上**（`next_refinery`）。

> **为什么 v8 之前看不出来**：那时 6 分钟到点就结束，卡在 5 级的对局直接记成
> 「撑到救援」，谁也看不出它其实什么都没干。**去掉时限等于把那批「其实卡住了」
> 的对局全部暴露出来了** —— 这是这一轮最有价值的一条副产品。
>
> 修完之后那三局分别在 12.4 / 13.0 / 14.4 分钟打死了它（`reason=killed`）。

### 12.4 第 2 条：帧率 —— **30 Hz 是我们自己设的上限，不是性能上限**

用户报「帧率太低、移动的手感不好」。先量，再改。

**量到的第一件事**：主循环是 `setInterval(..., 33)`，也就是**画面更新被钉死在
30 Hz**，而显示器是 60 Hz。用 `MutationObserver` 数「角色 / 地图容器的 style 被写了
多少次」：

| | 移动中 4 秒的 style 变更 | 折算 |
|---|---|---|
| 改之前（`setInterval(33)`） | 246 | **30.8 Hz** |
| 改之后（`requestAnimationFrame`） | 468 | **58.5 Hz** |

同时 `requestAnimationFrame` 自己的帧间隔实测是 **60.0 fps、p95 16.7ms**
（跑动阶段与对局阶段都是）—— 也就是说**主线程根本不忙**，那 30 Hz 纯粹是定时器
的节拍。rAF 是白捡的一倍帧率。

**改到的四处**：

1. 主循环 `setInterval(33)` → `requestAnimationFrame`（本地预演 + 相机 + 上行节流 +
   门抖动）。附带两个好处：标签页不可见时浏览器会停掉 rAF（定时器不会，后台标签
   一直在算）；高刷屏上能跑满。
2. `StasisShots` 的开火循环 `setInterval(40)` → rAF（原来弹丸被钉在 25 Hz，一帧跳
   一大截，看着像掉帧）。开火节奏由 `FIRE_MS = 420` 单独控，与循环频率无关，
   **所以这一改不碰平衡**。
3. **相机阻尼改成与帧率无关**：`CAM_LERP = 0.14` 是按「33ms 一帧」标定的
   （≈0.2 秒到位）。换 rAF 后一帧只有 16.7ms，照抄 0.14 会让相机快一倍 ——
   手感一变，「再大就等于硬跟随了」那条调参理由就不成立了。改成
   `1 - (1 - CAM_LERP) ** (dt / 0.033)`，30/60/120 Hz 上观感一致。
4. 门抖动的相位 `now / 42` 是**按 30 Hz 调的**，换 rAF 后同样的 42 会让抖动快一倍，
   除以 2 保持原频率。

**另外给「每帧都在动」的容器加 `will-change: transform`**（`stasisRules.WEB_GPU`，
只对 Web 生效）：整张地图是 700+ 个 DOM 节点，不提升图层的话浏览器每帧要把它们
重画一遍。**只给地图 / 角色这两个加** —— 每个 `will-change` 都真占一层显存，
十几发弹丸各占一层反而更慢。

> ⚠️ **这一条没有单独量出收益**：CPU ×6 降速档下整机都慢，隔离不出来（改前
> 39.4 fps、改后 39.6 fps，p50 都是 16.7ms）。留着是因为它按机制就该有用、
> 而且没有代价 —— 但**别把它当成上面那三条那样的实测结论**。

**改完的实测**（同一台机器）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 无降速，跑动阶段 | rAF 60 fps，画面 30.8 Hz | rAF 60 fps，**画面 58.5 Hz** |
| CPU ×6 降速，移动中 | 47 fps / p95 115ms（v6 记录） | 39.4 fps / p50 16.7ms / p95 150ms |

> ⚠️ **CPU ×6 那一栏改后反而更低，是预期的**：每秒要画的帧多了一倍，单帧成本不变
> 时总开销也翻倍。**要看的不是这一个数，而是「无降速时画面从 30 Hz 变成 58.5 Hz」**
> —— 用户是在正常设备上报的「帧率太低」，那正是被定时器砍掉的那一半。
> 降速档上 p50 仍是 16.7ms（绝大多数帧是满帧），只有偶发长帧。

### 12.5 最终数值：`ENTITY_DPS` 基数 10 → 12

「时间不限」落地之后人机的胜率一度是 **100% / 96% / 100%**（2/4/6 人档）——
**没有失败面**。这正是用户最早那句「鬼的攻击力比原作少」的同一件事：守得住就赢，
而守得住太容易了。

**32 局 × 3 档扫过四个基数**（`test/balance_stasis.py`，「均衡发展」这条打法）：

| `ENTITY_DPS` 基数 | 2 人 | 4 人 | 6 人 |
|---|---|---|---|
| 10（v7 旧值） | 100% | 96% | 100% |
| **12（现值）** | **87%** | **81%** | **100%** |
| 13 | 87% | 75% | 93% |
| 14 | 65% | 71% | 81% |

取 12（+20%）。**为什么抬的是伤害而不是血量**：抬 `ENTITY_HP` 会让「打不死它」
变成新的失败模式 —— 而 6 分钟击杀期限那一版已经量过，那样只会把弱打法一起压到 0
（`hp0=800` 时「只会造炮台」和「经济+输出」双双 0/20）。抬伤害改变的是**守不守得住**，
梯度保留得住：同一次扫描里弱打法仍有 9~31%。

**最终的 24 局/档分布**（`设计.md` §1.5.1 有完整表）：

| 打法 | 2 人 | 4 人 | 6 人 |
|---|---|---|---|
| 只会造炮台 | 29% | 12% | 8% |
| 龟缩守门 | 29% | 12% | 8% |
| **均衡发展**（= 人机） | **92%** | **87%** | **100%** |
| 经济+输出 | 33% | 33% | 21% |
| 矿工 | 0% | 0% | 0% |

**「超时」一栏全是 0** —— 30 分钟的防卡死兜底一次都没触发（§12.3.1 那个 bug
修好之后，僵住的对局就没有了）。单局中位数 3~10 分钟，比 v8 之前的 6 分钟长，
但**对齐原型的 10~15 分钟**。

### 12.6 有意不做 / 留给下一轮的

| 项 | 为什么不做 |
|---|---|
| **把鬼的进化彻底改成「按砸门进度」**（原型是砸门才升级） | 仍是这条曲线最贴原型的做法，也仍是独立一轮：要连着重做 AI 的经济节奏。本轮只把计时从 45 秒放慢到 50 秒 |
| **给撤退加「次数上限」**（王国保卫战那套：前两次回血、第三次一打到底）[93] | 一局本来就不长，撤退跑不了几趟；而且「气闸是它唯一的回血点」这条已经给了玩家「在路上截杀」的路径。**如果实测发现它还是「非要跑」，这是下一个该动的旋钮** |
| **去掉 `MAX_ENTITY_LEVEL`（让它无限进化）** | 那样「拖下去」就从「稳赢」变成「必输」，等于把用户明确否掉的时限**换个说法塞回来**。保留 10 级封顶 = 玩家的经济最终一定能压过它 |
| **`StasisScreen` 继续拆** | 主循环与相机还在屏幕层（1400 行左右）。拆它要连 `Animated.Value` 的所有权一起搬，收益不如上面几条确定 |
| **把 `DoorView` 也 `memo` 掉** | tick 只以 2.5 Hz 更新慢变量，12 扇门的 SVG 重建在实测里没进瓶颈（无降速时 p95 16.7ms）。等有数据再说 |

## 13. 第八轮：多张地图 + 多套人机性格（2026-10-13，用户要求）

用户的两条原话：

> 多做几张不一样的地图，甚至可以针对多人合作专门做，比如一个大房间里面隔成两个
> 小的，外面一个门里面一个门，鬼想要打里面必须先把外面的门打破，这样这个房间里的
> 玩家就可以合作，一个人发展经济，一个人发展武器

> 还要多写几个不一样的人机逻辑，不然每个人机造的建筑都一模一样；人机不需要特别
> 聪明，有时候甚至可以故意随机操作，放弃最优解，这样玩家体验会更好

这一轮是**新游戏 / 玩法增强先联网调研**这条规矩下做的（中英文各搜一轮，8 轮搜索）。

### 13.1 「一人搞经济 / 一人搞输出」是合作塔防的通行分工，不是我们的发明

多份攻略把这件事写成了标准打法：Tower Defense X 的官方 co-op 指南直接定义四人
分工（一人农场经济、一人制空、一人前排、一人补海路），并点明「**所有人都买同一个
DPS 就会崩**」[95]；All Star Tower Defense 的困难模式攻略把「**重叠投资是致命的**」
写成铁律，最成功的队伍会把职责拆开、指定专人当农夫 [98]；中文侧《幸运塔防》的官方
攻略第 2 条就是「双人分工：一人清杂兵、一人打 Boss……**不要两人全堆输出**」[99]。

Tower Defense Simulator 的攻略里有一个很直观的反面场景：「两人开局 30 秒都放了
Farm，结果没人带早期 DPS，第 3 波漏怪，一局还没开始就结束了」[96] —— 与我们在
「小房间合作」那张图上想促成的事情是同一件：**分工做对了才打得动，一起堆同一种
东西反而会输。**

### 13.2 「双层门 / 内外门夹一条缓冲走廊」是经典结构

用户描述的「外面一个门里面一个门」在关卡设计里是被反复验证过的结构：Dwarf
Fortress 的 wiki 里有一条专门的 **Airlock defenses / buffer zone** 条目（两堵墙
各带一座吊桥、外桥常开内桥常闭）[100]；中文的基地防御攻略讲「2 层门、且两门之间
带迂回，可以把敌人堵在第一道与第二道门之间……**形成一夫当关**」[101]；韩国 CSO
的「Double Gate」僵尸地图甚至把「A 闸门 / B 闸门，任一侧失守后续极难打」写进了
开发者日记 [102]。

我们做的 `suite`（双人套间）就是这条结构的一个具体解：**一扇共用闸门 + 一条门厅 +
两扇各自的房间门**。鬼要打里面那间，必须先砸破外面那道闸门 —— 与用户描述的一致。

### 13.3 ⚠️ 共用闸门的已知风险：**搭便车**（这一节是本轮最该记住的）

调研里唯一一条**明确的负面证据**，而且正好命中我们的设计：

- **「一道门保护两个人」在游戏设计上是一份非排他、非竞争的公共品**，天然诱发
  搭便车与社会惰化。中文的游戏心理学文章用一整节讲「搭便车效应」，给的机制解释
  是**责任分散**：「合作人数越多，责任分散越厉害，越容易形成相互推诿」，并认为
  这是《守望先锋》《风暴英雄》这类强团队游戏热度下滑的根本原因之一 [105]；
  MINIFINITI 的《Common Issues with Cooperative Games》把 **Free-Riding** 与
  **Alpha Player Syndrome**（一个人独揽决策）并列为合作游戏五大常见问题 [106]。
- **博弈论的根基是「纳什均衡 = 零贡献」**：公共品上任何人的贡献都会外溢给全组，
  于是「占优策略是贡献 0」[107][108]。翻译成我们这张图就是：**外闸门升级的钱
  由一个人掏、收益两个人分，理性玩家会天然倾向等对方来升。**
- 行业常见的解法是「**提高可见性 / 强制表态 / 内置修正**」，公共物品研究里反复
  出现的另一条是「**有惩罚机制时合作才会出现**」[106][109]。

**我们的处置（写下来，免得下次重新评估）**：

1. **闸门的血条与等级对两个住户都可见**（全站浮层里它排在所有房间之前，金色行），
   这是最轻的一档可见性 —— 至少「谁没出钱」这件事在界面上是看得见的（闸门一直是
   1 级、血一直不满）。
2. **人机的性格里带 `gate_bias`**：龟缩型 1.4 / 修补匠 1.6 愿意为公共防线多掏钱，
   莽夫型 0.7 只顾自己 —— 于是「跟人机搭档时闸门会不会有人管」是随性格变的。
3. **不做**「贡献账本 / 谁出钱谁得分」这类机制：它是另一个系统（要落盘、要进协议、
   要画界面），而**这一轮的验证目标只是「这张图能不能让分工发生」**。搭便车在
   2 人档本来也是最轻的（责任分散随人数加重，而我们这张图**恰好是 2 人一组**）。

> 这一条留在「有意不做」里，**不是因为它不重要，而是因为它还没有被实测撞上**。
> 如果以后收到「两个人都等对方升外门」的反馈，第一个该动的旋钮就是可见性那一档。

### 13.4 人机性格：让 AI 故意犯错是有学术背书的正当手法

- Drexel 的论文《Artificial Stupidity: The Art of Intentional Mistakes》正是这个
  题目 [110]：它明确写「让游戏有趣 ≠ 让对手更聪明」，「玩家本来就该赢」，但
  「因为 AI 做得烂而赢也是不可接受的」—— **乐趣最大化的方式是让 AI 的失误
  「有意为之但看起来合理」**。这几乎就是用户那句「有时候甚至可以故意随机操作，
  放弃最优解，这样玩家体验会更好」的学术版。
- 工程上「便宜又明显」的做法有成套清单：**按权重概率选而不是永远选最优、给效用
  分数加噪声、加入犹豫与延迟、区分风险偏好（保守型 vs 鲁莽型）、错误要贴合情境
  而不是纯掷骰子** [111]。我们照抄了前两条 —— `Profile` 的 `noise` 就是「按比例
  放弃最优解」，而 `_random_action` 只在**合法动作**里掷骰子（这一条是踩过坑补的，
  见 §13.5）。
- **工业界给多个 bot 做性格的通行做法是「全局一棵行为树 + 每个 profile 一套参数」**
  ，而不是每个 AI 单独写一棵树 [112]。我们的 `Profile`（frozen dataclass）+ 同一份
  `decide()` 就是这条：**差异全在十六个旋钮上，决策流程只有一份**。
- 「AI 太强 / 所有 AI 行为雷同都会毁体验」也有正式的名字：**Game AI 的恐怖谷**
  ——「太蠢破坏沉浸、太聪明直接毁掉乐趣，**刚好的 AI = 可信但仍可被击败**」[113]。

### 13.5 诚实的边界：哪几条**没有**找到来源

| 设想 | 支持度 |
|---|---|
| 双人塔防「经济发展 / 火力输出」分工 | ✅ 行业标准范式 [95][96][98][99] |
| 双层门 / 内外门 / 缓冲走廊 | ✅ 经典验证设计 [100][101][102] |
| AI 性格用「权重扰动 + 风险偏好」实现 | ✅ 有成套模式清单 [111] |
| 「AI 不必最优、要会犯错」 | ✅ 有论文背书 [110] |
| **一张地图专为「双人、一经济一火力」设计** | ⚠️ **没搜到直接先例**（多数是 2~4 人通用分工）—— 这是本作自己的取舍 |
| **「同一局内多名 AI 队友性格互异」作为设计目标** | ⚠️ **没有专门资料**（找到的都是「一个 profile 对应一个难度/一种对手」）—— 合理的自然推论，但缺直接来源 |
| **塔防里「共享那道门」的搭便车缓解方案** | ❌ **查不到**（只有通用的公共品/合作游戏讨论）—— 这部分只能自行设计，见 §13.3 |

### 13.6 本轮实际落地的东西（与上面每条对应）

- **地图注册表**：`stasis_map.py` 从「一张写死的图」重写成「声明式 `MapSpec` →
  编译成只读 `Map`」，三张图 `dorm`（默认，逐格与之前**完全相同**）/ `suite` /
  `atrium`。客户端**不再镜像几何**（见协议 §「地图几何」）—— 这是「多张地图」能
  做起来的前提：否则每加一张图，客户端那份几何实现都要跟着改一遍。
- **共用闸门**：字段与房间门**完全同构**（`door_level` / `door_hp` /
  `emp_until_ms`），所以砸门、修补、升级、EMP、快照五段逻辑**一行都不用分叉**，
  只有「砸破之后干什么」不同 —— 房间门破了会把舱室清空重置，闸门破了只是把门厅
  交出去（它**不淘汰任何人**）。
- **动态可达图**：门厅那些格子是通道类型，但**闸门没破时不在静默体的寻路图上**
  （`ghost_graph(open_gates)`）。这比「让鬼走进舱室」干净得多：它「只走通道」这条
  不变量活了下来，而「闸门是必经之路」也成立了。
- **人机性格**：六个 `Profile`（均衡/龟缩/莽夫/矿工/修补匠/随性），开局**按人数
  发互不相同的性格**（用户报的正是「每个人机造的建筑都一模一样」）。界面在全站
  浮层的人机名字后面标一个性格标签 —— 否则玩家只会觉得「这人机怎么乱造」。
- **故意的次优**：`noise` 按比例直接跳到 `_random_action`，而它**只在合法动作里
  掷骰子** —— 第一版给满血的门也发修补，被引擎一句「这扇门是满血的」拒掉，
  而 `_stasis_bot_think` 是静默吞 `ValueError` 的，「一次决策一个动作」下就是
  白扔一整轮决策（同 v2 那条死循环的教训）。**次优也必须选合法的那种。**

## 14. 第九轮：鬼的两条规则 + 矿与精炼机的数值（2026-10-13，用户实测）

用户的两条原话：

> 鬼即使在恢复过程中也要允许被打（不能无敌），而且不能一到血量阈值就跑，不然容易
> 出现没血了打一下就跑，回血后又过来又打一下就跑，永远打不死，可以设置至少打门的
> 百分之多少血量再跑

> 数值也要改一下，钻石矿改成 4096 合金，每秒生成 256 金币，并且钻石卡可以花费
> 4096 升级为氪金矿，秒产金币再翻倍，铜矿 128 合金产出 8 金币/s，银矿 512 合金
> 产出 32 金币/s，金矿 1024 合金产出 64 金币/s，游戏机最高等级增加，1 级 0.5 合金/s，
> 2 级 2 合金/s，3~6 级每级递增 2 合金/s（升级价格每次翻倍），7~10 级每级递增
> 5 合金/s（升级价格仍然是每次翻倍）所以 6 级生成 10 合金/s，满级 10 级生成 30 合金/s

> 本作术语：用户的「金币」＝本作的**生物能**，「合金」两边一致。
> 矿**产**生物能、**花**合金；精炼机产合金、花生物能。

### 14.1 「打一下就跑」：**上一轮自己写下的下一个旋钮，用户实测撞上了**

第六轮（§12.6）把「给撤退加次数上限（王国保卫战那套：前两次回血、第三次一打到底）」
列进了「有意不做 / 留给下一轮的」，并写了一句「**如果实测发现它还是「非要跑」，
这是下一个该动的旋钮**」[93]。这一轮用户报的正是它。

用户给的抓手比「次数上限」更直接：**「至少打门的百分之多少血量再跑」**。于是
`RETREAT_COMMIT = 0.25`：血掉到 25% 以下**只是准入条件之一**，还必须满足

```
本次出击对当前那扇门造成的伤害 ≥ 门血上限 × 0.25
```

- **承诺只对 `attack` 态生效**：追人 / 游荡 / 走在半路都放行。那几种状态下它没在
  跟任何一扇门较劲，把它按在原地等于让它站着挨打死 —— 走廊本来就是危险区，
  那是另一回事。
- **换目标就清零**（`trip_damage`）：`attack_accum`（进化用的累计伤害）是跨门的，
  这一个必须是「这一次盯上这扇门之后砸了多少」，所以两个字段分开记。

**为什么血线单独不够**（这一条值得记住）： retreated-to-40% 的回血 + 25% 的撤退线
意味着**一个来回净赚 15% 的血**。只要它每次出击造成的伤害少于「玩家在它往返路上
能打掉的血」，它就能无限循环下去 —— 而这正是用户看到的现象。血线管的是「什么时候
想跑」，承诺管的是「跑之前必须先付出多少」——**两个都要有，缺一个循环就闭不上**。

### 14.2 「再生期间无敌」是一条**凭空的无敌**，删它时带出来一个真 bug

旧代码在结算炮台伤害那一段写着 `if e["state"] != "regenerate"`，理由写在注释里：
「只有再生时它在气闸外打不到」。**这个理由站不住** —— 气闸就在地图边缘的**通道**上
（`dorm` 是 `(7,0)`，A1 的门就在它下面两格），射程够得着的塔本来就能打它。于是那条
守卫变成了一条没有任何机制依据的无敌：玩家看着它当着面回血、一发都打不进去。

删掉之后**立刻带出一个只有跑测试才看得见的 bug**：撤退判断因此**开始能在
`regenerate` 态下跑到**，而 `_may_retreat` 在非 `attack` 态一律放行 ——

```
tick N   : 走到气闸 → regenerate（target_door 清空、trip_damage 清零）
tick N   : 同一 tick 的 _combat ③ → 血还在线下 + 非 attack 态 → 放行 → retreat
tick N+1 : retreat 分支发现人在气闸 → regenerate
tick N+1 : _combat ③ → 又 retreat …
```

结果：**回血与撤退每 tick 互翻，撤退事件刷屏（实测 12 秒 7 次），血永远回不上去。**
修法是把 `regenerate` 一起排掉。**「再生时无敌」这条守卫当年顺手掩盖了它** ——
同一段代码里两条规则互相遮挡，是这一轮最值得记的一笔。

### 14.3 四座矿：与原作口径的差异（**用户拍板，且这个方向上一轮已经定过一次**）

本轮把这四个数拿去联网核了一遍（8 条来源文字完全一致 + 1 条玩家实测评论佐证）：

| 矿 | 原作（来源） | 本作 v10（用户口径） | 差 |
|---|---|---|---|
| 铜矿 | 128 闪电 → 8 金币/秒 | 128 合金 → 8 生物能/秒 | ✅ 一致 |
| 银矿 | **1024** → 32 | **512** → 32 | 产出同、价只有一半 |
| 金矿 | **2048** → **128** | **1024** → **64** | 价一半、产出也一半 |
| 钻石矿 | **4096** → **512** | **4096** → **256** | 价一致、产出一半 |
| 氪金矿 | **查不到** | 再花 4096 合金 → 512 | 用户口径 |

- **「氪金矿」这个名字在原作攻略里查不到**（搜了两轮零结果）。用户明确要求用它，
  所以按用户口径实现；但它**很可能来自魔改版/私服的命名**（4096 那个数字与钻石矿的
  放置价重合）。这一条写在这里，是因为它是界面上唯一一个**没有来源的本作名称**。
- **产率被有意压平了**：原作那条曲线是纯 ×4（8→32→128→512），本作取 8/32/64/256
  —— 金矿与钻石矿各砍一半，再靠**多一层升级**（氪金矿）把 512 接回来。
  净效果是**对矿的一次削弱**：旧口径 2048 合金就能买 512/秒，新口径要 **8192**
  （4096 建 + 4096 升）才拿到同样的 512/秒。
- **这是用户有意为之，理由写在数值上**：合金同时是第 6 级之后**每一次升级的硬门槛**
  （`upgrade_alloy`），「用合金换生物能产能」这条晚期循环太便宜的话，双资源的取舍
  就被抹平了 —— 谁会缺合金呢。压平矿的性价比就是把那条循环重新变成一道选择题。
- ⚠️ **代价是「矿工」这条打法彻底废了**：五行表里 **0/24 全灭**，而且是三种人数档
  全灭。它 v5 被专门加进模拟台时是能赢的（8/32/128/512 那套数）。**这是这组数的
  直接后果，不是 bug** —— 如果以后想救它，该动的是矿的产率或合金需求，不是这条打法。

### 14.5 `RETREAT_COMMIT` 带出来的新耦合：**升门 = 买炮台的输出时间**

这是本轮最需要记住的一条设计效应，**它不是 bug，但必须知道**：

> 它必须站桩挨够「门血上限的 25% ÷ 自己的 DPS」这么长时间才准撤。而**门血每级 ×2、
> 它的伤害每级只 ×1.5** —— 所以**门越高级，窗口越长**。

于是「升气密门」这件事从纯防守变成了**攻防一体**：门不只是盾，它直接买到了炮台的
输出时间。这解释了新表里最反直觉的一格 —— **「经济+输出」从 33%/33%/21% 跳到
62%/50%/54%**：那条打法的路线（床拉满 → 被门槛逼着把门顶到 5/8/13 级）**顺带把门
堆得很高**，而高门在新规则下等于长窗口。

**没有为了抹平它去调 `ENTITY_DPS`**，理由是量过了：见 §14.6。

### 14.6 `ENTITY_DPS` 最终**没动**（12），以及为什么

本轮改动让难度整体降了一截，所以按规矩扫了一遍补偿值

| 配置 | 只会造炮台 2/4/6 | 均衡发展（= 人机） | 经济+输出 |

- **抬伤害修不掉「人机没有失败面」**：均衡发展在 12/13/14 三档下都是 **88~100%**。

- **`ENTITY_DPS` 保持 12**：14 那一档把弱打法压到 8/4/2（6 人档 2/24），

  这就是「抬伤害」这条路的边界：它改变的是**守不守得住**，而本轮要修的
  「打不死它」已经由 `RETREAT_COMMIT` 解决了。

### 13.8 ⚠️ v9 客户端重写带出来的一个真 bug：**相机被夹到屏幕外**

E2E 在「拖动屏幕平移相机」这一步红了，报「视口里找不到一块落在地图上的空地下手」。
把断言换成一份几何快照之后，一眼就看出根因：

```
inner=844x390   viewportRect={x:0,y:158,w:390,h:554}
mapStyle=translateX(301.464px) translateY(473.159px)   mapRect={x:301,y:631,w:1100,h:1320}
```

地图的宽高都对（1100×1320 = 25×30 格），但**它的平移量是 (301, 473)**，而夹取区间
本该是 `[vw - MAP_W - 88, 88] = [-798, 88]` 与 `[554 - 1320 - 88, 88] = [-854, 88]`
—— 301 与 473 两个数都**远远越界**。反推一下它们从哪来：把 `MAP_W`/`MAP_H` 换成
**0**，夹取区间就成了 `[390 - 0 - 88, 88] = [302, 88]` 与 `[554 - 0 - 88, 88] =
[466, 88]`，取 `max` 得到 **(302, 466)** —— 正是相机正在逼近的那个目标值。

所以：**相机在按「还没有地图」的尺寸做夹取。** 机制是

1. v9 把几何从**模块常量**改成了 **React state**（`mapRef`，开局/重连/换图时刷新）；
2. 主循环那个 effect 的依赖数组是 `[following, heroXY, camXY, vw, viewportH, reduceMotion]`
   —— **没有地图几何**；
3. 于是它在挂载时捕获的 `clampCam` 永远绑着 `EMPTY_MAP`（0×0），一直用到有别的
   依赖变化为止。

**症状**：跑动阶段没占到房的玩家（也就是**所有人开局那 30 秒**）看到的是一整片
背景 —— 地图被推到屏幕右下角外面去了。

**修法**：地图尺寸放进 `mapSizeRef`，`clampCam` 在**调用时现读**（闭包再旧也拿到
当前值）；尺寸还没到时按视口宽兜底，夹取区间退化成 `[-88, 88]` 这种正常的小范围。

**这条教训比这个 bug 本身值钱**：**把一份数据从「常量」改成「state/ref」时，
凡是「被 effect 闭包捕获、又不在依赖数组里」的函数，都要重新过一遍。**
v9 之前几何是常量，这个坑**只可能在那次重写里长出来**。同类的还有
`panResponder` 的 `useMemo([camXY, vw, viewportH])` —— 它里面也调了 `clampCam`。

## 15. 第十轮：**「双人套间打开全是黑的」**（2026-10-14，用户实报）

**它躲过了当时所有测试，而躲过去的方式比 bug 本身更值得记**。

### 15.1 定位：一张黑图，四种成因

「看不到地图」在这套界面里有四种完全不同的成因（**没渲染 / 被浮层盖住 /
相机夹错 / 地图尺寸为 0**），所以第一步不是猜，是**打一份几何快照**。快照立刻
把范围收窄到一种：

```
mapStyle: width: 0px; height: 0px; transform: translateX(-86.2px) translateY(88px)
doors: 0   gates: 0   beds: 0          ← 三类元素一个都没有
panel: run   （倒计时 00:28 在走、摇杆在、角色在）
```

- 地图盒 **0×0** ⇒ `MAP_W = map.mapW = p.w * TILE = 0` ⇒ 客户端手里是 `EMPTY_MAP`；
- 而**跑动阶段的面板、倒计时、摇杆全都正常** ⇒ 对局状态收到了，只有几何没吃进去。

第二步是**在浏览器里挂 `framereceived` 监听**，直接看线路上的字节：

```
[ws] type=sync  len=7239  map.id=suite w=31 h=24 rows=24 rooms=12 gates=6
```

服务端**发的是全量几何**。于是只剩一种可能：客户端在解析时抛了异常。

### 15.2 根因：闸门的载荷形状与房间门**分叉**

`buildMap()`（`app/src/stasisMap.ts`）里只有一个 `toDoor()`，房间门与共用闸门
共用它 —— 而它按 `d.door[0]` 取门格：

```js
function toDoor(d) { return { inCell: [d.in[0], d.in[1]],
                              doorCell: [d.door[0], d.door[1]], ... }; }
```

服务端 `Map.payload()` 给**房间门**发的是 `_door_json()`（`in`/`door`/`out`/`side`），
给**闸门**发的却是 `{"cell": …, "in": …, "out": …, "side": …}` —— `d.door` 是
`undefined`，`undefined[0]` 直接 `TypeError`。

引擎侧一切正常：闸门在 `stasis.py` 里就是一扇没有主人的门，字段同构、分支共用，
**30 条闸门用例全绿**。分叉只发生在**最后一公里的载荷**上。

### 15.3 为什么它躲过了 30 步 E2E

三件事叠在一起：

1. **E2E 只「选过图」，没在 suite 上开过局**。第 3 步（房主切成 suite、房间页
   文案跟着换、再切回默认图）验的是**大厅里的芯片接线**，而 bug 在**进对局之后**。
   那之后所有断言都按 dorm（25×30、气闸 `(7,0)`）写 —— 一局都没在 suite 上跑过。
2. **`socket.ts` 那个 `try` 是静默的**：

   ```js
   try { const msg = JSON.parse(...); this.dispatch(msg); } catch { /* ignore */ }
   ```

   本意是「服务端偶尔发了非 JSON 就丢掉这条」，实际把**处理器自己的异常**也一起
   吞了，而且一声不吭 —— 界面上唯一的表现是「图是黑的」，控制台里连一行日志都
   没有。**静默 try 会把「崩溃」伪装成「功能没做」**，两者的排查成本差着量级。
   定位时正是把它临时改成 `console.error(e)`，栈帧第一行就是 `at toDoor`。
3. **类型声明与实现一起撒了谎**：`stasisTypes.ts` 里 `StasisGateState extends
   StasisDoorPayload`（含 `door`）**又**多声明了一个 `cell`。两边都"有据可依"，
   TS 全绿。

### 15.4 修法（四处，缺一不可）

| 处 | 改动 |
|---|---|
| `stasis_map.py` | 新增 `Map.gate_door(gid)`，**与 `room_door` 同一个形状**；`payload()` 里闸门也走 `_door_json` |
| `stasisTypes.ts` | 删掉那个幽灵 `cell`（类型照实写） |
| `socket.ts` | `try` **只包 `JSON.parse`**，`dispatch` 挪到外面（真·解析失败才吞） |
| `test_stasis.py` | 新增 `test_a_gate_payload_is_the_same_shape_as_a_room_door`：三张图逐张验「房间门与闸门的键集**逐字相同**」 |

E2E 也补了一轮：**打完一局回大厅 → 换成 suite → 真的再开一局**，断言的是
**地图盒的像素尺寸**（`31×44 × 24×44`）与 12 门 / 6 外闸 / 12 床 —— 「尺寸为 0」
正是 `buildMap` 抛异常唯一的外部特征（顺带锁住了「局间换图」这条本来没人测的路径）。

### 15.5 三条教训

1. **「同构」要连载荷一起同构**。引擎里共用一批字段/分支只算一半 —— 只要客户端
   只有一个解析函数，**服务端的键名就必须只有一个**。给一个概念起两个名字
   （`cell` 与 `door`），代价是整张地图画不出来。
2. **静默 catch 是排查成本放大器**（同 §13.8 那条「闭包吃旧几何」一样，属于
   「机制没错、接线错了」的一类）。项目全局早就写着「不写空 try」，这一处漏了
   一年多 —— 它恰好长在**所有 WS 消息的唯一入口**上，于是任何一处处理器的异常
   都会变成「界面没反应」。
3. **E2E 的覆盖面要跟着「新维度」走**。v9 加了「多张地图」这个维度，而 E2E 只在
   大厅里验了选图 —— **新维度必须有一条「在新维度上真的玩一局」的断言**，
   否则新增的那条轴等于没测。回归已按这条补上（suite 开局那一轮）。

## 16. 第十一轮：**控场道具**（2026-10-14，待办项落地）

这一节回答的是 §11.8 里挂了一轮的那条：

用户本轮的指令是「把增强调研里待办事项一一实现」，所以这一轮把它做掉。

### 16.1 原作的这四件（中文联网调研）

| 粒子加速器 | 炮台**攻速 +50%** | 2048 |

同一份来源里还列了另外六件：取款机（128，让炮台「偷钱」）、瞭望台（256，炮台

⚠️ **可信度**：四条数值来自**同一段文字的两次转载**（好游快爆、虫虫助手，

只能算一条。英文侧搜不到（"Haunted Dorm" 的英文攻略极少，检索词全部落到

限制」「有没有冷却」这三件事来源里一个字都没有** —— 那三处是本作自己定的，
下面逐条写清。

### 16.2 换皮与落地方案

名字**全部是本作自己的**（v7 起界面上不许出现原版名称）：

| kind | 本作名 | 原创名 | 价（合金） | 上限/间 | 效果（本作） |
|---|---|---|---|---|---|
| `shield` | **应急力场** | 能量罩 | 64 | 1 | 门血 ≤30% 时展开 **3 秒无敌护盾**，冷却 **60 秒** |
| `binder` | **束缚弹射器** | 符咒弹射器 | 64 | 1 | 它**放技能时 30%** 概率定住它 **3 秒** |
| `cryo` | **低温阱** | 冰箱 | 256 | 3 | 每台 **−20% 攻速**（乘算，三台 ×0.512） |
| `accelerator` | **粒子加速器** | 粒子加速器 | 2048 | 1 | **本舱**哨戒炮攻速 **+50%** |

- **四件都掏合金**。这不是随手挑的：合金的唯一来源是精炼机，而控场道具正是
  「精炼机刚起来、炮台还没成规模」的那一段最想要的东西 —— 于是「先造控场还是
  先造矿」变成一道真选择题（同 §14.3 里「矿与合金是同一个池子」那条设计）。
- **上限是每间舱室**（同 `MAX_REPAIRS` 的口径）。应急力场与束缚弹射器是
  **布尔式**效果（有/没有），建第二台毫无意义 → 上限 1；低温阱与粒子加速器是
  乘算，叠起来会破坏机制 → 3 与 1。

### 16.3 三处必要的「翻译」（原作 → 本作）

1. **「猛鬼释放技能」在本作里对应什么** —— 原作的触发条件是它放技能。本作的
   静默体没有技能表，但有两个**可观测的离散瞬间**：**放 EMP**（每 25 秒一次）
   与**刚进入过载**（门血跌破 20%、攻速 ×2 的那一刻）。束缚弹射器就挂在这两个
   瞬间上。为此**新增了 `entity_rage` 事件** —— 过载原来只有「血条变红」这一个
   暗示，而它是守门人最该知道的一刻，本来就该显式下发。
2. **「无敌」落在本作的 DPS 模型上**就是「这三秒的伤害置 0」（伤害是连续 DPS，
   没有弹丸实体，见 §10.3）。护盾的剩余时长随 tick 下发（`doors[].shield_ms`），
   客户端在门上画一层罩子 + 一行「力场」标签 —— **不画出来的话，玩家看到的是
   「门卡住了」**。
3. **「+50% 攻速」落在本作里是「本舱炮台的 DPS ×1.5」**，而且**不跨舱室**：
   本作没有原作的「帮队友建造」，所以加成只作用于加速器所在舱室的塔。低温阱与
   束缚弹射器同理 —— 它们只护**它正在砸的那扇门**（闸门没有舱室，所以三件护不到
   共用外闸，这是有意的）。

### 16.4 采纳 / 不采纳

**采纳**：上面四件。理由：它们是「门顶不住之后」的第二层防御，而本作的合作线
此前只有远程修补（一个人花生物能救另一个人），四件补上了**「花合金买时间」**
这条完全不同的防线，也让合金在中后期多了一个去处。

**不采纳（含理由，勿重新评估）**：

| 项 | 不采纳的理由 |
|---|---|
| **瞭望台**（炮台射程 +20%） | 与本作已有的「炮台每级 +0.5 射程、6 格封顶」重复，而且射程在 6 格封顶之后**再加就是越过通道打到隔壁舱室的门**（`TURRET_RANGE_BY_LEVEL` 那条封顶的理由）。要它就得先推翻那条封顶 |
| **诱捕**（网住正在撤退的鬼 2 秒） | 它服务的是「撤退路上截杀」，而 v10 起**撤退本身已经要跑完整条走廊**（`RETREAT_SPEED_MULT` 那段），截杀窗口是设计里刻意留的；再加一层网等于把这套节奏推平。**如果实测发现它跑得太快、截不住，先动的是 `RETREAT_SPEED_MULT`，不是加道具** |
| **倒刺**（门被砸时反弹 1% 生命/秒） | 它把「门血」偷偷变成了输出手段，会让「升门」这条线的收益再次翻倍（v10 的 `RETREAT_COMMIT` 已经造过一次这种耦合，见 §14.5）。本作的门就是血条，不该兼输出 |
| **断头台**（鬼血 <20% 时打掉它 10% 上限） | 与「磨死它」这条主循环冲突：它把斩杀从「持续输出」变成「一次判定」。而且 2048 合金的价位上，粒子加速器是更好的选择 |
| **取款机**（炮台偷钱） | 原作的「偷钱」是它自己的经济系统的一部分，本作没有对应概念（合金只有精炼机一条来源，是刻意的） |
| **电磁圈** | 原始来源在它那里**截断了**，效果查不到 —— 没有依据就不做（同「查不到就写查不到」那条纪律） |

## 17. 第十二轮：**进化与撤退按用户口径重做**（2026-10-14，v13）

用户在这一轮中途给了四条口径，其中两条**推翻了 §12.6 与 §14.8 里挂着的待办**。
原话（逐字）：

> 不应该限制一局最多撤两次，可以无限撤退，但是每次至少需要把门打掉 25% 的血量才能
> 撤退（不含恢复，如果总共打了 25% 但门同时回血或升级满血，也要满足撤退条件，而不是
> 硬性检查现在门的血量是否 < 75%），而且鬼把血回满再出来进攻，而不是回到 40% 就出来，
> 并且回血过程中不无敌，只要在炮台范围内就可以打

### 17.1 三条口径 → 三处实现

| 口径 | 落地 | 推翻了什么 |
|---|---|---|
| **撤退次数不限** | 删掉「一局最多撤两次」（`RETREAT_LIMIT` 与 `retreats` 字段、快照里的 `retreats_left`、界面文案一起删） | §12.6 那条「给撤退加次数上限」（王国保卫战那套）。**它是错的**：次数用完 = 它后期再也回不了血，玩家的输出一够它就必死，难度梯度整个塌掉（实测见 §17.4） |
| **每一趟必须打掉门血上限的 25%** | `trip_damage >= trip_commit`，而 `trip_commit` 在**出发那一刻按门血上限冻住**（`_start_trip`） | 判据从「此刻门的血量比例」改成「**这一趟打掉的伤害**」。前者会被「边挨打边修补 / 升级即满血」永远挡在门外 —— 用户点名的就是这个坑 |
| **回满血再出来 + 回血中不无敌** | `REGEN_UNTIL` 0.4 → **1.0**；再生期间照样吃炮台伤害（v10 起已经是这样） | v2 那条「必须 < 1，回满血就再也打不死了」的注释。它的两个前提（再生无敌、撤退没有门槛）现在都不成立了 |

**连带修掉一个「表现层说谎」**：`dynamic_snapshot` 的 `shots` 原来挂着
`if e["state"] == "regenerate": []` —— 那是「再生期间无敌」时代的遗留。v10 删掉
无敌之后，伤害一直在结算，而**客户端一发弹道都不画**：玩家看着它当面掉血、
却看不到是谁在打。现在发不发只看「有没有塔够得着」。

### 17.2 进化：先试「按打掉的门血归一」——量到正反馈，改回「按砸门时长」

§11.4 / §12.6 / §14.8 连记三轮的那条是「把鬼的进化彻底改成按砸门进度」。第一版
按最直白的方式实现：进度 = `伤害 / 该门当前的血量上限`，攒够一定量升一级。
**跑模拟台立刻否掉了它**（16 局 × 5 打法 × 3 人数档）：

| 阈值（每次进化要砸掉几扇门） | 结果 |
|---|---|
| 0.25 | **任何打法都在 48 秒内全灭**（均 8~10 级） |
| 0.5 | 均衡发展 16/6/7 |
| 0.75 | 均衡发展 16/16/15，但只造炮台也有 7/2/2 —— 刀刃上 |
| 1.0 | **谁都能赢**（4/6 人档 16/16、均 1.3 级） |

根因是**正反馈**：升级越快 ⇒ DPS 越高 ⇒ 砸穿同一扇门越快 ⇒ 升级更快。这条曲线
在 0.5 与 0.75 之间从「全灭」翻到「全胜」，**中间没有可用的档位**。

现在的实现是 **`EVOLVE_ATTACK_MS`（砸门时长）**：进度只在它**真的贴着门啃、
门血在掉**的那些 tick 累加（游荡 / 赶路 / 追人 / 撤退 / 再生**一律不算**），
啃够 35 秒升一级。于是升级速度恒为「每 35 秒的**实际啃门时长**一级」，
**与它当前多强无关** —— 正反馈被掐掉了。它同时更贴原型（砸门才升级），
而且**顺带修掉 §11.8 记的那条**：老口径的「累计 1500 伤害」是绝对值，门血每级
翻倍 ⇒ 砸破一扇 13 级门会一口气把它顶到满级；换成时长之后，门血厚不厚由
「砸穿它要花多久」自己表达。

⚠️ **代价写清楚**：一局里它大概只有一半时间在啃门，所以 35 秒 ≫ 老计时器的
50 秒**游戏时钟**，但**成长其实更慢**；而「把它打跑」第一次真的能掐断它的成长
（老实现里打跑只是让它晚回来一点，等级照涨）。

### 17.3 平衡：v13 的表（`test/balance_stasis.py --games 24`，只有击杀算赢）

| 打法 | 2 人 | 4 人 | 6 人 |
|---|---|---|---|
| 只会造炮台 | 8/24 | 4/24 | 6/24 |
| 龟缩守门 | 10/24 | 4/24 | 6/24 |
| **均衡发展（= 人机）** | **24/24** | **24/24** | **24/24** |
| 经济+输出 | 22/24 | 17/24 | 17/24 |
| 矿工（见 §17.5） | 24/24 | 23/24 | 24/24 |
| 超时 | 0 | 0 | 0 |

**这张表在 v13 里其实只量了一件事：有没有把生物能换成「升级过的」输出。**

- 两条「塔停在 1 级」的打法（只造炮台 / 龟缩守门）**全在 17~42%**；
- 三条「会把炮台升上去」的打法**全在 71~100%**。

对照实验最干净：把「矿工」那条的**最后一步（升炮台）删掉**，同一条打法从
**16/15/16** 直接掉到 **1/0/0** —— 它该造的矿一座没少、生物能一分没少，
只是没有任何东西把生物能换回输出。这与 v8 定下的胜负条件是一致的
（**只有击杀算赢**），只是 v13 把「不设防」的代价从「发育慢一点」改成了
「失去唯一的打断手段」（成长现在挂在砸门上）。

### 17.4 「撤退次数上限」为什么被撤回（实测）

同一批参数下，两种撤退规则各跑 16 局 × 5 打法 × 3 人数档：

| | 均衡发展 2/4/6 | 只会造炮台 | 龟缩守门 |
|---|---|---|---|
| 一局最多撤 2 次 | 16/11/12 | 12/7/5（旧口径下是 9/3/2） | 15/7/6 |
| **次数不限（现值）** | 16/16/16 | 5/3/4 | 7/3/4 |

次数上限**把三条打法一起拉高**，而且把「只会造炮台」从 8~37% 抬到 44~75% ——
因为限制撤退 = 它后期再也回不了血 = 玩家的输出一够它就必死。**难度梯度被压平**
就是这条规则的直接后果，这也是它被撤掉的量化理由（不是口味问题）。

### 17.5 「救矿工」这条待办：两次都是「它测的不是矿工」

§14.8 挂的是「矿的性价比是用户拍过板的，要救它得动产率或合金需求」。**这一轮
一个字都没动那些数**，因为实测下来问题不在矿上：

1. 原定义是「2 座塔 + 精炼机，合金全砸矿」⇒ **0/24 全灭**。它测的是「一炮不造」；
   改成 4 座塔之后**仍然 0/24** —— 因为它除了造矿什么升级都不做（床停 1 级、
   门停 1 级、塔停 1 级），那还是自杀；
2. 现在它是一条**真的经济流**：4 座塔 + 精炼机起步，合金全砸矿，生物能优先顶床
   （床的钱被门等级卡着就先升门），**最后才轮到升塔** ⇒ **24/23/24**；
3. 而**游戏里的「矿工」人机性格本来就是活的**（§14.7 那套 16 局/档：9/5/5）——
   这一轮只把它的**开局炮台从 3 座提到 4 座**（不动任何数值），因为它那条
   「少铺一座塔」的性格在 v13 里的代价变了：少一座塔 = 少一个打断它成长的手段。
   实测 **9/5/5 → 11/7/7**。

**结论：矿这条线不需要动**（它现在是「先矿后床」这条经济流的正当组成），
要救的是两个**风格化脚本的定义**。

## 18. 这一轮**仍然有意不做**的两条（从 §14.8 顺延，理由已复核）

用户这一轮要求「把增强调研里待办事项一一实现」。下面两条**经过复核仍然不做**，
理由与 §14.8 写的一致，另附这一轮的复核结论 —— 它们不是「忘了」，是**判断为不该做**：

| 项 | 复核结论 |
|---|---|
| **给共用闸门做「按出资分收益」的贡献账本** | **拆成两半**：**可见性那一档做了**（§18.1），**分收益那一档不做**。理由是它一旦与收益挂钩，就会长出「谁该出多少」的争议，而本作没有聊天、没有投票、也没有房主仲裁 —— 那等于把一道人际题硬塞进一个没有说话渠道的界面 |
| **给「假装没占到房」之类的 AI 花招** | **不做**。用户对 AI 的要求是「不必聪明、偶尔乱来」，`noise`（按比例故意放弃最优解）已经精确覆盖它；而且 v13 把「占房 / 躺下」这条链路的代价抬高了（没躺下 = 不能建造、走到走廊就是出局），**「假装没占到房」在本作里等于自杀**，不是花招 |
| ~~**去掉 `MAX_ENTITY_LEVEL`（让它无限进化）**~~ | 仍然不做（§12.6）：那等于把用户明确否掉的时限换个说法塞回来 |

### 18.1 出资账本：这一轮只做**可见性**（v13）

`stasis.py` 新增 `_credit_gate()`：升闸门、修闸门都把**实际花掉的资源**记到
`gates[gid].contrib[uid]`，随 `map` 下发（`协议.md` 有字段），界面在**共用外闸面板**
里按出资额排序显示一行「出资：你 320 生物能 + 64 合金（3 次）· 某某 30 生物能（1 次）」。

- **为什么值得做**：§13.3 记的那条风险（搭便车 / 责任分散）是这一轮控场道具之外
  唯一一条明确的**反面证据**，而当时的处置只有「血条可见 + 人机性格里的 `gate_bias`」。
  「谁出的钱」一旦公开，「两个人都等对方升外门」就从一个**看不见的僵局**变成
  **看得见的一行字** —— 而这一局里没有聊天，玩家唯一的沟通渠道就是界面。
- **为什么只做可见性**：见上表。**任何数值收益都不挂在这份账本上**，
  它是一份纯展示的流水（代码里 `_credit_gate` 的注释也写死了这一条）。
- 回归：`test_stasis.py::TestGateMechanics::test_gate_spending_is_credited_to_whoever_paid`。

## 19. §12.6 那两条客户端项的处理（v13）

| 项 | 结论 |
|---|---|
| **把主循环与相机从 `StasisScreen` 搬出去** | **不做**。待办原文自己写着「收益不如上面几条确定」，而搬它要连 `Animated.Value` 的所有权一起动（相机、角色、静默体、门抖动四套值的创建/清理都在屏幕层），风险大于收益。**这一轮做的是另一半**：门与共用闸门抽成 `DoorLayer`（`memo`）+ 稳定回调（屏幕层用 ref 存最新实现，否则 memo 白写），E2E 复核通过 |
