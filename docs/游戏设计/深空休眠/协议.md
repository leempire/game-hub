# 深空休眠 WS 协议（前后端契约）

> **这份文档是前后端的唯一契约。** 并行开发时以它为准；改协议先改这里。
> 设计依据见 [设计.md](设计.md)，复刻调研见 [增强调研.md](增强调研.md)，
> 引擎实现在 `server/app/game/stasis.py`，地图几何在 `server/app/game/stasis_map.py`。

## 与其它游戏不同的三点

1. **它是本项目第一个有服务端 tick 的游戏**：服务端每 200ms 推进一次引擎并广播
   `stasis_tick`。客户端**不要自己推演战斗**，只按收到的快照渲染 + 插值。
2. **状态分三层下发**（频率不同），客户端要分别处理：

   | 消息 | 频率 | 内容 |
   |---|---|---|
   | `stasis_tick` | 5 Hz | 会动的东西：时钟、静默体位置、**玩家位置**、门血、资源、**「能不能躺下」** |
   | `stasis_state` | 离散动作后 + 进房/重连 | 全量：地图（房型 + 门 + 建筑） |
   | `stasis_events` | 立即 | 离散事件（门破/撤退/进化/EMP/撞倒…） |

3. **服务端是位置的权威，客户端做本地预演**。摇杆方向每 tick 上行一次，服务端按
   方向积分位置并广播；客户端为了手感也本地按同一个方向与速度积分，收到 tick 后
   按服务端位置校正（差得远直接吸附，否则插值）。**落点碰撞客户端也要算一份**
   （`stasisMap.canStand`，镜像自服务端 `stasis_map.can_step`）——预演如果穿墙，
   校正时会被拽回来，看起来像瞬移。

## 客户端 → 服务端

沿用现有 `ready` / `start` / `add_bot` / `remove_bot` / `surrender` / `leave` / `ping`。

> ⚠️ `surrender` 在服务端对深空休眠走 `rm.stasis_surrender`（**只结束本人、遗产平分
> 给队友**），**不能**调通用的 `rm.surrender`——那是「对手获胜」的 2 人对战语义，
> 会把整局判给静默体。文案上叫「弃守」。
新增这些动作：

| type | 字段 | 说明 |
|---|---|---|
| `stasis_move` | `dx`, `dy`: float（-1..1） | **移动输入，5 Hz，每 tick 一条**。松手必须补一条 `(0,0)`，否则服务端会一直按最后的方向推着人走。**躺着时服务端把方向压成 0** 并回 `{ok:false, reason:"lying"}` |
| `stasis_lie` | — | **躺进休眠舱**（**人要走到休眠舱的九宫格之内**，v6 收紧）。**跑动阶段就能躺**，躺下**不可逆** |
| `stasis_build` | `kind`: `"turret"`\|`"refinery"`\|`"repair"`\|`"copper"`\|`"silver"`\|`"gold"`\|`"diamond"`，`cell`: `"x,y"` **字符串** | 在空格建造。**四座矿是四个独立的 kind**（v5），没有「培养槽升级链」。**纳米修复器每间舱室最多 4 台**（v7，`stasis.MAX_REPAIRS`），菜单里要把 `n/4` 写出来 |
| `stasis_upgrade` | `target`: `"bed"` \| `"door"` \| `"x,y"` \| `"gate:G1"` | 升级休眠舱 / 气密门 / 该格的建筑 / **共用闸门**（v9）。能升的建筑：哨戒炮（13 级）、精炼机（**v10 起 10 级**）、**钻石矿（v10 起 2 级，2 级＝氪金矿）**；纳米修复器与其余三座矿不能 —— 矿是并列条目，想换就拆了重造。**第 6 级起同时要生物能与合金**（合金 = 生物能 / 32，v7），客户端的两张费用表要跟着看 `upgrade_alloy`。⚠️ **矿升级掏的是合金**（与建造费同一个池子，`stasis.upgrade_res`），客户端不能用「生物能够不够」去判 |
| `stasis_demolish` | `cell`: `"x,y"` | 拆除，返还建造费的 50% |
| `stasis_patch` | `target_uid`: int \| null，**或 `gate`: `"G1"`** | 修补气密门；省略或等于自己＝修自己（20 生物能），给别人修 ×1.5（30）。**v9 起带 `gate` 就是修共用闸门**（一律按 1.5 倍算，它是两个人的前线） |
| `room_setting` | `key`: `"map"`，`value`: `"dorm"` \| `"suite"` \| `"atrium"` | **房主在等待大厅里选地图**（v9；v1.15 起走全站统一的房间级设置入口）。只能等待态发；换图会把人机全部移除（人机的性格是开局时按人数发的）。服务端回一条 `lobby` 广播给全房，选项与当前值在 `room.settings` 的 `map` 项里 |

> **`stasis_stand` 已删除**（v4）。躺下不可逆，整局都在这张床上 —— 于是
> 「走出去救队友」的玩法连同协议一起删掉了（`增强调研.md` §9.3）。客户端发
> `stasis_stand` 会落到未知类型分支（什么都不发生）。

> **`stasis_lie` 是「进房间之后要干嘛」那一步**，也是**开启一切操作的那一步**。
> v2 的 `in_bed` 由**位置**推出（站在床格上＝躺着），玩家走进舱室站在床边时界面上
> 没有任何东西告诉他还要再走一步，而站着产的资源是零 —— 用户实测报的就是
> 「进房间没法躺下、生物能没有增加」。现在 `lying` 是显式状态：
> **躺着才产资源、躺着不能移动、位置被吸到床心**。
> v4 又加了两条：**跑动阶段（倒计时内）就能躺**（原型就是倒计时内上床），
> 而且 **`build` / `upgrade` / `demolish` / `patch` 全部要求已躺下** ——
> 没躺下时回 `error: "要先躺进休眠舱才能建造与升级"`。
> 服务端在躺下后推一份全量 `stasis_state`（同其它离散动作）。
>
> **v6 把判据收紧成「人在休眠舱的九宫格之内」**（用户要求），同时**把判定权整个
> 交给服务端**：`stasis_tick` 的每个玩家多带一个 `lie` 布尔值，客户端「躺下」
> 按钮的显隐**直接读它**，不再自己算。理由是这条判据在客户端复刻过三版都不对
> （5 格太窄、整间舱室只是把边界推远），根因是客户端预演与服务端权威位置稳态差
> 0.14 格、跨格子边界时能差出一整格 —— **客户端的第二份实现必然漂移**（同象棋
> `legal` / UNO `playable` 的约定）。代价是按钮最多晚一个 tick（200ms）出现。

> `stasis_upgrade target="bed"` 有一条**硬前置**：气密门达到 `BED_DOOR_REQ` 里
> 写明的等级。**门槛是间断的**（不是每级 +1）：门 2 → 床 ≤4、门 5 → 床 ≤6、
> 钢门 3 → 床 ≤7、振金门 3 → 床 ≤10。不满足时回
> `error: "休眠舱升到 Lv5 需要铁门 5（现在 铁门 2）"` —— **客户端要把这句话
> 显示出来**，否则玩家只能看到「点了没反应」。

> **`cell` 是字符串 `"x,y"`，不是整数。** v1 用抽象格号（`0..N-1`），v2 把格子坐标化
> 之后建筑的键就是坐标。`ws.py` 的参数校验与客户端的 `stasisMap.cellKey` 必须同时改
> —— 只改一边会让建造请求被**静默拒掉**（只回一条 `error`，界面上「点了没反应」）。

**失败一律走现有的 `error` 消息**（`{type:"error", message:"..."}`），不静默。
可预期的失败文案（客户端可直接 toast）：`生物能不够` / `合金不够`（**v7 起两种资源
分别报错**，不再是一句笼统的「资源不够」）/ `这一格不能建造` / `纳米修复器最多 4 台` /
`这扇门是满血的` / `已经是满级` / `对局还没开始` / `你已经失压出局了` /
`要走到休眠舱旁边才能躺下` / `要先躺进休眠舱才能建造与升级` /
`休眠舱升到 LvN 需要<门名>（现在 <门名>）` / `这种建筑不能升级`。

`stasis_move` **不回 ack**：位置真值走 `stasis_tick` 广播，逐条回 ack 只会把上行带宽
翻倍，而客户端本来就做本地预演、不等 ack。它**也不落盘**（一局要发上千条，
是「tick 内零写盘」这条不变量最容易被破坏的地方；移动方向是瞬态输入不是状态）。

## 服务端 → 客户端

### `game_start` / `stasis_state` —— 全量状态

两条消息**载荷完全相同**（都是 `stasis.game_to_sync(gs, uid)`），差别只在信封：

| 消息 | 形状 |
|---|---|
| `game_start` | `{"type":"game_start","game": <载荷>}` —— **套 `game` 键**，沿用全项目惯例 |
| `stasis_state` | `{"type":"stasis_state", <载荷扁平展开>}` —— 与 `stasis_tick` 一致 |

> ⚠️ **扁平那条的 `game` 字段是字符串 `"stasis"`，不是对象。** 客户端如果把两条
> 消息塞进同一个处理函数、写成 `if (msg.game) adopt(msg.game)`，扁平那条会拿字符串
> 去当载荷用、被 `adopt` 的 `!g.players` 挡掉 —— 表现是「建造/升级完界面上什么也没变」。

```jsonc
{ "type": "stasis_state", "game": "stasis",
  "num_players": 6,
  "seat_uids": [1, 2, 3, 4, -5, -6],                    // 负数是人机
  "seat_colors": ["blue","red","green","yellow","purple","cyan"],  // theme.stasisSeatColors 的键
  "your_seat": 0,
  "your_uid": 1,
  "phase": "run" | "playing" | "over",
  "difficulty": "normal",    // v1.18.1 三档难度（easy/normal/hard）
  "difficulty_label": "标准",
  "run_ms": 24000,           // 跑动抢舱室倒计时剩余毫秒（phase=run 时有意义）
  "clock_ms": 42000,         // **游戏时钟**（跑动阶段恒为 0）
  "game_ms": 360000,         // **参考时长，不是终点**（v8）：一局没有时长上限，
                             // 客户端拿它画不了进度条，顶部那栏改成**正计时**
  "map": {
    // **v9 起整张图的几何由服务端下发**（见下文「地图几何」），这里只列状态字段
    "id": "dorm", "name": "标准货舱区",
    "w": 25, "h": 30,
    "rows": [".....cc...", ...],   // 30 行 × 25 字符：.=空 c=通道 w=舱壁 d=门格 f=地板

    "spawns": [[7, 1], ...],       // 跑动阶段的出生格
    "rooms": {
      "A1": {

        "cells": [[1,1],[2,1],...],// 该房型下的**地板格**（画地板用）
        "bed": [2, 3],

        "gate": "G1" | null,       // 这间舱室外面的**共用闸门**（v9，只有 suite 图有）

        "buildings": [ {"cell": "9,7", "kind": "turret", "level": 2}, ... ]

        //       copper·silver·gold(各 1 级) / diamond(**v10 起 2 级：2 级＝氪金矿**) /
        //       **v13 控场四件**：shield(应急力场, 1 台) / binder(束缚弹射器, 1 台) /
        //       cryo(低温阱, 3 台) / accelerator(粒子加速器, 1 台)
        //       四件都不产任何东西、也不能升级；效果落在「它正在砸的那扇门」或
        //       「本舱的炮台」上，见 增强调研.md §16
      }, ...

    "gates": {                     // **共用闸门**（v9，只有 suite 图非空）
      "G1": {

        // 服务端两边都走 `stasis_map._door_json`）—— 客户端的 `buildMap` 只有一个
        // `toDoor()`，房间门与闸门共用它。v9 第一版给闸门发的是 `cell`，两边叫法
        // 分叉 ⇒ `suite` 图上直接抛异常、**地图全黑**（用户报的，见 `增强调研.md` §15）。

      "pos": [8.5, 12.5],       // **浮点格坐标**，格 (x,y) 的中心是 (x+0.5, y+0.5)
      "lying": false,           // 躺下了（`stasis_lie`，**不可逆**）
      "in_bed": true,           // == lying 且位置在床心：正在产生物能
      // `lie` **只在 `stasis_tick` 里**（5 Hz），不在 `game_to_sync` 里 ——
      // 「现在能不能躺下」，客户端拿它画按钮、不复刻判据（见上文 v6 那段）
      "bio": 128, "alloy": 34,  // 整数，已取整
      "bed_level": 3,

                                // 「龟缩」「莽夫」这样的标签（`AI_PROFILE_NAMES`）
    }, ...
  },
  "finished": false,
  "reason": null,               // "killed" | "timeout" | "wiped"（v8 起没有 rescue）
  "winner": null                // "players" | "entity"
```

**地图几何：v9 起整张由服务端下发**（`stasis_map.Map.payload`）。

v9 之前是「协议只下发房型分配（`map.shapes`），格子类型 / 门位 / 床位两边各推
一份」——那是**单张地图**时代的做法（同 `ludo.py` / `ludoBoard.ts` 的约定）。
要做多张地图时这条就崩了：每加一张图，客户端那份几何实现都要跟着改一遍，而且
**两边算出来的东西必须逐格一致**。现在服务端把整张格子网格（`rows`，30 行 × 25
字符的字符画）连同每间舱室的包围盒 / 地板格 / 门的三格 / 床位、每扇闸门的三格
一起发下来，客户端一行几何规则都不用重写（`app/src/stasisMap.ts` 只剩解析）。

代价是 `game_to_sync` 大了一点（约 1KB），但**一局只发几次**（`game_start` 与
离散动作后的 `stasis_state`），不进 5 Hz 的 tick。

地图注册表（`stasis_map.SPECS`）当前三张：

| id | 名字 | 尺寸 | 特点 |
|---|---|---|---|
| `dorm` | 标准货舱区 | 25×30 | 12 间独立舱室，**默认图**（与 v8 之前逐格相同） |
| `suite` | 双人套间 | 31×24 | 6 组「**门厅 + 两间套房**」，每组外面一道**共用闸门** |
| `atrium` | 中庭货舱 | 30×27 | 12 间舱室围着中央大厅，通道更长 |

`suite` 是**专为双人合作**做的那张（用户要求）：鬼要打里面那间，必须先砸破外面
那扇共用闸门 —— 于是同一组里的两个人天然有分工（一个发展经济、一个发展火力）。
闸门**没有主人**，字段与房间门同构（`door_level` / `door_hp` / `emp_until_ms`），
另外多一个 `broken`；**破了就永久敞开**（房间门破了会把舱室清空重置，闸门不会，
它只把门厅交出去）。

⚠️ **「同构」是这条协议里最容易说一套做一套的地方**：引擎侧同构（同一批字段、
同一批分支）只是第一半，**载荷也必须逐字同构** —— 客户端的 `buildMap` 只有一个
`toDoor()`。v9 第一版就是引擎同构、载荷分叉（闸门发 `cell`、房间门发 `door`），
于是 `suite` 图上客户端抛异常、**地图全黑**，而服务端一切正常（见 `增强调研.md` §15）。
判据写成了回归：`server/test/test_stasis.py::TestMapPayload::
test_a_gate_payload_is_the_same_shape_as_a_room_door`。

### `stasis_tick` —— 动态快照（5 Hz）

```jsonc
{
  "type": "stasis_tick",
  "clock_ms": 42200,
  "run_ms": 0,
  "phase": "playing",
  "entity": {
    "level": 4,
    "hp": 8420.5,
    "max_hp": 10000.0,
    "state": "idle"|"approach"|"attack"|"chase"|"retreat"|"regenerate",
    "pos": [9.5, 11.0],       // **浮点格坐标**，直接乘 TILE 画
    "path": [[9,12],[9,13]],  // 还要经过的格子；**空数组＝已到达**
    "target_door": "B2",      // 正在逼近/攻击**哪扇门**：舱室 id 或 "gate:G1"；
                              // null＝游荡中。**v9 从 `target_room` 改名而来** ——
                              // 目标可能是共用闸门，叫 room 就名不副实了
    "target_uid": 2           // 正在追谁（state=chase 时）；否则 null
  },
  "players": {
    "1": {"pos": [12.5, 12.5], "room": "B2", "lying": true, "in_bed": true,
          "lie": false,     // **现在能不能躺下**（v6）。客户端「躺下」按钮的显隐
                            // 直接读它 —— 判据不在客户端复刻，见上文 `stasis_lie`
          "bio": 128, "alloy": 34, "alive": true}, ...
  },
  "doors": { "B2": {"hp": 620.0, "max": 750.0, "shield_ms": 0} },  // 只含有主的舱室
  // `shield_ms` = **应急力场的护盾还剩多久**（v13，0 = 没开）。那 3 秒里门不掉血，
  // 客户端据此画罩子 —— 不画出来的话玩家看到的是「门卡住了」。
  // **表现层弹丸**（v5）：哪些哨戒炮正在开火、朝哪儿打。引擎里**没有弹丸实体**
  // （伤害是连续 DPS），这一层只是把「谁在打」告诉客户端，由客户端自己定开火
  // 节奏画枪口焰/弹丸/命中环 —— 见 `增强调研.md` §10.3。
  "shots": [ {"cell": "9,7", "level": 3, "tx": 9.5, "ty": 11.0}, ... ]
}
```

**静默体与玩家的位置都直接画**：`pos` 是浮点格坐标，乘 `TILE` 就是像素。
`path` 只用于画「它要往哪走」的提示线，**客户端不要自己推路径**（同飞行棋的教训）。
两条消息的 `players` 是**字段级合并**的：tick 只带会动的字段，把 tick 当全量状态用
会把建筑列表、门的等级、舱室归属全部抹掉。

### `stasis_events` —— 离散事件（立即下发）

```jsonc
{ "type": "stasis_events", "events": [ {"type": "...", ...}, ... ] }
```

| event.type | 附加字段 | 客户端该做什么 |
|---|---|---|
| `airlock_open` | — | 跑动阶段结束，静默体进场（重震） |
| `room_claimed` | `uid`, `room`, `auto?` | 占房提示；`auto: true` 是倒计时结束后的自动分配 |
| `room_released` | `uid`, `room` | 走出舱室、让出了它（**躺下之前舱室跟着人走**，见 `设计.md` §1.3）。客户端不需要提示，但收到它意味着 `stasis_state` 会紧跟一份 |
| `entity_target` | **`door`** | 提示「静默体盯上了 XX 的舱室 / 共用外闸」 |
| `entity_attack_start` | **`door`** | 门体震颤开始 |
| `entity_chase` | `uid` | 提示「静默体在通道里追 XX」 |
| `entity_retreat` | — | 提示「静默体被打退了」 |
| `entity_regenerate` | — | 提示「退回气闸再生」（**再生期间它照样能被打**，见 `设计.md`） |
| `entity_return` | — | 提示「它又出来了」 |
| `entity_evolve` | `level` | 提示「静默体进化到 Lv N」+ 震动。**v13 起成长只来自砸门**（见 `设计.md`），所以这条只在它真的啃到门时才会来 |
| `entity_rage` | **`door`** | **它进入过载**（门血跌破 20%，攻速 ×2，v13 起显式下发）。以前只有「血条变红」一个暗示，而这是守门人最该知道的一刻 |
| `entity_bound` | `room`, `ms` | **被束缚弹射器定住**（v13）。`ms` 是定身时长（3000），期间它不动、不砸门、不放技能 |
| `shield_up` | `room`, `ms` | **应急力场展开**（v13）。`ms` 是护盾时长（3000），期间该舱室的门**不掉血** |
| `entity_emp` | **`door`**, `rooms` | 提示「XX 的哨戒炮被 EMP 瘫痪」；**砸闸门时 `rooms` 是它后面所有的舱室**（闸门是共用前线，瘫一半留一半说不通） |
| `door_breached` | **`door`**, `uid` | 该舱室失压，重震 |
| `gate_breached` | `gate`, `rooms` | **共用闸门被砸破**（v9）—— 不淘汰任何人，只是把门厅交给了鬼 |
| `entity_catch` | `uid` | **在走廊里被静默体抓住**（紧跟着就是 `player_eliminated`）。它只抓得到没躺下的人 |
| `player_eliminated` | `uid`, `heirs`, **`cause`** | 有人出局；`cause` = `entity`（被鬼抓）/ `breach`（舱室失压）/ `surrender`（弃守）—— 三种死法文案不同，只靠 uid 分不出来 |
| `entity_killed` | — | 反杀成功 |

### `game_over`

```jsonc
{ "type": "game_over", "winner": "players"|"entity",
  "reason": "killed"|"timeout"|"wiped", "ranking": [ ... ] }
```

> ⚠️ **这条不带 `game` 载荷**（只有 winner / reason / ranking）。别的对局屏习惯写成
> `setGame(prev => ({...prev, ...msg.game}))`，在这里会什么都不发生 —— 必须自己把
> `finished` 置上，否则结算弹窗永远不弹。

`reason`：`killed`（打死了静默体）/ `timeout`（撞上防卡死兜底）/ `wiped`（全员失压）。
`winner`：`players` / `entity` —— **`players` 当且仅当 `reason == "killed"`**。

> ⚠️ **v8 删掉了 `rescue`（「撑到救援舰抵达」）**：用户要求唯一的获胜条件是击杀
> 静默体，而且**一局没有时长上限**（「不要求 6 分钟内打死，时间不限」）。
> 所以终局只有两条：打死它（`killed`，胜）或全员失压（`wiped`，败）。
> `timeout` 只剩一种来源 —— `STALL_CAP_MS`（30 分钟）的**防卡死兜底**，正常对局
> 碰不到（静默体 10 级封顶、约 7 分半就不再变强，而玩家的炮台是无限爬坡的）。
> 老战绩里仍可能存着 `rescue`，客户端保留了对它的展示兜底
> （`HistoryScreen.STASIS_REASON`），但**新协议不再产生这个值**。

## 服务端内部约定（给改 room_manager/ws 的人）

- **tick 循环**：`room_manager._stasis_tick_loop(code)`，每 `TICK_MS` 醒一次。
  - **懒启动**：房间进 `playing` 且 `game == "stasis"` 时起任务。
  - **自净**：循环里每轮检查 `room["status"] != "playing"` → `break`，`finally` 里
    从 `_tick_tasks` 摘掉自己。
  - **对账兜底**：`_sweeper_loop` 里补一句「playing 的 stasis 房没有活任务 → 起一个」。
  - **全员离线时暂停**：房间里一个真人在线都没有 → 只 sleep、不 `advance`
    （游戏时钟因此冻结，重连后无缝继续）。
- **落盘**：tick 内**一次盘都不写**。tick 里只改内存 + `_touch_memory_only(room)`
  （只刷 `last_activity`，不写 SQLite）。**每 25 tick（5 秒）**才落一次关键帧；
  离散动作照旧立即落盘（走 `_finish_action`）。
- **热重启**：`reschedule_after_restore` 里加分支 —— `status == "playing" and
  game == "stasis"` → 起 tick 任务。状态全在 `game_state` 里，最多丢 5 秒游戏时间，
  且因为用的是游戏时钟**不会跳变**。
- **人机队友**：`stasis_ai.decide(gs, uid)` 返回一个动作 dict 或 None。
  **跑动阶段每 tick 都要调**（那时它的动作是「移动方向」，按间隔发会让它一顿一顿地走），
  对局阶段按固定间隔（1 秒）调。
  - **性格**（v9）：开局 `assign_profiles(rng, 人机的 uid)` 发**互不相同**的一套
    （`Profile` 存在玩家的 `ai_profile` 上）。`decide()` 的流程只有一份，
    差异全在 `Profile` 的旋钮上；`noise` 会按比例跳进 `_random_action`（**只在
    合法动作里掷骰子**）。⚠️ **`_stasis_bot_think` 静默吞 `ValueError`** ——
    人机返回的任何被引擎拒掉的动作都会变成「一次决策一个动作」下的死循环，
    所以每加一条判据都要带 `_can_upgrade` / `_bed_gate_ok` 这类前置检查。
- **人数**：2-6（`stasis.PLAYER_MIN` / `PLAYER_MAX`）。`room_manager.create_room`
  里 `max_players` 对 stasis 单独取 6，其余多人游戏仍是 4。
- **地图**（v9）：`create_game(..., map_id=...)` 时把几何定下并落进 `gs["map"]`
  （`id` / `shapes` / `rooms` / `gates` / `airlock`）。房间上另存一个
  `stasis_map_id`（等待大厅里房主可改，**v1.15 起走全站统一的 `room_setting`**），
  **开局后改不了**。选项与当前值随 `room.settings` 的 `map` 项下发
  （`{key,label,kind,value,value_label,blurb,choices}`），房间页只画那一行摘要 +
  底部抽屉 —— 服务端不再单独下发 `stasis_maps`。
