# 点格棋 设计文档

- 屏：`app/src/screens/DotsScreen.tsx`　引擎：`server/app/game/dots.py`　AI：`server/app/game/dots_ai.py`
- 人数 2｜支持人机｜战绩落库

## 玩法

5×5 个点 = 4×4 个格。双方轮流在相邻两点间画一条边；**谁画出格子的第 4 条边
谁就占下这格，并立即再走一次**（连画）。所有边画完后格子多者胜，可平局。

```
│        [认输]  [退出]        │
└─────────────────────────────┘
```

## 交互设计

### 画边：细长热区

每条边是一个绝对定位的 `TouchableOpacity`，带 `testID="h-y-x"` / `"v-y-x"`：

- 水平边热区：`width = cellSize - 2*DOT_R`，`height = 2*HIT_PAD + EDGE_W`
- 垂直边热区：转置

即热区在**垂直于边的方向上被放大到 `2*HIT_PAD`**，这是细长目标的标准做法——
让手指不用精确压在 3px 的线上。

视觉上只画 3px 的线（`EDGE_W`），但可点区域是它的十几倍。

**「可画边」提示（v1.5.2 重做）**：轮到自己时，尚未画的边画成**细虚线 + 中性灰**
（`HINT_EDGE_W = 2px`、`colors.textMuted` `#6B7280`，vs 棋盘底 `#FAFAF8` 实测
**4.63:1**）。原先的淡紫 `rgba(79,70,229,0.15)` 只有 **1.25:1**，边在哪根本看不出来。

为什么不冒充「已画边」（已画边 = 3px 实线 + 饱和玩家色）——三层差异：
1. **虚线是主通道（形状）**：虚线在界面语言里表示「尚未填上 / 待画」，实线才表示
   「已存在」。这是与颜色无关的第二通道，色觉障碍用户同样能分辨；
2. 线宽 2px < 已画的 3px，更远小于封格提示的 6px；
3. 中性灰与玩家蓝/红在色相上完全分离。

虚线是**显式画的 3 段小短线**（`EdgeLine` 的 `dashed` 分支），没有用
`borderStyle: 'dashed'`——RN 原生端单边虚线在 Android 上不渲染、iOS 上遇
`borderRadius` 会退化成实线，跨端不可靠。非己方回合的未画边仍是极淡灰
（`rgba(0,0,0,0.06)`，不暗示可点）。

### 封格提示（把规则画出来）

点格棋真正的难点是**连画**——封格后立刻再走一次。16 个格子光看比分数字，新手
读不出哪一步会连锁，规则说明写再多也不如直接画在棋盘上。

- 轮到自己时，扫描每条未画的边：若它相邻的任一格已有 **3 条边**，这条边就是
  「封格边」，渲染成琥珀色（`colors.warning`，vs 棋盘 4.81:1）并且**线宽加倍**
  （6px vs 已画边的 3px）。
- **第二通道必须是线宽，不能只靠颜色**：琥珀与红边的亮度几乎相同（1.04:1），
  只给色觉障碍用户看会和「红方已画」混淆。
- 只在**轮到自己**时显示；封格成功后提示立刻消失（此时该格已满 4 条边）。
- 测试钩子：提示边的 `testID` 是 `dots-hint-{h|v}-{y}-{x}`（已画的边仍是
  `h-y-x` / `v-y-x`，e2e 靠它点击，**不要改**）。

回归：`e2e_dots_smoke.py` 第 07-09 步（凑 3 条边 → 断言只有己方回合出现提示、
且落在唯一那条边上 → 顺着提示封格并连画）。

### 连画（extra turn）

画出第 4 条边后服务端**不切换回合**，玩家继续画。前端不需要特殊处理——
回合提示文字自然还是「轮到你画边」。这一点容易在改回合逻辑时被误改，
改 `dots_apply_move` 时要确认 `extra_turn` 分支仍不切 `next`。

### 反馈

- 画边：10ms 震动（原生）。
- 封格：格子填充玩家色（`rgba` 半透明，不遮挡点阵）。**填充有 220ms 的动效**
  （`BoxFill`：透明度 0→1 + 轻微放大 0.85→1，`useNativeDriver:
  Platform.OS !== 'web'`）——小元素的轻微变化落在方法论 §2 的 200-300ms 区间。
  一次可能封两格（连画），两格同时动。只有**本次走子封下的格子**才播动画
  （`animBoxes` 记录刚封的格子、340ms 后清空），避免重连 `sync` 时整盘已有格子
  一起「跳一下」。原实现是瞬时出现。
- 比分与「已占 N / 16 格」实时更新。

## 状态与协议

- `game_start` / `sync` 逐人下发（各自带 `your_color`）。
- 走子：`{type:'move', orient:'h'|'v', y, x}` → 广播 `move`
  （含 `completed` 坐标数组、`extra_turn`、`scores`、`next`）。
- 人机：`dots_ai.best_move` 返回 `(orient, y, x)`。AI 策略为「能封格必封 →
  不下第 3 条边 → 被迫开局时最小化连锁损失」。

## 结算

`dots_make_move` 在画完最后一条边时调 `_set_game_over(room, winner, 'score')`
把房间转 `finished`。

**这是本游戏最著名的一个坑**：早期漏调 `_set_game_over`，房间停在 `playing`，
玩家点「返回房间」后房间页 sync 到 `status=playing`，RoomScreen 立刻又把人
弹回对局页——表现为「返回房间按钮点了没反应」。回归由
`test_room_lifecycle.py::test_dots_natural_end_marks_waiting` 和
`test/e2e_dots_smoke.py`（真画完 40 条边再点返回）双重覆盖。

## 已知限制

- **边线热区**：`HIT_PAD = 20` → 热区高 **43px**，已接近 HIG 的 44pt。
  4×4 棋盘 cellSize 约 89px，再放大就会与相邻边热区重叠，这是上限。
- 点阵（`DOT_R=6`）与边线在深色模式下的对比度未单独校验。
- **执子颜色**：引擎标识是 `black`/`white`（PLAYER1/PLAYER2 的历史命名），
  但界面实际渲染为**蓝 `#4F46E5` / 红 `#EF4444`**，文案一律写「蓝方/红方」。
  曾出现「棋盘画的是蓝红、结算文案写黑白」的错位——文案与填充色现在都取自
  `DOTS_COLORS` 单一声明，不要再各写各的。

## 最近一步标记

刚画的那条边上叠一层**黄色光晕**（比玩家色粗 6px，两侧各露 3px，
`testID="dots-last-h-Y-X"` / `dots-last-v-Y-X`），与另外三个棋类共用同一套
「黄 = 最近一步」的语言（`theme.ts` 的 `lastMoveMark`）。

点格棋尤其需要它：边只有 3px 粗，两条相邻的边颜色又挨着，连画时根本看不出
对方刚画了哪条。黄色 + 加粗两条通道，同时**玩家色照旧从中间透出来**，不丢身份。

> **踩坑（勿回退）**：`handleMove` 原来只更新 `h`/`v`/`boxes`，**没有维护
> `prev.moves`**——`moves` 永远停在 sync 时的快照（开局是空数组），高亮取不到
> 数据。新增「最近一步」类需求时先确认 moves 链路通不通。

## 配色

- 归属格填充与比分点一律取自 `theme.playerColors`（引擎里叫 `black`/`white`，
  但棋盘实际渲染是蓝 `#4F46E5` / 红 `#DC2626`，文案一律「蓝方/红方」）。
- 点与边线色是 `theme.dotsInk`（vs 棋盘 9.86:1）。
- 「可画边」提示是 `colors.textMuted`（vs 棋盘底 4.63:1）；封格提示边仍是
  `colors.warning`（vs 棋盘 4.81:1）+ 线宽加倍。
