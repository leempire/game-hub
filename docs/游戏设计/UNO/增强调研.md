## 2. 玩法维度：官方与社区把 UNO 扩展成了什么

把所有来源的规则变化归一下类，**只有六种**（这是本方案的分类基础）：

| 类别 | 具体规则 | 需要什么 |
|---|---|---|
| **A. 出牌时机** | Jump-in / 同色同数字抢出 [1]；Sequences 连续出牌 [21] | 非本回合动作、放宽回合校验 |
| **B. 罚牌传递** | 同型叠加（现状）/ **等值或更高叠加** [8] / 任意功能牌互叠（Uno from Hell）[21] | 改 `can_play_now` 一条判据 |
| **C. 摸牌行为** | 摸一张（官方）[19] / **摸到能出为止** [8] / Force Play 自动出 [12] / 强制出牌不许摸 [16] | 改 `draw()` 与 `_can_draw` |
| **D. 手牌易主** | **7 换手 / 0 传手** [12][16] / 传一张给队友（Teams）[5] / Wild Swap Hands | 新动作 + 手牌整体重排 |
| **E. 牌堆与获胜条件** | No Mercy 六张新牌 + 25 张 Mercy + **最后一人存活** [7][8][9]；Go Wild 双倍功能牌 + Discard All [13]；500 分累计 [3][4] | 新牌面美术 + 新终局路径 + 跨局状态 |
| **F. 组队** | UNO Teams 2v2 [5][6]；官方 Partners [2] | 队伍状态 + 配合机制 |

**注意一件事**：官方自己的「产品线」其实就是把房规做成了独立商品 ——
`JUMP-IN UNO`、`UNO FLIP`、`UNO SHOW 'EM NO MERCY`、`UNO TEAMS` 各自只改一两条规则 [1][5][7]。
这说明**「房规」不是边缘玩法，它就是 UNO 这个游戏的主要扩展方式**。

### 与本作现状的差距

本作现在是「经典 + 同型叠加 + 单局定胜负 + 不抓罚 + +4 恒可出」。
上表里 **A、C、D 三类一条都没做**，B 只做了最保守的一档，E 只做了最小的牌堆。

## 3. 视觉维度

| 结论 | 来源 / 依据 |
|---|---|
| 新牌**必须沿用现有五层画法与四色形状徽标体系**（红圆 / 蓝方 / 绿三角 / 黄星 / 黑菱形），不能引入第二种视觉语言 | 本作 `设计.md`「颜色不能单独承载信息」；官方也做了无障碍牌面「Beyond Colors」[14] |
| 新牌（+6 / +10 / 跳过所有人 / 弃同色 / 变色反转+4）**角标必须在缩到 5px 时还认得出** | 本作角标规则（`设计.md`「角标是重叠状态下唯一的身份」）；牌宽 <52px 时不画角标 |
| 「颜色轮盘」这条牌需要**逐张翻牌的表现**，但**结果是服务端算的**，客户端只播动画 | 本作「弹道是纯表现层」的同类做法（深空休眠 `StasisShots`）；也符合「客户端零规则」 |
| 2v2 组队的**队友座位必须有独立标识**（不能只靠「他是我队友」的文字） | 座位条现在只画身份色点；组队档需要第二通道（如队友边框 + 「队友」徽标） |
| 模式名与说明**由服务端下发**，客户端不抄一份 | 本项目踩过「游戏名散在七处」的坑；`bs_sizes` / `stasis_maps` 已是这个做法 |

## 4. 交互维度

| 结论 | 依据 |
|---|---|
| **抢出（Jump-in）需要第二通道**：高亮现在等价于「轮到我」，抢出开启后「能出」与「该我出」是两回事，必须用徽标/文案区分，否则玩家分不清 | WCAG 1.4.1「颜色不能单独承载信息」；本作可出牌已用「位移 + 双环」双通道 |
| **抢输必须有明确提示**（「这张牌被抢走了」），不能静默失败 | 本项目铁律：被静默拒绝的动作在界面上就是「点了没反应」（海战棋武器、深空休眠建造都踩过） |
| **7 换手要选人**：座位条从「只读展示」变成「可点选」 | 军棋布阵「点两子交换」是同一类「两步选择」交互 |
| **手牌整体易主时不要逐张动画**，整体重排 + 一次提示即可 | 20 张牌逐张飞会糊成一片；2048 的 FLIP 动画是可参考的做法 |
| **房规档位芯片沿用 `RoomScreen` 现有的 `mapChips` 那一行** | 与扫雷难度 / 军棋玩法 / 深空休眠地图 / 海战棋尺寸完全同构 |
| **不做回合计时器** | 一起优诺有 10 秒时限 [16]，但本作 13 个游戏全部没有计时器（靠 120s 断线保座兜底），加一条会破坏全局一致性；「快节奏」用起手牌数表达即可 |

## 5. 方案：**一份引擎 + 一张房规表 + 命名预设**

### 5.1 核心设计主张

**不要为每个模式分叉一份引擎。**

三条理由：

1. **本作已有先例，而且刚被验证过**：军棋的明棋/暗棋是同一个引擎的 `mode` 字段；
   深空休眠的六种人机性格「差异全在 `Profile` 的旋钮上，决策流程只有一份」。
   分叉一份引擎意味着每个 bug 要修 N 遍、每条回归要写 N 份。
2. **规则之间会互相作用**：`摸到能出为止` + `25 张 Mercy` 必须一起开才有意义
   （前者让手牌爆炸，后者才有淘汰路径）[7][8]；`+4 严格化` 与 `叠加` 的口径必须同时定义。
   预设是「一组合法的旋钮值」，比 N 份实现更能表达这种耦合。
3. **社区玩法本来就是组合式的**：官方 2v2 赛事用的就是 `Stack + Discard All` 的组合 [15]。

具体做法：

- 引擎里新增 `game["rules"]`（一个 str 键 dict），**所有判据改读它**；
  **默认值必须与今天的经典行为逐字节一致** —— 这是硬回归保证。
- 新增 `server/app/game/uno_rules.py`：房规定义 + 预设表 + 每条规则的**中文名与说明**
  （随房间数据下发，客户端不抄）。
- 房间级设置 `uno_pick`（只有房主 / 只有 `waiting` / 改完广播 `lobby`），
  与 `luzhanqi_pick` / `battleship_pick_size` / `stasis_pick_map` / `mine_pick` **完全同构**。
- 客户端**一格规则都不写**：新旗标（`can_jump` / `jumpable` / `swap_targets` / `must_play` …）
  全部服务端下发，与现有 `playable` / `can_draw` 同一条纪律。

### 5.2 房规表（knobs）

| 键 | 取值 | 默认 | 引擎里对应今天哪一行 |
|---|---|---|---|
| `stack_mode` | `off` / `same` / `upgrade` | `same` | `can_play_now` 的 pending 分支（`same` = 现状） |
| `draw_until_play` | bool | `False` | `draw()` 只摸一张 |
| `must_play` | bool | `False` | `_can_draw` 恒真 |
| `jump_in` | bool | `False` | `_guard_turn` 拦掉非本回合 |
| `seven_zero` | `off` / `swap` / `rotate` / `both` | `off` | 7 / 0 现在只是普通数字牌 |
| `wild4_strict` | bool | `False` | `_matches_color_or_kind` 里 `is_wild → True`（**撤销「+4 恒可出」**） |
| `wild4_challenge` | bool | `False` | 无（依赖 `wild4_strict`） |
| `uno_penalty` | bool | `False` | `call_uno` 只置标记 |
| `hand_size` | int | `7` | `HAND_SIZE` |
| `deck` | `classic` / `no_mercy` | `classic` | `build_deck()` |
| `win_condition` | `first_out` / `last_standing` | `first_out` | `_finish_emptied` |
| `mercy_limit` | int \| None | `None` | 无（No Mercy 是 25） |
| `teams` | `off` / `2v2` | `off` | 无 |
| `rounds_to` | int \| None | `None` | 无（跨局，排到最后） |

### 5.3 预设档位

| 预设 | 组合 | 人数要求 |
|---|---|---|
| **经典** | 全默认（= 今天的 UNO） | 2-4 |
| **热闹** | `stack_mode=upgrade` + `jump_in` + `seven_zero=both` + `draw_until_play` + `must_play` | 2-4 |
| **无怜悯** | 热闹 + `deck=no_mercy` + `mercy_limit=25` + `win_condition=last_standing` | **≥3**（2 人局下淘汰≡出完，没有意义） |
| **组队** | `teams=2v2` | **恰好 4**（同五子棋满员先例） |
| **自定义** | 逐条开关（**不是一个芯片，而是一个状态**） | 2-4 |

`热闹` 与 `无怜悯` 都**不新增牌**（后者在批次 B 才换牌堆），所以批次 A 就能上两档体感明显不同的玩法。

### 5.4 分批排期

**批次 A —— 基础设施 + 三条轻量房规**（性价比最高，牌面美术零改动）✅ **已实现（v1.14）**
1. `uno_rules.py` + `game["rules"]` + 默认档逐字节回归
2. `uno_pick` 房间级设置 + RoomScreen 房规表单 + `help.tsx` 按档位给文案
3. 三条房规：`draw_until_play` / `jump_in` / `seven_zero`（外加 `must_play` 与
   `stack_mode=upgrade` —— 都是一行判据，顺手做了）
4. 预设：经典 / 热闹 / 自定义

> **与初版计划的两处出入**（记录在案，免得下次重新评估）：
> - **「官方」档（+4 严格化 + 可挑战 + 抓 UNO 罚）挪到了批次 B**。它们各需要一条
>   **事件窗口 + 一个新按钮**（挑战 / 抓），是真正的协议与交互改动，和批次 A
>   「零新概念」的定位不符。
> - **「自定义」不是一个可选档位，而是一个状态**。大厅里那几行开关本身就是它的
>   界面；再放一个「自定义」芯片，等于让房主点一个什么都不会发生的东西。
>   档位由 `preset_of` **反查**得出 —— 手动把开关调回经典那一组时，「经典」会自己
>   亮回来，界面显示的就是真实生效的那一份房规。

**批次 B —— 无怜悯牌堆 + 25 张淘汰** ✅ **已实现（v1.14，除颜色轮盘）**
1. 新牌 `+6` / `+10` / 跳过所有人 / 弃同色 / 变色反转+4
2. `deck=no_mercy` + `mercy`（25 张出局）
3. 预设「无怜悯」

> ⚠️ **计划里写的 `win_condition=last_standing` 是多余的**，已按原文改掉。
> 我原以为第二种获胜方式是「出完牌的人被淘汰、活到最后的人赢」，读到官方原文
> 「**两条**获胜路径：①像经典那样出完所有牌；②在别人因 Mercy 出局后成为最后站着
> 的人」才发现**出完手牌照常获胜**。于是只需要「手牌 ≥ 25 → 出局」，
> 「只剩一个人就终局」直接复用现成的 `_check_game_over`（认输/判负走的就是它）
> —— **一个旋钮都不用加**。这条如果做反了，会变成一种没人玩过的奇怪游戏。

> **「颜色轮盘」（Wild Color Roulette）** —— 初版计划把它留到下一轮（理由是它要
> 一个全新的「等待某人选择」状态），**后来还是放在同一批做了**：它确实是本作第一条
> 「等某个座位做选择」的状态机（`game["roulette"]` + `uno_roulette` 消息），
> 但拆开做反而要连着改两轮 `_guard_turn` / `playable_cards` / `_can_draw` 这三处
> 必须同时挡的地方，合在一起更安全。六张牌到齐，「无怜悯」才是完整的 No Mercy。

**批次 C —— 2v2 组队**（UNO Teams）
1. ✅ 队伍状态 + 对家配对（`seat % 2`）+ 「两人都出完才算赢」（v1.16）
2. ✅ 队友可以替你喊 UNO（v1.17）
3. ✅ **GOING OUT：出完手牌接管队友一半，接着打**（v1.17）
4. ✅ **TAGGING BACK IN：队友摸到牌就把场外的你拉回来**（v1.17）
5. ✅ **Wild Team Play / Wild Team Draw Four 两张专属黑牌**（v1.17）
6. ⬜ 「Passing Symbol」传牌牌（见下，**来源不足，仍不做**）
7. ✅ 人机要懂配合（换手不拿队友当对象；喊 UNO 会自动替队友喊）

> **v1.17 拿到了官方说明书原文，推翻了 v1.16 的两处判断**：
>
> 第一处是**「接管队友一半手牌」那条不再是「来源不足」**。[28] 是 Mattel 的
> `UNO TEAMS` 官方说明书（JLG93，`service.mattel.com/instruction_sheets/JLG93-Eng.pdf`），
> 里面 GOING OUT / TAGGING BACK IN / CALLING "UNO!" 三节把细节全写清了：
> - **出完手牌不等于出局**：队友把手里**一半（向下取整）**交过来，本人接着打；
>   **奇数张时传的人留多的那些**（9 张 → 传 4 留 5）。
> - **只有队友手里只剩 1 张**（半手传不出来）时本人才真的留在场外。
> - **TAGGING BACK IN**：人在场外时，队友**只要摸到牌**就立刻分他一半、把他拉回来。
>
> ⚠️ **这直接推翻了 v1.16 写在 `设计.md` 里的那句「这一档的张力在于『把牌倒干净
> 就跑等于把队友丢在场上』」** —— 官方规则里出完牌是**换半副新牌接着打**，
> 张力在于「你队友还剩几张」。v1.16 的实现（出完即进 `out`、等队友也出完）只是
> 这条规则的一个特例（队友恰好只剩 1 张时的分支）。
>
> 第二处是**两张专属黑牌可以做**（[5] 只说有这两张，[28] 给了逐条效果）：
> - **Wild Team Play**：选色 → 回合**直接跳到队友**；他出得了就接着打，
>   **出不了就罚出牌者摸 2 张**（罚的是打牌的人，不是队友）。
> - **Wild Team Draw Four**：下家摸 2 停一轮，**他的队友也摸 2**
>   （原文括号：「even if they are currently out of the game」—— 场外的也照样摸）。
> - ⚠️ **张数是本作定的**（官方只写效果不写张数，同 No Mercy 那 56 张的处境）：
>   各 2 张。两张都是强力且单向的，4 张会让组队档退化成「谁摸到谁赢」。
>
> **仍然不做：「Passing Symbol」传牌牌。** 原文只有一句「You will notice some cards
> have a Passing Symbol on them. When you play a card with a Passing Symbol, you and
> your teammate both pass each other 1 card.」—— **哪几张牌带这个符号，说明书
> 一个字都没写**（那是实体牌面上印的），而「两人各传一张给对方」还要一个新的
> 「选哪张传」状态（同 7 换手的选人框）。**凑不出定稿规则就不做** ——
> 这条与 v1.16 拒绝第 3 条是同一条纪律，只是这次的缺口在「哪几张」而不是「怎么结算」。
>
> 人机的「配合」这一轮仍然只做了**不坑队友**（换手不选队友）+ **替队友喊 UNO**
> （`call_uno` 不传 `target` 时由引擎决定替谁喊，人机走同一条路）。
> 更细的配合（给队友留牌、盯住对手手牌最多的那个）与批次 D 一起排。

**批次 D（远期）—— 累计 500 分赛制**：需要房间级跨局状态，与「单局定胜负」模型冲突最大。

## 6. 已知坑与风险（逐条）

1. **抢出与 `drawn_this_turn` 正面冲突（真坑）**：A 摸完牌还没过牌时 B 抢出，
   若不处理，A 的 `drawn_this_turn` 还指着那张早已不在手里的牌 →
   `playable_cards` 返回 `[]` → **A 从此出不了任何牌**。
   修法：抢出成功时清掉**所有座位**的 `drawn_this_turn`。
2. **抢出的并发**：两人同时抢同一张 → 服务端单循环天然串行，但**抢输的人必须收到明确提示**，
   不能静默（本项目铁律）。回归要放在 WS 层。
3. **7 换手后手牌整体易主**：同样要清 `drawn_this_turn`；客户端的可出高亮与扇形布局要整体重排
   （别逐张 animate）；`hand_counts` 会瞬间跳变，座位条要能平滑跟上。
4. **`playable` 的语义分裂**：抢出开启后「能出的牌」≠「轮到我出的牌」。
   必须新增 `jumpable`（我此刻能抢出的牌），且客户端要用**第二通道**（徽标 + 文案）区分 ——
   否则玩家分不清「轮到我了」和「我可以抢」。
5. **淘汰赛的排名语义要跟着改**：`compute_ranking` 现在把「出完手牌的人」排第一；
   `last_standing` 下第一名是**最后剩下的人**，「出完牌」反而是**被淘汰**。
   `snapshot` 与 `HistoryScreen` 的回放也要一起改，否则战绩页会显示「最先出完的人赢了」。
6. **Mercy 判定的位置**：必须在**每次发牌之后**（罚牌 / 摸牌 / 换手都算）且**在 `_advance` 之前**，
   否则刚被淘汰的人还会轮到他。
7. **引擎不认识时间（架构纪律）**：`抓 UNO 罚` 的窗口必须是**事件窗口**
   （「从他变成 1 张、到他下一次出牌之前」），**不许**引入 `asyncio.sleep` 或墙钟。
   UNO 现在没有 tick，别为了这条规则引入 tick —— 这与深空休眠「引擎只认识 `dt_ms`」是同一条纪律。
   顺带：**这条推翻了 `设计.md`「已知取舍」里「不做抓 UNO」的理由**（原文是「没有仲裁与计时协议」），
   其实服务端全程知道谁有几张牌、谁喊过，**仲裁完全不需要人**。
8. **`+4` 严格化的连带**：`wild4_strict` 开启后要定义清楚它与叠加的关系。
   No Mercy 口径是「叠加只看等值或更高，不看合法出牌条件」[8]；
   两种口径混用会出现「被 +4 罚、手里有 +4 却出不了」。
9. **人机是隐藏成本**：每个开关都会改变最优解（有叠牌要留 +2 反击、有 7-0 要换给手牌最少的人、
   淘汰赛要盯手牌最多的、组队要帮队友）。且**任何被引擎拒绝的动作，在「一次决策一个动作」下
   就是死循环**（深空休眠 v2/v8 两次踩过）。人机的抢出判定要走同一条 `rm.uno_play_action`。
10. **`auto_pass` 与新模式**：淘汰赛下断线者会被 Mercy 快速淘汰，这是可接受的，
    但要确认 `uno_should_autopass` 的「全员断线就停手」护栏仍然成立。
11. **模式名与说明的服务端下发**：档位表、每条房规的中文名与说明都由服务端给，
    客户端不抄 —— 项目踩过「游戏名散在七处、改名漏一处就是两个名字」的坑。
12. **`help.tsx` 文案必须与引擎口径一致**：帮助里写「+2 只能叠 +2」而模式开了 `upgrade`，
    玩家照着打会被拒。帮助要按当前档位给文案。
13. **热重启**：`rules` 是 str 键 dict，`persistence.py` 的编码器天然能过；
    但 `teams` / 累计分进 `game_state` 后要补一条热重启回归。
14. **测试**：`test_uno.py` 的自对弈模糊测试（牌总数 108 / 必然终局 / 动作必须被引擎接受）
    **必须按每个预设各跑一遍** —— 这是新规则最有效的回归网。

## 7. 采纳 / 不采纳清单

### 采纳

| 方案 | 理由 |
|---|---|
| **房规表 + 命名预设 + 房间级选择** | 基础设施；与 `luzhanqi_pick` / `bs_size` 同构，无新概念 |
| **等值或更高叠加**（No Mercy 口径） | 比「同型叠加」更有张力，且是官方现行产品 [8] |
| **摸到能出为止** | 一行循环，但彻底改变牌局节奏；是 No Mercy 的核心张力来源 [8] |
| **抢出 Jump-in** | 官方有独立产品 [1]；**唯一一条非本回合规则**，戏剧性最强，引擎改动极小 |
| **7-0 换手** | 官方与数字版都列在房规清单首位 [12][16]；**唯一会手牌整体易主的机制** |
| **+4 严格化 + 可挑战** | 服务端知道手牌，判定是确定的，**不需要仲裁人**；撤销的是一条早已记在「已知取舍」里的简化 |
| **抓 UNO 罚摸 2 张** | 同上，仲裁不需要人；窗口用事件而非时间（见风险 7） |
| **No Mercy 牌堆 + 25 张 Mercy + 最后一人存活** | 社区热度最高的一档 [7][8][9]，且「出完牌的人出局」在本作**几乎是免费的**——`surrender` 已经实现了「只出局、牌局继续」，`_check_game_over` 也已经处理了只剩一人 |
| **2v2 组队** | 官方手游的主打模式之一 [11]，用户量最大的一档 |
| **Force Play / 强制出牌** | 各一行判据，作为「自定义」里的开关，不单独成档 |

### 不采纳（含理由，避免下次重新评估）

| 方案 | 不采纳的理由 |
|---|---|
| **UNO Flip（双面牌堆）** | 牌堆规模翻倍、美术翻倍、客户端要处理「整局翻面」的全局状态；收益主要是新鲜感，成本是批次 B 的两三倍 |
| **UNO Attack（发牌机）** | 物理外设，没有对应机制价值；「随机数量的罚牌」用「颜色轮盘」表达即可 |
| **Ring Royale 式锦标赛 / 多桌晋级** | 需要匹配、赛季、跨房状态，本项目基础设施全无 [14] |
| **自定义规则卡（Add-a-Rule）** | 需要玩家自由输入规则文本，无法程序化裁决 |
| **颜色数量 / 数字范围可变**（Foon-o [17]） | 会破坏牌面美术体系与「UNO」的识别度，收益低 |
| **回合计时器** | 与 13 个游戏的全局约定冲突（都靠 120s 断线保座）；「快节奏」用起手牌数表达 |
| **Sequences / Uno from Hell**（同色连出、任意功能牌互叠 [21]） | 前者需要「抢在别人出牌前连续操作」的实时窗口，与本作回合制模型冲突；后者会让牌局退化成纯运气 |
| **累计 500 分** | **不是不采纳，是排到最后**（批次 D）：需要房间级跨局状态，与「单局定胜负」模型冲突最大 |
