## 跨游戏通用设计规范

以下是全部对局屏共同遵守的规则，各游戏文档不再重复。括号里的数字是落地到
本项目的**实际取值**，改样式前先看这一节。

> 这些规则背后的**方法论**（响应时间预算、触控生理限制、确认弹窗的分级、
> 颜色无障碍、渐进式披露等，含外部研究出处）单独沉淀在
> [../移动端体验设计方法论.md](../移动端体验设计方法论.md)——不限于棋类游戏，
> 做任何移动端界面都用得上。

### 触控目标尺寸

各家规范给的最小值并不一致，取最严的落地：

| 来源 | 最小值 | 单位 |
|---|---|---|
| Apple HIG | 44 × 44 | pt |
| Material Design 3 | 48 × 48 | dp（约 9mm 实体尺寸） |
| WCAG 2.2 AA (2.5.8) | 24 × 24 | CSS px（含间距豁免） |
| WCAG 2.1 AAA (2.5.5) | 44 × 44 | CSS px |
| Nielsen Norman Group | 1 × 1 | cm（实测防误触经验值） |

落地情况：

- 操作按钮（认输/退出/掷骰/布阵）统一 `paddingVertical: spacing.sm + 6`（≈47px 高）；
  2048 方向键 48×48；**改按钮样式时不要把这些值调小**。
- 棋盘类控件受物理尺寸限制做不到 44pt/格，靠**第二条输入路径**补偿：
  - 五子棋 15×15 每格约 25px → 长按浮出**放大镜**拖动精瞄；另加**落子二次确认**
    （首点只放半透明预览子，再点同一处才落子），误触的撤销成本为零
  - 点格棋 4×4 每格约 89px，边线是细长目标 → 热区 `HIT_PAD = 20`
    （垂直于边方向 2×20 + 3 = **43px**，接近 HIG 的 44）
  - 扫雷**已经不再靠补偿**：格子固定 44px、棋盘双向滑动（v1.7.2）。
    这是「物理尺寸受限」被解除后的正解——能滑动就不该缩格子
  - 海战棋 10×10 每格约 30px → 竖屏单棋盘 + 分段切换，仍低于 44pt（待优化）
  - 飞行棋格宽按可用空间推导（`CELL = floor(min(w,h)/15)`），约 22-25px
  - 中国象棋 9 列交叉点每格约 **39px** → 用**两步落子**补偿：先选子、再点落点，
    误触只换选中、不会误走一步（撤销成本为零，比放大镜更适合「点—点」的棋类）
- 手势类操作（2048 滑动、五子棋拖动）以**整块棋盘**为热区，不受格子尺寸限制——
  这是小棋盘游戏最有效的补偿手段。

### 动效时长（有研究依据，不是拍脑袋）

- **直接操作触发的反馈**要 < 100ms 才感觉是「瞬间响应」（人一次眨眼约 100-150ms）。
- **小元素的轻微变化**（渐隐渐现、缩放）200-300ms；**大范围缓动位移**可到 400-500ms。
- 间接触发（切页、弹窗）可到 1s；**超过 2s 必须有 loading**，超过 10s 要有进度指示。

本项目取值（都偏快，符合「直接操作」定位）：

| 动效 | 时长 | 位置 |
|---|---|---|
| 2048 方块滑行 | 110ms | `Game2048Screen` `SLIDE_MS` |
| 2048 合并/新块弹跳（单程） | 100ms | `POP_MS`（1 → 1.18 → 1） |
| 飞行棋逐格移动 | `clamp(600/steps, 55, 115)`ms | `ludoBoard.stepDuration` |
| 飞行棋被撞回基地 | 260ms | `LudoScreen` `CAPTURE_MS` |
| 五子棋落子弹入 | 120 + 60ms | `GomokuScreen` `PopInStone` |
| 震动单脉冲 | 10-30ms | 业界建议 < 150ms |

缓动用 `Animated.timing` 默认的 `easeInOut`；弹簧感（落子、翻转）用
`Animated.spring`。**只用 `transform` 与 `opacity`**，这样能开原生驱动
（`useNativeDriver: Platform.OS !== 'web'`——RNW 不支持，必须降级）。

**脉冲类动效一律限次，不做无限循环（WCAG 2.2.2）。** 自动播放且持续超过 5 秒的
运动必须能暂停/停止；这里用「限次」代替「加暂停按钮」——脉冲的用处是把注意力
拉回屏幕，拉回来了就该停。五子棋回合脉冲 3 轮（1.6s/轮）、胜利脉冲 2 轮（2s/轮），
都压在 5s 内，停在高亮态而非熄灭态。

### 颜色与无障碍

- **WCAG 1.4.1：不能只靠颜色传达信息。** 本项目：
  - 2048 排行榜每行是「颜色点 **+ 昵称 + 名次数字**」，颜色只是辅助
  - 点格棋归属格是「半透明色块 **+ 顶部比分数字**」；封格提示边是「琥珀色 **+ 线宽加倍**」
  - 飞行棋飞机是「颜色 **+ 位置**（基地/轨道/航道）**+ 白色飞机图案**」；可动棋子是「深墨环 **+ 放大一档**」；虚线捷径是「深墨虚线 **+ 白色垫底 + 箭头**」（会横穿三种底色，单色描边总有一种看不清）
  - 海战棋命中/未命中是「图标与形状（着火/水花）」，不只是红蓝
  - 四个棋类的「最近一步」标记统一是「黄点 **+ 深墨描边**」（`lastMoveMark` /
    `lastMoveMarkEdge`，单色压不住黑子/白子/木色/绿底四种底）。位置各按棋盘特点放：
    五子棋/翻转棋在棋子中心、点格棋是画在边上的黄晕、象棋在棋子右上角（中心是汉字，会挡住）
  - 扫雷的剩余命数是「心形图标（实心/空心）**+ 剩余/总数数字**」，不是只变个颜色
- **对比度阈值**：正文 ≥ 4.5:1，大字（≥18px，或 ≥14pt 粗体）≥ 3:1，UI 组件与图形 ≥ 3:1。

**配色只有 `app/src/theme.ts` 一个来源。** 每个颜色的注释里写着实测对比度——
改色后**必须重算并更新注释**，别凭感觉挑色。饱和色同时要满足两个方向
（白字压在它上面 ≥4.5、它作为文字压在浅底上也 ≥4.5），这就是
`warning` / `success` 比常见取值深一档的原因：

| 令牌 | 值 | 实测 | 说明 |
|---|---|---|---|
| `danger` | `#DC2626` | 白字 4.83 | 原 `#EF4444` 白字只有 3.76 |
| `warning` | `#B45309` | 白字 5.02 | 原 `#F59E0B` 白字只有 2.15（曾用于「未准备」按钮） |
| `success` | `#047857` | 白字 5.48 | 原 `#10B981` 白字只有 2.54（曾用于「准备」按钮） |
| `textSecondary` | `#4B5563` | 7.56 | |
| `textMuted` | `#6B7280` | 4.83 | **可承载信息的最低一档** |
| `textFaint` | `#9CA3AF` | 2.54 | **仅占位符 / 禁用态 / 纯装饰**，禁止承载信息 |
| `border` | `#E5E7EB` | 1.24 | 仅作分隔线；**控件边界必须用 `borderStrong`**（3.19） |

配套的单一来源还有：`playerColors`（蓝/红/绿/黄四家身份色）、`ludoColors`、
`battleshipShipColors`、`g2048Tile()`、`withAlpha()`。**不要在屏幕里写死 hex**——
曾经出现过「引擎叫 black/white、棋盘画蓝红、文案写黑白」的三方错位，
以及同一个棋盘绿在两个文件里写成 `#2E7D32` / `#157A46`。

### 「最近一步」标记（四个棋类共用一套）

五子棋 / 翻转棋 / 点格棋 / 中国象棋都要把**最近一步**标出来——棋类游戏里
「对方刚走了哪儿」是每一步都要重新确认的信息，不标出来玩家得自己比对前后画面。

统一取 `theme.ts` 的 `lastMoveMark`（黄）+ `lastMoveMarkEdge`（深墨描边），
**位置按棋盘特点各放各的**（中心 / 边上 / 右上角），但「黄 = 最近一步」这条
语言在四个游戏里一致。

- 黄点单独用在这几个游戏的**所有**背景上都不达标（vs 白子 1.29:1、vs 木色棋盘
  ~1.9:1、vs 绿底 3.63:1），描边是让它成形的必需通道。
- 新增棋类时**不要**另挑一个颜色——换个颜色就等于换了一套语言。
- **踩坑**：翻转棋与点格棋的标记代码/渲染一直在，但 `handleMove` 没往
  `prev.moves` 追加，数据链路是断的，标记从来没显示过。加「最近一步」类需求时
  先确认客户端到底有没有在维护 `moves`。

### 反馈与手感

- **按下即高亮**：全部用 `TouchableOpacity` 的 `activeOpacity`，在手指按下时
  给出可视按压态（HIG 明确要求「在手指按下时而非抬起时高亮」）。
- **震动**：只在对局内动作上触发，单次 10-30ms。落子/开炮 10ms、命中/击沉 15ms、
  轮到己方 30ms。Web 端一律不震动。
- **动效只用于「值得注意的事件」**（落子、合并、撞机、胜利），不做常驻装饰。
- **手势不能被浏览器抢走**：Web 端参与自定义手势的元素加
  `touch-action: none`，并让 `onPanResponderTerminate` 与 release 走同一套判定
  （见 [2048 的设计文档](2048/设计.md) 的三个坑）。

### HUD 信息布局

- 顶栏：我方身份 + 回合提示（左），帮助按钮 + 房间号（右）。
- 分数/排名：按 scorebug 惯例放在视觉上方，但**小屏上不能占布局高度**——
  2048 的实时排行榜做成了右上角可收起的半透明浮层（浮层必须
  `pointerEvents="none"`，否则会截断棋盘上的滑动手势）。
- 危险操作（认输/退出）一律在底部，且**必须二次确认**。
- 道具/操作按钮尽量落在**拇指可达区**（屏幕下半部）；单手竖屏是主要形态。

### 让用户在等谁、等什么，一眼可见（含倒计时）

- **人机回合有 0.8-1.2 秒的服务端思考延迟**（故意留的节奏）。只写「等待对方…」
  用户既不知道在等谁、也不知道要等多久，会以为卡住了——所以对手是人机时文案改成
  `XX 思考中…`（`is_bot` 由服务端下发，房间名单里也有「人机」徽标）。
- 「对方已断线，等待重连（N 秒）」把**剩余时间和后果**都写出来，比「连接中…」有用。
  这里的 N 是**真倒计时**（每秒递减，归零即判负），不是写死的文案——静态的「120秒」
  摆在那儿一动不动，用户反而会怀疑页面是不是卡死了（v1.7 起改为服务端下发秒数 +
  客户端 `useDisconnectCountdown` 递减）。**秒数一律由服务端给**：超时是服务端配置，
  测试还会把它调成 5 秒，客户端写死就对不上实际判负时间。
- **正常但无效果的操作不要报错**：2048 往走不动的方向滑是正常操作，静默忽略即可
  （早期会弹提示框）。用户做错事了才提示。

### 房间与对局状态（v1.5.1 起）

- 房间状态**只有两种**：等待中（`waiting`）/ 游戏中（`playing`）。对局结束即回到
  等待中（`round` 自增），可续开、可加入；没有「已结束」这第三种状态。
- **掉线只在游戏中存在**：游戏中掉线保留座位 120 秒；等待房掉线不显示「断线」
  （玩家不会被立即移出，留 60 秒宽限期给「从对局页返回房间」的重连）。
- 结算弹窗只有「返回房间」，续开新局统一回大厅由房主点「开始游戏」。

### 禁止事项（会导致原生端崩溃或体验事故）

- 禁用 `window.confirm/alert/prompt`（原生端无此 API，1.1.x 白屏事故）。
- 禁用裸 `window.addEventListener`，Web 专属逻辑收口到 `backGuard` 的
  `onConfirmLeave`（1.3.1 APP 五子棋白屏事故）。
- UI 文案禁用 emoji（SVG 图标内的 `<Text>` 属矢量美术，不受此限）。
- 破坏性操作按钮不得直接执行，必须走 `useModalBackGuard` 接管的确认弹窗。
- SVG 图形的 `cx/cy` 不要做动画（必须 `useNativeDriver:false` 且写法不一致）；
  要动的元素放到绝对定位的 `Animated.View` 覆盖层，动 `transform`。
