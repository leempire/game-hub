# 移动端体验设计方法论

写这份文档的起因：给 GameHub 各游戏做交互优化时查了一圈资料，发现「怎么做」的
结论背后有一套「为什么」——响应时间、触控生理限制、确认弹窗的边际效用、
颜色无障碍等，都是有研究或标准支撑的，不是审美偏好。这些方法论不限于棋类游戏，
做任何移动端产品都用得上，所以单独沉淀一份。

**怎么用**：动手改交互前先扫一遍第 1、2、6 节（这三节最容易踩坑）；设计新界面时
用第 10 节的自查表过一遍。

---

## 1. 响应时间：把「多久算快」变成可计算的预算

用户感知的不是「动画好不好看」，而是「我操作之后多久看到变化」。业界把这段时间
切成三段（Nielsen 引用 Robert B. Miller 的研究）：

| 阈值 | 用户感受 | 设计要求 |
|---|---|---|
| **0.1 秒** | 感觉是「瞬间」，像是自己动作的一部分 | 直接操作触发的反馈必须在此内（按下高亮、选中态） |
| **1 秒** | 用户进入「心流」，专注等结果，但流畅感开始断 | 间接触发的反馈（切页、弹窗）允许到 1 秒 |
| **10 秒** | 超过 2 秒用户就觉得「失去控制」 | >2 秒必须给 loading，>10 秒要给**进度指示** |

100ms 这个数字来自「人一次眨眼约 100-150ms」——比眨眼还快的变化，大脑会把它
归入「我的动作」而不是「系统的回应」。

### 落地含义

- **按下即反馈**，不要等操作完成才高亮。按钮要从手指**按下**那一刻变色，
  而不是抬起时（Apple HIG 明确要求）。
- **乐观更新**：网络请求类操作，本地先更新界面再等服务端确认。本项目战绩/房间
  列表是轮询 + 拉取，对局内动作是纯服务端权威 → 所以走子必须靠"服务端广播回来
  再动"，此时**动画要盖住网络往返的空白**（见下一条）。
- **别让用户盯着静止的界面等**。本项目对局屏的「等待对方…」文案就是一种最低
  限度的状态可见性；人机回合的 0.8-1.2 秒延迟如果没有提示，用户会以为卡了。

## 2. 动效：时长按「元素大小」定，不按「好看」定

Material Design 给出的经验规律（本项目实测后沿用）：

| 变化的规模 | 建议时长 | 例子 |
|---|---|---|
| 小元素的轻微变化 | **200-300ms** | 渐隐渐现、图标缩放、选中态 |
| 大范围的复杂位移 | **400-500ms** | 整块面板滑入、翻页 |

gameanimation.info 的补充观点：**时长应该随元素尺寸变化**——大元素移动同样的
距离，用同样的时长会显得「太快、像瞬移」；小元素用大时长则显得拖沓。

### 几条容易被忽略的规则

1. **直接操作的动效要比默认值更快。** 上表是「界面动画」的通用区间；用户手指
   直接操控的对象（拖拽、滑动、落子）要压到 100-150ms，否则手感发黏。
   本项目：2048 方块滑行 110ms、合并弹跳单程 100ms、飞行棋逐格 60-130ms。
2. **只用 `transform` 和 `opacity` 做动画。** 它们能走 GPU 合成 / 原生驱动，
   改 `width/left` 会触发布局重算。Web 端 `useNativeDriver` 不支持，要降级
   （`Platform.OS !== 'web'`）。
3. **缓动不是可选项。** 匀速运动在物理上不存在，看起来"假"。进场用 ease-out
   （快起步慢收尾），退场用 ease-in。想要"弹"的手感用弹簧（spring）而不是
   硬编码的几段 timing。
4. **动效只标注「值得注意的事件」**：落子、合并、命中、撞机、胜利。常驻装饰性
   动画会消耗注意力预算，还会让真正重要的反馈淹没在噪声里。
5. **间隔要够**：同一批元素依次入场时错峰 20-50ms 即可；间隔太大整体会显得慢
   （本项目翻转棋的连锁翻转错峰曾被记为"略慢"）。
6. **超过 5 秒的自动动画要能暂停/停止**（WCAG 2.2.2）。

## 3. 触控：手指不是鼠标

### 3.1 目标尺寸

各家标准不一致，取最严的：

| 来源 | 最小值 | 说明 |
|---|---|---|
| Apple HIG | 44 × 44 pt | iOS/iPadOS 官方 |
| Material Design 3 | 48 × 48 dp | 约 9mm 实体尺寸 |
| WCAG 2.1 AAA (2.5.5) | 44 × 44 CSS px | 高无障碍等级 |
| WCAG 2.2 AA (2.5.8) | 24 × 24 CSS px | 底线，允许间距豁免 |
| Nielsen Norman Group | 1 × 1 cm | 实测防误触经验值 |
| 车载场景 | 76 × 76 dp | 需要"扫一眼就能点中" |

**棋盘类界面做不到 44pt/格时怎么办**——这是本项目反复遇到的问题，四条出路：

1. **加一条输入路径**：五子棋格宽只有 25px，靠「长按浮出放大镜 + 拖动精瞄」补偿。
2. **放大热区而非视觉**：点格棋的边只有 3px 粗，热区做到 43px（视觉不变）。
3. **整块棋盘当热区**：2048 的滑动、五子棋的拖动，手势不受格子尺寸限制——
   这是小棋盘游戏最有效的补偿手段。
4. **分开显示**：海战棋两块 10×10 盘叠在一起每格只有 30px，改成竖屏单盘 +
   分段切换可以把格子放大一倍。

### 3.2 拇指可达区（竖屏单手是主要形态）

- 主操作（主要按钮、常用 Tab）放在**屏幕下半部**，次要与危险操作放上半部或角落。
- 危险操作（认输/删除/退出）天然应该"不那么好按"——远离拇指反而降低了误触。
- 本项目做法：认输/退出固定在底部但必须二次确认；帮助按钮放顶栏右上角。
- 参考同类产品：移动端海战棋普遍是"竖屏单手布局 + 拖放布阵"，比"选船→点格→
  旋转"少两步。

### 3.3 手势的可见性

手势的问题在于**不可见**：用户不知道它存在就不会用。三条缓解：

- **给可见的替代路径**。本项目 2048 = 滑动 + 方向键；扫雷 = 长按/右键 + 模式切换
  按钮。手势是"快捷方式"，不是唯一入口。
- **在手势发生处给反馈**。五子棋长按浮出放大镜，用户立刻明白"按住可以精瞄"。
- **不要给同一手势两种含义**。扫雷若同时支持"长按插旗"和"长按放大镜"，用户
  无法预测长按会做什么——所以本项目的插旗是模式切换，不是长按。

### 3.4 Web 特有坑：手势会被浏览器抢走

移动浏览器会把某些手势当作**浏览器手势**处理（横滑返回、边缘返回、页面平移），
一旦浏览器决定接管，它会发 `touchcancel` **取消整条触摸序列**——自定义手势连
"松手"事件都收不到，表现就是"划到一半没反应"。

处理办法（本项目 2048 踩过）：
- 参与自定义手势的元素加 `touch-action: none`（仅 Web，告知浏览器别碰这块）。
- 应答器在**捕获阶段**就抢下手势（`onStartShouldSetPanResponderCapture`）。
- 拒绝移交（`onPanResponderTerminationRequest: () => false`），并让
  `onPanResponderTerminate` 与正常松手**走同一套判定**——被取消时至少还能
  按已累积的位移做判断。
- 覆盖在可交互区域之上的浮层要么 `pointerEvents="none"`（纯展示），要么用
  `box-none`（自身透明、子元素可点）。否则它会在指针经过时截断下层手势。

## 4. 多通道反馈：视觉 + 触觉 + 听觉

同一件事同时给两个通道，确认感明显更强（"震动 + 音效 = 命中"）。

### 触觉（震动）

- **单脉冲 < 150ms**，超了会变成"打扰"而不是"提示"。
- **每个震动都要有明确目的**：确认关键动作（落子、命中）或预警。随机震动
  只会让人困惑，用多了让人烦躁。
- **和视觉同时发生**，不要先震后画。
- 强度匹配事件量级：轻推用轻震，命中用重震。
- **不要给桌面/网页端震动**（无意义且无法感知）——本项目 `Vibration` 只在原生端调。

### 本项目取值

| 事件 | 震动 | 依据 |
|---|---|---|
| 落子 / 开炮 | 10ms | 常规动作，确认即可 |
| 命中 / 击沉 | 15ms | 需要强调 |
| 轮到己方 | 30ms | 把注意力拉回屏幕 |

## 5. 状态可见性：让用户永远知道"现在发生了什么"

Nielsen 第一条启发式。移动端的常见缺口：

- **操作性状态**：按下有没有生效？提交中是卡住了还是没点？——按钮要有 loading
  态（尤其耗时 >1s 的操作），并禁用重复点击。
- **系统状态**：网络断了、对方掉线了、对手在思考——要明说。本项目对局屏的
  「对方已断线，等待重连（120秒）」把**剩余时间和后果**都写清楚了，比一个
  "连接中…" 有用得多。
- **进度**：>2 秒给 loading，>10 秒给百分比或步骤（"第 2/5 步"）。
- **别用静默失败**：操作被拒绝一定要有反馈。反例：2048 往走不动的方向滑，服务端
  返回"无效移动"，早期会弹一个提示框——但"滑到墙"是正常操作，不该报错；现在
  改成静默忽略。**规则是：用户做错事了要提示，用户做了正常但无效果的操作不要吵。**

## 6. 防错与容错：确认的分级，而不是一刀切

这是最常被做错的一节。**给所有破坏性操作都加"确定吗？"是反模式**——弹窗太频繁，
用户会训练成不看内容直接点确定，等真正危险的确认出现时它也失效了（狼来了）。

### 摩擦应该与「后果的不可逆程度」成正比

NN/g 与业界实践总结出的**摩擦阶梯**：

| 级别 | 手段 | 适用 |
|---|---|---|
| 0 | 直接执行 + 提供**撤销** | 可逆的日常操作（归档、移动） |
| 1 | 轻确认（可一键撤销的 toast） | 删除单条可恢复的记录 |
| 2 | 普通确认弹窗 | 会中断当前任务但不丢数据的操作 |
| 3 | **写明后果**的确认弹窗 | 认输、退出对局、解散房间 |
| 4 | 输入名称才能确认 | 删除整个工作区、清空全部数据 |

设计确认弹窗时的四条要点（NN/g）：

1. **只在后果严重或不可逆时用**，日常操作不用。
2. **写明会发生什么**，不要写"你确定吗？"。用户应该能从文案里**认出自己是不是
   点错了**。本项目：「认输后本局判负，无法撤销」比「确定认输？」有用得多。
3. **按钮用具体动词**，不用「是 / 否」。「确认认输 / 再想想」比「确定 / 取消」清楚。
4. **优先提供撤销**，撤销比确认更不打断用户（`user control and freedom`）。

### 防错比容错更省事

- 按钮到该能用时才可用（未满足条件就禁用 + 说明原因）。本项目「开始游戏」
  在人数不够/未准备时置灰。
- 危险操作**远离**高频操作，不要在同一个位置。
- 输入校验前置且实时（注册页的用户名规则）。

## 7. 渐进式披露：一次只教一件事

新手引导失败的最常见原因是**信息前置**：一打开 App 就是功能介绍、权限申请、
注册、付费墙，用户还没做任何有意义的事就被淹没了。NN/g 的建议是**简短、可选、
只给最小必要信息**；业界普遍建议把首启流程压到 **3-7 步**，并聚焦"第一个有意义
的动作"。

### 游戏场景的具体做法（Apple 开发者文档）

- **教"核心循环"而不是全部系统**：核心循环是反复发生的基本活动（打怪→金币→
  买装备），先教这个，其他慢慢来。
- **在玩中学，不要在文本里学**：把教学嵌进玩法，而不是先弹一段说明。
- **分成多个短教程**：机制多就拆成多个小教程，各自只引入一个新概念（《皇室
  战争》拆成 5 个），后面的教程基于前面已掌握的技能。
- **允许跳过**：老手可能只想马上开始（《卡卡颂》会问"要继续还是稍后看规则"）。
- **不重要的信息放到引导之后**。

### 落到本项目的形态

游戏规则帮助系统（`help.tsx`）就是这个思路：规则**不在开局时弹**，而是做成
「大厅/房间/对局中随时可查」的按需面板——想学的人随时能查，不想看的人一点
不被挡。每个游戏的帮助文案也按「玩法概述 / 操作 / 胜负 / 小技巧」分层，
而不是一大段。

## 8. 一致性与心智模型

- **平台一致性**：返回、Tab、导航的行为要和系统一致。本项目为此专门做了
  `backGuard`——返回键的优先级（弹窗 > 对局确认 > 主 Tab 双击退出）是**用户
  已有心智模型**，不能各屏各写。
- **内部一致性**：同类控件在全部界面表现一致。本项目把"按钮高度 ≈47px"
  "危险操作二次确认""同一个 testID 命名法"都写进了规范，就是为了这个。
- **命名一致性**：同一个东西永远用同一个词。反例：点格棋引擎里叫 `black`/
  `white`，界面渲染成蓝/红，文案一度跟着引擎写成"黑方胜"——用户看到的是蓝红，
  读到的却是黑白。**命名与呈现不一致，迟早会以 bug 的形式暴露。**
- **贴近现实世界**：用用户的语言而不是系统的语言。飞行棋的"掷骰子"而不是
  "roll_dice"；错误提示说"房间密码错误"而不是"401"。

## 9. 无障碍：不只是"少数人的需求"

无障碍的很多要求，本质上是**给所有人降低认知负担**。

### 颜色

- **WCAG 1.4.1：不能只靠颜色传达信息。** 色盲人群约占男性 8%，红绿区分是重灾区。
  做法：颜色永远配一个第二通道——文字、图标、形状、位置。
  - 2048 排行榜：颜色点 **+ 昵称 + 名次数字**
  - 点格棋归属：半透明色块 **+ 顶部比分数字**
  - 飞行棋：颜色 **+ 位置**（基地/轨道/航道）
  - 海战棋：命中/未命中是**形状**（着火/水花），不只是红蓝
- **对比度**（WCAG 1.4.3 / 1.4.11）：
  - 正文 ≥ **4.5:1**
  - 大字（≥18px 或 14px 粗体）≥ **3:1**
  - UI 组件与图形（边框、图标、焦点环）≥ **3:1**
- **不要用高对比闪烁**做提示（WCAG 2.3.1 对闪烁频率有限制）。

### 其他

- 触控目标可放大（WCAG 1.4.4 文本可缩放 200% 不丢功能）。
- 动态内容可暂停（>5 秒的自动动画）。
- 表单错误要**指出是哪个字段、错在哪、怎么改**（WCAG 3.3.1/3.3.3）。
- 别把重要信息只放在 hover / 长按里——触屏没有 hover。

## 10. 信息设计：界面本身就是说明书

对棋盘游戏尤其成立——**图形不是装饰，是接口**。棋盘游戏没有引擎来动态提示，
所有信息都要靠静态组件在一次扫视里读出来。

- **图标系统胜过图标堆**：一套统一的视觉语言能让用户不读文字就懂。
- **一次扫视可读**：字号、对比、留白都是为了让"扫一眼"能完成信息获取。
- **把规则画出来**：可落子提示、可动棋子高亮、危险格标记——能画出来的规则
  就不要靠文字解释。
- **层级分明**：主信息（棋盘、分数）永远最大最亮，辅助信息（房间号、帮助）
  退到边上。

## 11. 自查表

改交互时按顺序过一遍：

**时间**
- [ ] 直接操作的反馈在 100ms 内出现（按下即高亮）
- [ ] 界面动画：小元素 200-300ms，大位移 400-500ms；手指直接操控的对象 100-150ms
- [ ] 危险操作不用过场动画拖延
- [ ] >2 秒给 loading，>10 秒给进度；任何等待都有文字说明在等什么

**触控**
- [ ] 主要控件 ≥44×44pt（Android ≥48dp），做不到的至少 24×24 且有间距
- [ ] 小目标有第二条输入路径（放大镜 / 方向键 / 整块区域当热区）
- [ ] 手势有可见替代入口，且不同手势不冲突
- [ ] Web 端自定义手势元素加了 `touch-action: none`，并能处理被取消的情况
- [ ] 覆盖在可交互区上的浮层设了 `pointerEvents`（`none` 或 `box-none`）

**反馈**
- [ ] 每个操作要么有结果，要么有"正在处理"
- [ ] 正常但无效果的操作不报错（滑到墙不算错误）
- [ ] 震动 <150ms、有明确目的、只在原生端
- [ ] 反馈多通道：视觉为主，触觉/听觉补充

**防错**
- [ ] 破坏性操作按不可逆程度分级加摩擦，不是一律弹窗
- [ ] 确认弹窗写明**后果**，按钮用具体动词
- [ ] 能撤销的优先给撤销，而不是确认
- [ ] 条件不满足的按钮禁用并说明原因

**一致与无障碍**
- [ ] 同一控件在所有界面表现一致；返回行为符合系统心智模型
- [ ] 命名与呈现一致（内部叫 black 就不能给用户看"黑"）
- [ ] 颜色不是唯一的信息通道；正文对比度 ≥4.5:1、大字与图形 ≥3:1
- [ ] 文案用用户的语言，不用系统/代码的语言
- [ ] 新功能不做信息前置，帮助按需可查、可跳过
