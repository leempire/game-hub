# 好友与聊天

v1.23.0 发布准备：账号级好友与文字私聊，与局内快捷语及观战独立。

## 使用方式

底部导航顺序为「游戏 / 房间 / 社交 / 我的」。社交页提供消息、好友和申请入口；输入对方**完整登录用户名**查找，发送申请，经对方确认后成为双向好友并可文字私聊。收到的申请可接受或拒绝，发出的申请可取消。好友列表支持进入聊天、删除好友和拉黑；可管理并解除自己的拉黑。

文字消息保存到服务器，重新登录、换设备或服务重启后仍可读取。聊天前台自动刷新，支持加载更早记录、未读数和已读回执。停留底部时跟随新消息，上翻阅读旧记录时保留位置且不自动读掉新消息；点「回到最新消息」可恢复跟随。输入最多1000字；发送失败保留内容，同一次发送重试使用原标识，避免网络超时造成重复消息。社交导航角标合计未读消息与收到的申请。

页面失焦、退出账号或应用进入后台后停止轮询，不将后台消息自动标为已读。列表每3秒、底栏摘要每5秒、聊天每2秒刷新，请求10秒超时，旧会话返回不会覆盖新会话。再次打开会补取消息和未读状态。当前是前台自动刷新的好友文字私聊，不依赖系统推送。

网页 `/social` 对应社交入口，`/chat/{用户ID}` 可直接进入对应好友聊天；好友聊天链接在未登录时先登录再恢复目标页面。

## 关系与权限

- 申请不等于好友；仅收件人可接受或拒绝，申请人仅可取消。双方同时申请不会跳过确认。
- 删除好友后立即失去新的聊天读写权限；原始消息保留，重新成为好友可恢复历史。删除不等于替双方删除已发送消息。
- 任意一方拉黑后，双方不能申请或聊天；拉黑同时解除好友/待处理申请。解除拉黑不自动恢复好友。
- 封号、改密和账号删除沿用现有逐请求鉴权。被封号/删除或被任一方拉黑的用户不出现在可互动的搜索、好友或申请列表中。
- 搜索只返回用户名、昵称、ID及与当前人的关系，不返回密码、盐、角色或其他会话内容。所有聊天端点逐次校验双方关系。

## 数据与并发

`social_schema.py` 在现有 `init_db` 内幂等建表，保留旧数据和参与表迁移事务。`friend_links` 使用规范化双方ID作为唯一键，记录申请方和关系状态；`social_blocks` 为单向拉黑表。`direct_messages` 持久化发送人、收件人、正文、UTC时间和客户端发送标识；`direct_reads` 保存每个人在该对话的已读游标。

写操作使用 `BEGIN IMMEDIATE`，关系检查与写入在同一事务中，避免同意/删除/拉黑和发送之间的竞态。读取使用一致快照。SQLite连接继续复用现有线程本地连接，HTTP同步路由在线程池运行，社交不占用游戏tick，也不复用玩家WS。

消息唯一键是 `(sender_id,client_id)`：相同收件人/正文的重试返回原消息，相同标识携带不同内容返回409。消息按数据库ID稳定排序。历史默认最新50条，`before`排除游标并向前加载；`after`排除游标并升序补取，`has_more` 为真时继续拉取，避免离线积压超过一页时丢消息。一次最多100条。

已读只推进到请求游标以内的本对话收件消息，使用MAX单调更新，不会把游标之后的新消息顺手标为已读；对方读取进度用于自己的发件回执。申请重新发送至少间隔60秒，每分钟最多20个新申请；好友最多200人。文字发送每账号10秒最多10条，幂等重试不重复计数。

## 接口

均需现有 Bearer JWT。`/api/social` 是账号社交，与局内快捷语和只读观战接口独立。

| 方法 / 路径 | 请求 / 返回 |
|---|---|
| GET `/api/social` | 好友及最近消息/未读数、收到/发出申请、本人拉黑列表、`unread_total` |
| GET `/api/social/summary` | 轻量 `unread_total/incoming_total`，供底栏角标刷新 |
| GET `/api/social/users?q=用户名` | 精确搜索，`items` 含 `relation`（none/friend/incoming/outgoing） |
| POST `/api/social/requests` | `{user_id}` |
| POST `/api/social/requests/{peer}/{accept|decline|cancel}` | 处理或取消申请 |
| DELETE `/api/social/friends/{peer}` | 删除好友 |
| POST / DELETE `/api/social/blocks/{peer}` | 拉黑 / 解除本人拉黑 |
| GET `/api/social/chats/{peer}` | 可选 `before` 或 `after`、`limit`；返回 `peer/items/has_more/peer_read_through` |
| POST `/api/social/chats/{peer}` | `{body,client_id}`，返回服务器确认的消息 |
| POST `/api/social/chats/{peer}/read` | `{through_id}`，返回实际单调读取进度 |

未知字段/错误类型/超长输入422；无权聊天403；目标或申请不存在404；关系或重试标识冲突409；过频429。

## 调研与取舍

- [React Native AppState](https://reactnative.dev/docs/appstate)：前后台状态独立于导航焦点；两者共同决定是否刷新与标读。
- [React Navigation useFocusEffect](https://reactnavigation.org/docs/use-focus-effect/)：离开页面清理任务，异步返回需判断当前会话，防旧账号/旧会话结果覆盖新页面。
- [SQLite事务](https://www.sqlite.org/lang_transaction.html)：关系校验与消息写入必须串行化，读列表和权限来自同一快照。
- [FastAPI同步路由线程池](https://fastapi.tiangolo.com/async/)：沿用现有同步SQLite调用方式，不把阻塞数据库操作放进游戏事件循环。

采用现有HTTP鉴权与有界前台轮询，先完整实现好友确认、消息持久化、分页、已读与重试契约；不新增原生依赖或引入游戏WS中的自由文本消息。
