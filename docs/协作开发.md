# 协作开发流程

> 面向所有参与本项目的人。改动协作方式前先改本文档。

## 分支模型

| 分支 | 谁在用 | 说明 |
|---|---|---|
| `main` | 维护者 | 稳定分支。**只有维护者能合并 PR / 打发布提交**，其他人不要直接往它推。 |
| `dev/<用户名>` | 每位开发者 | 从 `main` 切出，自己的开发分支。测试全绿后推上去，联系维护者合并。 |

`dev/<用户名>` 用你自己的用户名（或 GitHub 账号名）作后缀，一人一个，互不覆盖。

### 关于公开仓库的历史

**`main` 是快照式提交，远端不含维护者本机的完整开发历史** —— 公开仓库里只有公开
快照提交，以及后续经 PR 合并进来的 `dev/<用户名>` 分支提交（原因见下面的「敏感信息」）。所以：

- 克隆下来看到的历史很浅，**不要以为项目只提交过几次**；
- 不要对 `main` 做 `git push --force`、`--mirror` 之类的操作；
- 你的 `dev/<用户名>` 分支按正常方式提交、推送即可，合并时由维护者处理；
- 合并 PR 会把该分支的**提交历史**一起公开——推分支前先看 `git log`，
  历史里出现过的密钥删不掉（见「发版流程 → 提交历史」）。

## 流程

```bash
# 1. 从最新的 main 切分支
git fetch origin
git checkout main && git pull
git checkout -b dev/<用户名>

# 2. 开发 + 自测（见下面「合并前的测试要求」）
#    ...

# 3. 提交并推送自己的分支
git add -A
git commit -m "feat: 新增某某功能"
git push -u origin dev/<用户名>

# 4. 完成一个可发版的版本后，按下面「发版流程」整理并开 PR
```

**不要**把 `dev/<用户名>` 直接合并进 `main` 再推 —— 合并到 `main` 是维护者的动作。

## 合并前的测试要求

按改动范围跑，**下面四项是底线**（命令与前置条件见 `docs/测试矩阵.md`）：

| 检查 | 命令 | 何时必须跑 |
|---|---|---|
| 后端单测 | `cd server && python -m pytest test/ -q` | 动了 `server/` 任何代码 |
| 类型检查 | `cd app && npx tsc --noEmit` | 动了 `app/` 任何代码 |
| 视觉与静态审计 | `python test/visual_audit.py` | 动了界面（**前后端都要在跑**） |
| 相关 E2E | `python test/e2e_*.py` | 动了对应游戏/流程 |

新增游戏或改动对局屏时，**必须**同步检查这几处（漏掉不会报错，只会静默失效）：
对局屏进 `backGuard.PROTECTED_SCREENS` 并接 `onConfirmLeave`、战绩快照分支、
`help.tsx` 帮助文案、`app/src/games.tsx` 游戏名单、`RoomScreen` 游戏类型与人数规则。

## 发版流程

> **分工**：**协作者**把这一版做完整，与 `main` 对齐，整理好文档与目标版本号，在
> `dev/<用户名>` 上开 PR；**维护者**在 GitHub 审阅合并，再回到**服务器**构建 APK、
> 部署、验证并打发布提交。
>
> 协作者**不构建 APK**（Android SDK 与真实地址都在维护者服务器上），**不往 `main` 推**；
> 构建与线上部署只发生在维护者一侧。

一句话版本：**协作者先把 `main` 合进来 → 全量测试 + 文档/版本号整理 → 推分支开 PR；
维护者 GitHub 合并 → 服务器构建部署 → 验证 → 打发布提交 → 通知大家同步。**

> **AI 可全程执行**：上面的 GitHub 动作都能用 [`gh` CLI](https://cli.github.com/) 完成——
> 协作者先 `gh auth login` 登录自己的账号，再 `gh pr create`；维护者侧用
> `gh pr view / diff / merge`。命令写在对应步骤里，**不需要额外的 GitHub skill**。
> **合并 PR、推 `main`、发版属于对外可见的写操作**——AI 可以准备好命令与审查结论，
> 但执行前要由人确认。

### 一、协作者：先与 main 对齐，提前解冲突

**提 PR 前必须把最新的 `origin/main` 合进自己的分支。** 把冲突留到合并那一刻，维护者
没有你的上下文，最容易解错；而且 PR 页面上的冲突提示会拖慢整个发版。

```bash
git fetch origin
git checkout dev/<用户名>
git merge origin/main

# 解冲突 → 提交 → 重新跑一遍测试（见「合并前的测试要求」）
git add -A
git commit -m "merge: 合并 main 到 dev/<用户名>"
git push
```

- 冲突高发区：`CLAUDE.md`、`docs/更新计划.md`、`docs/游戏设计/README.md`、
  `docs/测试矩阵.md`、`docs/接口协议.md`、`app/src/theme.ts`，以及 `ws.py`、
  `room_settings.py` 这类注册表式文件。
- **按语义合并，不要按「选我 / 选他」草率了事**：文档两边的内容都保留；注册表两边都加项；
  数值冲突先弄清楚哪边是已发布版本的值。
- 合并后**必须重跑测试**——冲突解错往往只在测试里暴露。再确认没有残留冲突标记：
  `git diff --check`。
- 统一用 `git merge`，**不要用 `git rebase` 重写已推送的提交**：rebase 之后 GitHub 上的
  PR 对比、别人的分支基线都会变乱。

### 二、协作者：发版前整理

#### 1. 测试全跑，不是按需跑

发布前按 [`docs/测试矩阵.md`](测试矩阵.md) **全跑**（后端 `50541` + web `50540` 都要在跑）：

```bash
scripts/status.sh
(cd server && python3 -m pytest test/ -q)   # 有 server/.venv 就用 .venv/bin/python
(cd app && npx tsc --noEmit)
python3 test/visual_audit.py
# 本版涉及的 e2e_*.py 与脚本式测试（test_ws_game / balance_stasis / bench_* 等）
```

新增游戏或改动对局屏时，把「合并前的测试要求」里那几处接线逐项核一遍。

#### 2. 文档

| 位置 | 要做什么 |
|---|---|
| `docs/更新计划.md` | 首行 `当前版本：vX.Y.Z`；把本版完成的条目从「计划更新」移到 `## 已完成 → ### vX.Y.Z（日期）`；没完成的留在原处并重排优先级；本版**明确不做**的方向写清理由 |
| `docs/游戏设计/<游戏>/` | 改玩法/数值/交互的写回 `设计.md`；新游戏必须有 `设计.md` + `增强调研.md`（来源链接、采纳与**不采纳**的理由） |
| `docs/接口协议.md` | 改了 WS / HTTP 消息必须同步（字段、时序、逐人下发还是广播） |
| `docs/测试矩阵.md` | 新增/改动测试脚本要补一行，写清覆盖的断言与时序陷阱 |
| `docs/使用指南.md` / `README.md` | 玩家可见的变化（新游戏、新玩法、人数/入口变化） |
| 根 `CLAUDE.md` | 只更新「当前版本」行与跨游戏约定；**版本流水账不进 CLAUDE.md** |

#### 3. 版本号

- 版本规则：修 bug → 第三位 +1；向下兼容的新功能 → 第二位 +1；不兼容改动 → 第一位 +1。
- **协作者要改**：`docs/更新计划.md` 首行的目标版本、`app/app.json` 的 `expo.version`
  （作为本版目标版本，PR 标题与文档都以它为准）。
- **协作者不要改**：
  - `app/app.json` 的 `expo.android.versionCode`：`bin/release-apk.sh` 在维护者服务器上
    **自动 +1**，提前改会跳号；
  - `server/config/config.json`：本机真值、**不进版本库**，发版脚本会在维护者服务器上双写。
- 最终以维护者构建时传入的版本号与脚本写回的 `versionCode` 为准；两者不一致时，
  维护者要回头把文档里的版本号补齐。

#### 4. 敏感信息与临时文件

```bash
git status                                   # 临时脚本、构建产物、config.json 都不该出现
git grep -n -I -E "(api[_-]?key|secret|token|password|AKIA|AKLT|X-Tos-)" -- .
```

`server/config/config.json`、`server/config/jwt_secret.key`、`tmp/`、`test/tmp/`、
构建产物一律不提交（红线见下文「敏感信息」）。

#### 5. 提交历史

- `git log --oneline origin/main..HEAD` 自查：一个提交只做一件事，信息符合「提交信息」规范。
- **PR 的提交历史会随合并一起进入公开仓库**，所以不能只看最终文件 —— 历史里出现过的
  地址、口令、密钥**删不掉**，只能作废重发。不确定就先问维护者。

### 三、协作者：推送并开 PR

```bash
git push -u origin dev/<用户名>
```

在 GitHub 开 PR：**`dev/<用户名>` → `main`**。标题写清目标版本，例如
`v1.20.0：每日挑战与排行榜`。正文至少包含：

- 这一版做了什么（按「新功能 / 修复 / 文档」分组）；
- **跑了哪些测试、结果如何**（列命令；E2E 写脚本名与步数）；
- 是否已与 `main` 对齐、有冲突时怎么解的；
- 界面变化附截图（**APP 端与浏览器端各一张**，两端行为不总一致）；
- 风险、已知遗留、需要维护者特别注意的地方。

```bash
# 正文先写成文件再传，避免 shell 引号/换行转义问题
gh pr create --base main --head "dev/<用户名>" \
  --title "v1.20.0：每日挑战与排行榜" \
  --body-file /tmp/pr-body.md
```

开 PR 后**不要再 `--force` 重写历史**；要补改动就追加提交，PR 会自动更新。

### 四、维护者：GitHub 审阅与合并

```bash
git fetch origin
git log --oneline origin/main..origin/dev/<用户名>    # 审提交历史，不只看 diff
git diff --stat origin/main...origin/dev/<用户名>

# 用 gh 审 PR（只读；PR 号从 gh pr list 拿）
gh pr list --state open
gh pr view <PR号> --json title,body,files,commits,author
gh pr diff <PR号>
gh pr checks <PR号>          # 本项目暂无 CI，通常为空
```

1. **红线检查**：没有 `server/config/config.json`、密钥、真实地址；`versionCode`
   没有被手改；版本号与 `docs/更新计划.md` 一致；文档与测试说明齐全。
2. **测试结论**：本项目暂无 CI，以 PR 里的命令与输出为准；有疑虑就在本地拉分支复跑，
   不要靠猜。
3. **合并方式选 `Create a merge commit`**（不要 Squash、不要 Rebase）：
   - 保留协作者的提交与作者信息，也保留「谁改了什么」的追溯能力；
   - 协作者继续在 `dev/<用户名>` 上开发时，不会因为历史被重写而反复冲突。
   ```bash
   gh pr merge <PR号> --merge      # 等价于 GitHub 的 Create a merge commit
   ```
4. **不要对 `main` 做 `force-push` / `--mirror`**：`main` 是公开快照分支，历史只增不改。
5. 合并后**不要删除协作者的 `dev/<用户名>` 分支**，他还要继续用；分支落后时由协作者
   自己合并 `main`（见文末「发版后」）。
   - 仓库已关掉 `delete_branch_on_merge`；`gh pr merge` **不要**加 `--delete-branch`。

> `main` 的分支保护要求 1 个 approving review，但 `enforce_admins=false`——维护者账号
> （`ADMIN`）可以绕过，所以自己的 PR 也能合并。**如果以后收紧 `enforce_admins`**，
> 就需要另一个人 approve（`gh pr review <PR号> --approve`），否则 AI 只能把审查结论
> 准备好、停在合并前等人点头。

### 五、维护者：服务器构建、部署与收尾

在**维护者服务器**上执行（有 `server/config/config.json` 与 Android SDK 的那台）：

```bash
git checkout main
git pull --ff-only origin main

# 1) 合并后的最终门禁：发布前全跑，构建前必须通过
scripts/status.sh
(cd server && .venv/bin/python -m pytest test/ -q)   # 没有 .venv 就用 python3
(cd app && npx tsc --noEmit)
python3 test/visual_audit.py
# 相关 e2e_*.py 与脚本式测试

# 2) 构建并部署 APK：自动 versionCode+1、双写版本号、校验地址真的内联进包
bash bin/release-apk.sh <版本号>

# 3) 重启后端（cfg.py 在 import 时读版本号），并验证
scripts/restart.sh backend
curl -s http://127.0.0.1:50541/api/app/version
source scripts/lib.sh && curl -I "$(public_base)/media/app-release/gamehub-latest.apk"
```

验证通过后，打发布提交并推 `main`（这是维护者**唯一**可以直接提交的场景——发版记账；
功能代码仍一律走 PR）：

```bash
git status                     # 应只有 app/app.json（version/versionCode）与要补的文档行
git add app/app.json CLAUDE.md docs/更新计划.md
git commit -m "chore: 发布 vX.Y.Z（versionCode N）"
git push origin main
```

发布提交里写清：本版内容、验证结果（单测/类型检查/视觉审计/E2E 全过、`/api/app/version`
返回新版本、APK 已部署），以及需要协作者知道的事。

**发版后：**

- 通知协作者拉取新 `main`，并把 `dev` 分支同步过来（用 `git merge origin/main`，不要 rebase）：
  ```bash
  git fetch origin
  git checkout dev/<用户名>
  git merge origin/main
  ```
- 若发版后发现必须紧急修复：照常从 `main` 切分支 / 在 `dev` 分支上修，**走 PR**，
  补丁版第三位 +1；`versionCode` 仍由发版脚本递增，**永远不要手改**。
- 发版当天就出现「构建成功但线上没生效」时，先查两件事：后端是否重启过
  （`cfg.py` 在 import 时读配置）、客户端地址是否在打包时已内联（只改配置不重启/不重打包无效）。

## 敏感信息（公开仓库，务必遵守）

仓库是**公开**的，以下东西一律不要提交：

- `server/config/config.json`（**已 gitignore**，装的是本机真实地址与口令）——
  模板见 `server/config/config.example.json`；
- JWT 密钥、管理员口令、任何 API Key / Token；
- 真实服务器地址与端口（代码里一律从配置或环境变量读，见 `CLAUDE.md`「配置与密钥」）。

排查时用：

```bash
git grep -n -I -E "(api[_-]?key|secret|token|password|AKIA|AKLT|X-Tos-)" -- .
```

**已经提交上去的密钥改不掉，只能作废重发** —— 所以宁可先问一句，也别先提交。

## 提交信息

中文，一行说清做了什么，前缀用：

| 前缀 | 用于 |
|---|---|
| `feat:` | 新功能 / 新游戏 |
| `fix:` | 修 bug |
| `docs:` | 只改文档 |
| `chore:` | 发版、构建、依赖等杂项 |
| `refactor:` | 不改行为的重构 |

一个提交只做一件事；改数值、改协议这类影响面大的改动，在提交信息里写清**为什么改**。

## 提 Issue / 反馈

带上：现象、复现步骤、期望行为，以及**前后端日志**（`tmp/log/{backend,web}.log`）
或报错截图。界面问题请注明是 **APP 端还是浏览器端** —— 两端行为并不总是一致
（`window.*` 一类浏览器专属 API 在 APP 端会直接白屏）。
