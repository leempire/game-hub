# 协作开发流程

> 面向所有参与本项目的人。改动协作方式前先改本文档。

## 分支模型

| 分支 | 谁在用 | 说明 |
|---|---|---|
| `main` | 维护者 | 稳定分支。**只有维护者合并**，任何人不要直接往它推。 |
| `dev/<用户名>` | 每位开发者 | 从 `main` 切出，自己的开发分支。测试全绿后推上去，联系维护者合并。 |

`dev/<用户名>` 用你自己的用户名（或 GitHub 账号名）作后缀，一人一个，互不覆盖。

### 关于公开仓库的历史

**`main` 是快照式提交，远端不含开发历史** —— 公开仓库里只有维护者合并出来的快照
提交（原因见下面的「敏感信息」）。所以：

- 克隆下来看到的历史很浅，**不要以为项目只提交过几次**；
- 不要对 `main` 做 `git push --force`、`--mirror` 之类的操作；
- 你的 `dev/<用户名>` 分支按正常方式提交、推送即可，合并时由维护者处理。

## 流程

```bash
# 1. 从最新的 main 切分支
git fetch origin
git checkout main && git pull
git checkout -b dev/<用户名>

# 2. 开发 + 自测（见下面「合并前的测试要求」）
#    ...

# 3. 提交并推送自己的分支
git add -A
git commit -m "feat: 新增某某功能"
git push -u origin dev/<用户名>

# 4. 联系维护者合并到 main（附上测试结果）
```

**不要**把 `dev/<用户名>` 直接合并进 `main` 再推 —— 合并到 `main` 是维护者的动作。

## 合并前的测试要求

按改动范围跑，**下面四项是底线**（命令与前置条件见 `docs/测试矩阵.md`）：

| 检查 | 命令 | 何时必须跑 |
|---|---|---|
| 后端单测 | `cd server && python -m pytest test/ -q` | 动了 `server/` 任何代码 |
| 类型检查 | `cd app && npx tsc --noEmit` | 动了 `app/` 任何代码 |
| 视觉与静态审计 | `python test/visual_audit.py` | 动了界面（**前后端都要在跑**） |
| 相关 E2E | `python test/e2e_*.py` | 动了对应游戏/流程 |

新增游戏或改动对局屏时，**必须**同步检查这几处（漏掉不会报错，只会静默失效）：
对局屏进 `backGuard.PROTECTED_SCREENS` 并接 `onConfirmLeave`、战绩快照分支、
`help.tsx` 帮助文案、`app/src/games.tsx` 游戏名单、`RoomScreen` 游戏类型与人数规则。

## 敏感信息（公开仓库，务必遵守）

仓库是**公开**的，以下东西一律不要提交：

- `server/config/config.json`（**已 gitignore**，装的是本机真实地址与口令）——
  模板见 `server/config/config.example.json`；
- JWT 密钥、管理员口令、任何 API Key / Token；
- 真实服务器地址与端口（代码里一律从配置或环境变量读，见 `CLAUDE.md`「配置与密钥」）。

排查时用：

```bash
git grep -n -I -E "(api[_-]?key|secret|token|password|AKIA|AKLT|X-Tos-)" -- .
```

**已经提交上去的密钥改不掉，只能作废重发** —— 所以宁可先问一句，也别先提交。

## 提交信息

中文，一行说清做了什么，前缀用：

| 前缀 | 用于 |
|---|---|
| `feat:` | 新功能 / 新游戏 |
| `fix:` | 修 bug |
| `docs:` | 只改文档 |
| `chore:` | 发版、构建、依赖等杂项 |
| `refactor:` | 不改行为的重构 |

一个提交只做一件事；改数值、改协议这类影响面大的改动，在提交信息里写清**为什么改**。

## 提 Issue / 反馈

带上：现象、复现步骤、期望行为，以及**前后端日志**（`tmp/log/{backend,web}.log`）
或报错截图。界面问题请注明是 **APP 端还是浏览器端** —— 两端行为并不总是一致
（`window.*` 一类浏览器专属 API 在 APP 端会直接白屏）。
